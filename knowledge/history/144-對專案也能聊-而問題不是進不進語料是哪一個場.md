# 144：對專案也能聊——**而問題不是「進不進語料」，是「哪一個場」**

- 日期：2026-08-27 · spec 076（階段 70 第一刀）· 相關：

## 轉移：spec 074 把問題問錯了

spec 074 我把它寫成「**外部知識該不該進檢索語料**」，答案是「進搜尋、不進語料」。
那個答案不錯，但**問題本身太窄**。使用者要「對專案也可以聊」的時候才看得出來：

**正確的問法是「哪一個場」。**

| 你站在哪 | 語料 |
|---|---|
| 💬 互動 | 你自己的理解（`why_nodes`） |
| 🧰 開發（站在某個 base 裡） | **那個 base 的 `knowledge/`** |

⇒ 那道膜**沒有變薄**——VizGPT 的判準只在你**明確站在 VizGPT 裡**時是語料，切回來就不是。
spec 074 的兩層測試（行為＋掃描）照樣綠，而且多了一組同形狀的新測試。

⚠️ **判準：當一個「要不要讓 X 進來」的問題答不漂亮時，先問「進到哪裡」。**
兩個場的答案，比一個場加一條例外乾淨得多。

## 三個實作上的決定

- **切塊照標題切，不照字數盲切。** `ext_items` 共 184 萬字、最大一份 226,460 字，
  整份塞不進 context。⚠️ 而盲切會把一條判準腰斬，**腰斬過的塊檢索得到也讀不懂**。
- **向量住自己的表。** `entry_embeddings` 的 id 空間已被 `digest_entries`（正）
  與 `why_nodes`（負）佔了 ⇒ 擠進去是等著碰撞。塊的向量跟著重抓一起作廢，語意剛好。
- **只有四層進語料**（`experience`／`concepts`／`principles`／`vision`）。
  ⚠️ 而**哪幾層進了要說出來**——否則「答不出來」會被讀成「它不知道」。

## ⚠️ 而門檻又量了一次，這次沒有斷點

沿用 `rag_min_score`（0.10）的話，問「Transformer 的殘差匯流排」——knowie 根本不談這個
——它回了 6 段。量：

| 問題 | 最高分 |
|---|---|
| 為什麼 why 沒有 oracle？ | **0.824** |
| 知識庫要怎麼收斂？ | 0.442 |
| draft 什麼時候該放手？ | 0.423 |
| **Transformer 的殘差匯流排**（不在這個 base） | **0.441** |
| 義大利麵要煮幾分鐘 | 0.198 |
| 2024 年台北的房價 | 0.263 |

⇒ **明顯離題的（<0.30）切得乾淨；「技術性但不在這個 base」切不掉**
——那是**領域相似**的雜訊，不是主題相關。

⚠️ 而這次跟 [143](143-先量重疊再蓋橋-而那座橋沒有兩岸.md) 的結論**不同**，
理由值得寫下來：**那一刀是「回答」（替你決定），這一刀是「檢索」（給你段落）**。
檢索的失敗代價小得多——你看到出處就知道那段不相干；
而漏掉一段相關的，你會以為那個知識庫不知道。
⇒ **檢索寧可寬、回答必須嚴**；門檻設 0.35 擋掉明顯離題的，其餘靠**每段標出處**由人判斷。
