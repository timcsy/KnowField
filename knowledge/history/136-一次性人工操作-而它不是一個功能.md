# 136：一次性的人工操作——而它**不是一個功能**

- 日期：2026-08-27 · 使用者要求 · 相關：[131](131-行政區-而禁令要做在結構上不是紀律上.md)（那條禁令）

## 發生了什麼

使用者：「可以幫我把原本的分拆掉嗎？我想要重新劃分」，接著「我不要封存，要刪除，因為那是舊時代的了」。

正式庫執行：**79 件歸屬 → 0**（知識 118 件完全沒動）· 6 個領域 **封存 → 抹除**（留 6 塊疤）。
抹除前照 spec 056 檢查「指著它的東西」＝ 0。舊對照表存在 `/tmp/kf-before-redistrict.json`。

## ⚠️ 為什麼要留這一篇：它跟階段 63 的禁令看起來矛盾

階段 63 特地讓**全量重劃在 API 層面不存在**——劃界只讀 `domain_id IS NULL`。
而這次卻把 79 件歸屬清空了。未來的讀者一定會問：「不是說做不到嗎？」

⇒ 界線在這裡：

| | 誰發動 | 存在形式 |
|---|---|---|
| **禁止的** | 系統／介面 | 一個按鈕、一條 API ⇒ **會被例行使用** |
| **這次做的** | **人明確要求的一次** | 沒有按鈕、沒有 API，動手做的 |

⚠️ 而**沒有因此加一個「重新劃分」按鈕**——那正是這篇存在的理由：
**做過一次，最自然的下一步就是把它產品化，而那會把結構上的禁令變回紀律上的。**

⇒ 判準：**這件事做完之後，最自然的下一步會不會把剛立的禁令拆掉？**
會 → 那就要在這裡寫下「不要」，而不是靠下次記得。

## 兩個順帶的紀律

- 走的是**自己設計的兩道門**（封存 → 抹除），不是 raw `DELETE`——
  raw SQL 會繞過 `_LIVE`、繞過疤、繞過「抹除只作用在遺骸上」那條。
- **先存對照表再動**（記錄轉移，不只記錄狀態）：79 件原本在哪，事後仍然查得到。
