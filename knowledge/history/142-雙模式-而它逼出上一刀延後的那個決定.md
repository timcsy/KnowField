# 142：雙模式——**而它逼出上一刀刻意延後的那個決定**

- 日期：2026-08-27 · spec 074（階段 69 第一刀）· 相關：
  [141](141-下界不是門檻的性質-是語料規模的性質.md)（前一刀）· 設計源 draft §七

## 這一刀做完了什麼

互動／開發雙模式。開發模式讀階段 68 抓進來的六層——⚠️ **而升的時候才看清楚：
它就是那 514 個檔案的消費者。** 在這之前，它們只被教訓抽取與死指標用到。

## 轉移：「外部知識算不算你的場」——現在必須答

spec 073 的 out of scope 逐字寫著：「讓 `ext_items` 進搜尋／檢索語料——那是**另一個決定**，
不順手做掉」。而 §七 的判準是「**⌘K 必須跨模式**——Spark 跟即時通訊搜不到彼此就是那個病」。

⇒ 拖不下去了。而它有一個乾淨的答案，**因為那本來就是兩件事**：

| | 是什麼 | 外部知識 |
|---|---|---|
| **搜尋**（⌘K） | 「找得到」 | ✅ 進——但**每一筆標來源**，而且排在你自己的場之後 |
| **檢索語料** | 聊天時當你的**地基** | ❌ 不進——那是原則 6 那道膜守的東西 |

⚠️ 混為一談的失敗方式是**沉默的**：別人的判準會**沒有經過冊封**就開始影響你的回答，
而畫面上一切正常，回答只是慢慢變成別人的。
⇒ 所以那條線有**兩層**測試：行為層（語料裡搜不到那句話）＋掃描層（語料的組成不含任何 `ext_` 表）。

## ⚠️ 判準：一個被延後的決定，會被下一刀逼出來——而那正好是它該被決定的時候

我在 spec 073 把它標成「另一個決定」時，看起來像謹慎。而它其實是**沒有足夠資訊**：
那時外部知識還沒有讀者，「該不該進搜尋」問不出答案。
到了雙模式，讀者出現了，答案就自明了。

⇒ **延後一個決定的正確理由是「還沒有資訊」，不是「還沒想好」。**
判準：**問「什麼事情發生之後，這題會自己有答案？」**——答得出來就等它；答不出來就是在拖。

## 三個寫進結構的禁令（都撞得紅）

- **寫在哪就算哪邊** ⇒ **沒有「移動」功能**。有了它就會有「我到底搬過去了沒」那種狀態
  ——雙模式介面第三個坑。掃原始碼釘住。
- **persona 不進開發模式**——專案 base 天然隔離（它是另一個 repo），再疊一層可見性只是負擔。
- **模式走 URL 不走元件狀態**——可分享、上一頁有用、重整不掉。

## 同日補做：側欄也要換，而主區要全寬

使用者：「**側邊欄也要依據 [互動｜開發] 而有所變化。對於開發而言，側邊欄放的就是專案。**
⋯README 預覽⋯**現在太窄了**⋯可以比照類似領域那樣的佈局，就是類似一個 IDE 的樣子。」
以及「**不要顯示『別的知識庫』了**」。

⇒ 第一版我把「選專案／選層／選檔」全放在**主區**，於是變成
「側欄 ＋ 清單 ＋ 內容」三欄，內容被擠到剩一條。**而 IDE 的形狀是兩欄**：
左邊是檔案樹，右邊是**那一份檔案**。

⚠️ 而我**又做錯一次**：第二版把檔案樹也塞進側欄，於是主區只剩預覽。
使用者再講一次：「**我的側邊欄要放的是專案，然後主要區域的左邊是檔案樹，右邊是預覽**」。

⇒ IDE 是**三段**，不是兩段：

| | 放什麼 | 寬度 |
|---|---|---|
| 側欄 | **專案**（就這樣） | 16rem |
| 主區左 | 檔案樹（層＝資料夾、檔案＝葉子） | 14–16rem |
| 主區右 | **預覽** | 剩下全部；字行收在 56rem |

實測字行寬度：13 吋 44rem · 14/16 吋以上 56rem。
（第一版：清單與預覽擠在同一個 `max-w-3xl` 裡 ⇒ 字行只有約 30rem。）

ⓘ 「別的知識庫」移出互動側欄，改成開發側欄的「⚙ 管理專案」。

⚠️ **同一件事我連錯兩次**，而兩次都是我把「左邊」讀成了「側欄」。
⇒ 判準：**使用者描述版面時，先把它畫成一張欄位表再動手**——
「左邊」是相對於**某個容器**說的，而容器是誰，只有畫出來才會發現雙方講的不是同一個。

ⓘ 而這一步幾乎沒有成本，是因為**模式與位置一開始就走 URL**（FR-002）：
側欄與主區各自讀 `?base=&layer=&doc=`，**不需要共享狀態、不需要溝通**。
⇒ 判準：**當兩塊介面要看同一個選取，先問「它能不能是網址的一部分」**——
能的話，拆開重排就只是搬 JSX；不能的話，就要一路傳 props 或開 context。

### 再一次：檔案樹要是**真的樹**，而手機要是 master-detail

使用者：「這邊用檔案樹呈現會比較好」（附圖）＋「也要想一下行動版的畫面」。

⚠️ 我做的是「**層的籤 ＋ 平面清單**」。而那個形狀**說不出巢狀**——
`knowledge/skills/knowie-pull/SKILL.md` 有三層，被壓成一行檔名之後，
「它在哪個 skill 底下」就不見了。⇒ 改成真的樹：資料夾可展開、深度不限、資料夾在前。

⚠️ 而「層」這個概念本來就是**從路徑導出來的**（`layer_of`）。
用它當導覽，等於**拿一個衍生物取代原本的結構** ⇒ 判準：
**當一個分類是從結構算出來的，別讓它取代那個結構當導覽——它只該是篩子。**
（API 的 `?layer=` 留著給搜尋結果連過來，但樹改成一次拿全部路徑。）

**行動版**：三欄在手機上不可能 ⇒ **master-detail**（沒選檔＝樹滿版、選了＝預覽滿版
＋「← 檔案」）。ⓘ 而它**不需要任何新狀態**——「有沒有選檔」本來就在網址裡（`?doc=`）。
那是「選取放 URL」的第三次紅利（前兩次：重排免溝通、⌘K 直接送到另一個模式的某份檔案）。

ⓘ 展開狀態**刻意不進 URL**：它是**當下的視線**，不是位置。
塞進網址的話，分享出去的連結會帶著你的展開狀態——那不是對方要的東西。
⇒ 判準：**位置進網址，視線不進**。

### 行動版：切模式**不該**關抽屜

使用者：「我在行動版切換到開發的時候，**側邊欄會自己縮回去**。」

原因：`ModeSwitch` 拿到 `onNavigate`，點擊時就關抽屜。而那個 handler 的用意是
「**你選了一個目的地，抽屜可以收了**」——對每一個導覽連結都對，唯獨對模式切換是反的：
**你切過去，就是要看新的那份側欄**（開發那邊是專案清單）。關掉等於把你要看的東西收走，
然後你得再點一次漢堡。

⇒ 判準：**「導覽到某處」關抽屜；「換一組導覽」不關。**
順帶把模式也放到手機頂端那條，不開抽屜就切得了。

ⓘ 同時放大檔案樹的字（`text-xs → text-sm`）。⚠️ 而順手掃過去才發現
「← 檔案」也是 `text-xs`——**它是手機上的點擊目標，不是說明文字**。
⇒ 判準：**看到小字先問「它是給人讀的、還是給人按的」**——按的那些不能小。

### 收尾：移除 base ＋ 「管理專案」搬進開發模式

使用者：「把移除 base 做一做，然後**管理專案那邊也要修一下，更好融入現在的開發 UI**。」

⚠️ 而「不融入」的**根本原因不是樣式**：那一頁在 `/bases`，而
`dev = pathname.startsWith("/dev")` ⇒ **點進去側欄整個切回互動那套**。
⇒ 判準：**「它算哪個模式」是路由的事，不是樣式的事。**
搬成 `/dev/bases`（舊連結留一條轉址），側欄的「⚙ 管理專案」才亮得起來，
而版面自動吃到 `isFull`（同一個判斷）。

ⓘ 順手修掉一個安靜的錯：側欄原本用 `window.location.pathname` 判斷「我在哪」
——**它不隨路由更新**，於是那個訊號會停在你第一次進來的那一頁。改 `useLocation`。

**移除**是**真的刪**，四張表一起清。⚠️ 而它跟 spec 055 的「封存→抹除」不同族：
外部知識是**別人 repo 的快照**，重加一次就回來 ⇒ 沒有遺骸要留。
（那一套是給**你自己的**知識用的，因為那些刪掉就真的沒了。）
⚠️ 而**已冊封的借來判準不動**——它們是 `why_nodes`，你冊封過，那是你的了。
對話框把這兩件都講出來：**刪除的提示要說「留下什麼」，不然人不敢按，或按了才後悔。**
