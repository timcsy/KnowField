# 142：雙模式——**而它逼出上一刀刻意延後的那個決定**

- 日期：2026-08-27 · spec 074（階段 69 第一刀）· 相關：
  [141](141-下界不是門檻的性質-是語料規模的性質.md)（前一刀）· 設計源 draft §七

## 這一刀做完了什麼

互動／開發雙模式。開發模式讀階段 68 抓進來的六層——⚠️ **而升的時候才看清楚：
它就是那 514 個檔案的消費者。** 在這之前，它們只被教訓抽取與死指標用到。

## 轉移：「外部知識算不算你的場」——現在必須答

spec 073 的 out of scope 逐字寫著：「讓 `ext_items` 進搜尋／檢索語料——那是**另一個決定**，
不順手做掉」。而 §七 的判準是「**⌘K 必須跨模式**——Spark 跟即時通訊搜不到彼此就是那個病」。

⇒ 拖不下去了。而它有一個乾淨的答案，**因為那本來就是兩件事**：

| | 是什麼 | 外部知識 |
|---|---|---|
| **搜尋**（⌘K） | 「找得到」 | ✅ 進——但**每一筆標來源**，而且排在你自己的場之後 |
| **檢索語料** | 聊天時當你的**地基** | ❌ 不進——那是原則 6 那道膜守的東西 |

⚠️ 混為一談的失敗方式是**沉默的**：別人的判準會**沒有經過冊封**就開始影響你的回答，
而畫面上一切正常，回答只是慢慢變成別人的。
⇒ 所以那條線有**兩層**測試：行為層（語料裡搜不到那句話）＋掃描層（語料的組成不含任何 `ext_` 表）。

## ⚠️ 判準：一個被延後的決定，會被下一刀逼出來——而那正好是它該被決定的時候

我在 spec 073 把它標成「另一個決定」時，看起來像謹慎。而它其實是**沒有足夠資訊**：
那時外部知識還沒有讀者，「該不該進搜尋」問不出答案。
到了雙模式，讀者出現了，答案就自明了。

⇒ **延後一個決定的正確理由是「還沒有資訊」，不是「還沒想好」。**
判準：**問「什麼事情發生之後，這題會自己有答案？」**——答得出來就等它；答不出來就是在拖。

## 三個寫進結構的禁令（都撞得紅）

- **寫在哪就算哪邊** ⇒ **沒有「移動」功能**。有了它就會有「我到底搬過去了沒」那種狀態
  ——雙模式介面第三個坑。掃原始碼釘住。
- **persona 不進開發模式**——專案 base 天然隔離（它是另一個 repo），再疊一層可見性只是負擔。
- **模式走 URL 不走元件狀態**——可分享、上一頁有用、重整不掉。

## 同日補做：側欄也要換，而主區要全寬

使用者：「**側邊欄也要依據 [互動｜開發] 而有所變化。對於開發而言，側邊欄放的就是專案。**
⋯README 預覽⋯**現在太窄了**⋯可以比照類似領域那樣的佈局，就是類似一個 IDE 的樣子。」
以及「**不要顯示『別的知識庫』了**」。

⇒ 第一版我把「選專案／選層／選檔」全放在**主區**，於是變成
「側欄 ＋ 清單 ＋ 內容」三欄，內容被擠到剩一條。**而 IDE 的形狀是兩欄**：
左邊是檔案樹，右邊是**那一份檔案**。

| | 之前 | 現在 |
|---|---|---|
| 側欄 | 兩個模式共用（領域／對話／身分） | 開發模式換成**專案樹**（專案 → 層 → 檔案） |
| 主區 | 18rem 清單 ＋ 剩下的 | **只有那一份檔案**，全寬（`/dev` 進 `isFull`） |
| 「別的知識庫」 | 在互動側欄 | 移到開發側欄的「⚙ 管理專案」 |

ⓘ 而這一步幾乎沒有成本，是因為**模式與位置一開始就走 URL**（FR-002）：
側欄與主區各自讀 `?base=&layer=&doc=`，**不需要共享狀態、不需要溝通**。
⇒ 判準：**當兩塊介面要看同一個選取，先問「它能不能是網址的一部分」**——
能的話，拆開重排就只是搬 JSX；不能的話，就要一路傳 props 或開 context。

## 兩個自己的錯

- ⓘ **markdown 洩漏第四次**：又在 JSX 純文字裡寫了 `**其他專案**`。掃描器抓到。
- ⚠️ 對抗性驗證時我用 `git checkout src/knowfield/web/app.py` 還原一個攻擊，
  **把那個檔案裡這一刀的未提交改動一起洗掉了**（兩條路由＋排序）。
  是測試把它們一條一條指出來才補回去的。
  ⇒ 判準：**還原一次攻擊要還原「我剛剛改的那一處」，不是「那個檔案」。**
  攻擊前先 `cp` 一份備份，用備份還原——`git checkout` 的粒度是檔案，而攻擊的粒度是一行。
