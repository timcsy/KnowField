## 這一刀做完了什麼

場自己去 GitHub 拿別的專案的 `knowledge/`：GitHub App（`Contents: Read-only`）、
不 clone、六層全抓、其餘只抓目錄樹。實跑三個 repo（含**私有**）：
教訓數 **73／122／421 逐字對上**本機算的，VizGPT 的分支正確抓成 `knowledge-python`。

## 轉移一：tarball 快 8 倍，而我選了慢的

| | 時間 | API 呼叫 |
|---|---|---|
| 逐個 blob（8 併發，287 個 md） | **16.8s** | 288 |
| 整包 tarball | **2.0s** | 1 |

tarball 會把整個 repo（含程式碼）下載下來再丟掉大部分。
⇒ 那讓「**場從來沒有拿過你的程式碼**」從一個**掃程式碼就能驗證的結構**，
退化成一句「有下載，只是沒有留」的紀律。

⚠️ 判準（[131](131-行政區-而禁令要做在結構上不是紀律上.md) 的第二次現身）：
**當一個承諾可以被寫成「程式裡不存在那條路徑」時，就不要用「有那條路徑但我們不走」換效能。**
代價是 15 秒，而那 15 秒發生在一個**幾天才跑一次**的背景任務裡。

## 轉移二：⚠️ 死指標報告第一版有 **467 條**，真的只有個位數

已知答案（`digest/builder.py`，五個檔案指著它）**有找到**——但它埋在 467 條裡。

雜訊的來源，一層一層剝：

| 誤報 | 為什麼 |
|---|---|
| `concepts`、`history/040`、`experience.md` | 那是**相對於 `knowledge/`** 的引用，不是 repo 根路徑 |
| `store/schema.py` | 人會寫**部分路徑**——它其實是 `src/knowfield/store/schema.py` |
| `3/64`、`63/64` | 分數 |
| `why_nodes.kind`、`id/topic/title/markdown` | 欄位名、欄位列表 |

⇒ 收窄成三條機械規則（已知副檔名白名單 · **後綴**比對而非逐字相等 · 知識庫內相對引用用前綴解）
之後：**467 → 83**，而已知答案還在最上面。

⚠️ **而根本的錯是：我在猜什麼算路徑——那是語意判斷偽裝成機械判斷。**
它比純粹的語意判斷更危險，因為輸出看起來像一份客觀清單。

⇒ 判準：**一份 90% 是雜訊的報告等於沒有報告**——沒有人會讀第二次，
而它的失敗方式是**被關掉**，不是被發現錯了。
所以「這條算不算」如果需要猜，就**收窄到不用猜的那個子集**，而不是全部報出來讓人自己篩。
（這跟「不擋、要呈現」不衝突：**擋**要寬容，**報**要精確。）

## 順帶：對抗性驗證漏掉的第四種

五種攻擊裡，「把 `default_branch` 改成寫死 `main`」**16 條測試全部照樣綠**
——因為它們全餵**預先抓好的假資料**，`fetch()` 真正的分支邏輯**一次都沒被執行過**。

而實測 VizGPT 的預設分支就是 `knowledge-python`，寫死就是 404 或抓到錯的分支。
⇒ 補了一組把 HTTP 層樁掉、斷言**實際請求的 URL** 的測試，攻擊才紅。

⚠️ 判準：**當測試餵的是「那一步的產物」，那一步本身就沒有被測到。**
這是 [137](137-兩條規則被同一天的實跑推翻-而測試都是綠的.md)
「測試餵的是功能沒被真正使用的版本」的變體——這次不是使用方式，是**管線的上游**。
