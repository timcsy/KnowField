# 015：Web 主題深挖——效能優化與即時進度
> 日期：2026-07-24

階段 6 web 上線後，使用者回饋主題深挖「很久、不知道挖到哪」。分三刀解決。

## 1. 效能：115s → 37s → ~20s
- **根因**：即時拉對**每個候選逐一呼叫 embedding API**（幾十次序列呼叫），又慢又觸發
  額度隔離（allocation_quarantined，見 history/008/012）。
- **批次 embedding**：`Embedder.embed_many`；OpenAI 一次呼叫嵌入多筆（≤64/批）；dedup 語義層
  與 ranking 改用批次 → **115s → 37s**。
- **並行消化**：`article.build_articles` 用執行緒池同時打多則消化 LLM 呼叫（I/O bound，
  as_completed）→ **37s → ~20s**（總時間趨近最慢單則）。
- web 拉縮小規模（arXiv max_results 12、消化上限 6）求互動回應；CLI 仍可全量。

## 2. 即時進度：/pull 阻塞 → SSE 串流（決策轉移）
- **舊**：`GET /pull` 阻塞跑完整條管線才回整頁（使用者盯空白 20s）。
- **新**：`GET /pull` 只回**串流殼**（0.006s）＋新增 `GET /pull/stream`（SSE）逐步推事件：
  「抓到 N 候選 → 去重 M → 排序 → 每篇文章寫好即推 card（1/6..6/6）→ done」。前端
  EventSource 邊收邊插卡片、即時更新進度。快取逐則秒推；串流中失敗推 error 事件。
- **為何**：慢操作要讓使用者看到真實進度、已知就顯示（假 spinner 不夠）。
