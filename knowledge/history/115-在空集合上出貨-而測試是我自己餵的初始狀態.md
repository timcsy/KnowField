# 我在空集合上出貨了一個功能，因為驗收時的初始狀態是我自己餵的

**日期**：2026-08-25 · **spec**：[`specs/050-organizer/`](../../specs/050-organizer/) · **commit**：`7f35010`
**階段**：vision 階段 45

---

## 轉移一：「搬得動」被推翻成「搬不動」

階段 44 的 commit message 寫「知識搬得動」，測試全綠，實跑也真的搬了。
出貨當天使用者問「**現在要如何把知識整理到領域裡面？**」，我去查：

| | 未歸屬／總數（正式庫） | 介面 |
|---|---|---|
| 對話 | **31/31** | `unfiled.length` 只印數字，**清單沒列出來** |
| 核心理解 | **75/75** | 沒有入口（而 `move_knowledge` 早就支援 `why_node`） |
| 文章 | **2/2** | 同上 |

「搬到…」那個下拉掛在 `inDomain(selected.id)` 上 ⇒ **整理的起點動作不存在**。

⚠️ 而我的實跑是這樣做的：**先用 SQL 把資料塞進領域，再測搬動**。
測試與實跑都對，因為我餵了一個**現實中不存在的初始狀態**。

⇒ 判準的形狀：**驗收的起始狀態必須是使用者的起始狀態**，
而使用者的起始狀態幾乎永遠是「**什麼都還沒做**」。

## 轉移二：互動次數是可行性，不是體驗

108 件 × （開下拉 ＋ 選）＝ **216 次點擊**。
這跟 spec 049 FR-004 那條「搬一段跳 15 條詢問 → 第二次就沒人用」**是同一條判準**：
**互動次數超過某個量，功能等於不存在。**

⇒ 批次不是便利功能，是這一刀的主體。拖放是使用者另外要的（2026-08-25 裁決）。

## 轉移三：糾纏的判準在批次下要重寫

單件版本問的是「鄰居**現在**在不同領域嗎」。批次下它會誤報：

> 把對話 A 和它的理解 B 一起搬到「數學」。
> 單件判準：B 現在在別的領域 ⇒ 糾纏。**但搬完兩者都在數學，沒有被拆散。**

⇒ 正確判準是「**搬完之後**兩端是否不同域」——同批成員一律排除。
＋ 同一鄰居可能被多個成員碰到 ⇒ 去重，否則 10 件會顯示成 30 個問題。

## 轉移四：來源的身分是 url，不是 id

`list_source_groups` 是 `GROUP BY de.url` ⇒ **一個「來源」＝一個 url ＝多個塊**。
`_KIND_TABLE` 因此從 `kind → 表` 變成 `kind → (表, 鍵欄位)`。

⚠️ **否決用 `MIN(id)` 當代表**：那不只讓其他塊沒有領域，`MIN(id)` 還會**隨新增塊改變**
——一個會自己漂移的主鍵。實跑驗證：搬 3 個來源 ＝ **224 塊全部**帶上領域。

## ⚠️ 兩個前端的坑（都會安靜地壞）

1. **HTML5 drag-and-drop 在觸控裝置完全不觸發。** KnowField 是 PWA
   ⇒ `draggable`／`onDrop` 那版在手機上**不能拖，也不報錯**。改用 Pointer Events。
   ⓘ 這也是它驗得到的原因——合成滑鼠事件產生 pointer 事件，不產生 drag 事件。
2. **定義在 render 裡的 JSX 元件每次 render 都是新型別**，React 會把整棵子樹卸載重掛。
   拖曳一秒幾十次 render × 105 列 ⇒ **頁面卡死到連截圖都逾時**。
   把 `Row`／`Node` 改成一般函式（`renderRow`／`renderNode`）就好了。

## 被否決的

- **自動分類**——沿用階段 43／44 的裁決。
- **單件端點與批次並存**——第三次「同一件事兩套介面」（spec 045、047 都是拿掉那個）。
- **批次時逐件詢問**——216 次點擊換一個包裝。
