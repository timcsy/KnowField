# 092：回答截斷的可觀測性三刀 ＋ 長度紀律——兩個自洽的假設被實測推翻

> 日期：2026-08-14。承 `history/088`／`089`／`090`（上線後真實使用）。
> 由來：使用者「昨天又有還沒回答完被截斷的狀況了」——「**又**」是關鍵：`e241797` 已把
> `chat_max_tokens` 1200→4096 修過一次，卻復發。接著使用者補上第二個感覺：「**現在 AI 回答的量
> 好像有點太長了，理解上會有一點點小負擔，或許這也是容易超過 4096 的原因**」——這句把兩個症狀連了起來，
> 而且方向對、因果和我猜的不同。

## 一、為何會有「又」：三種斷法在畫面上長得一模一樣

診斷後發現程式**分不出**是哪一種斷，所以上次那刀只治到其中一種：

| | 機制 | 當時的狀況 |
|---|---|---|
| A 撞上限 | 模型講到 `max_tokens` 被切 | `finish_reason` **全程沒有任何一處讀過**；`[DONE]` 照送、`done` 事件照送 → **靜默半句、看起來像好好講完了** |
| B 連線中途斷 | gateway／反向代理／網路 | `_post_stream` 的 `try` **只包住 `urlopen`**，`for raw in resp` 在 try **外面** → `IncompleteRead`／`reset`／timeout 不會變成 `OpenAIError`；`_stream_gen` 又只攔 `(SourceUnavailable, OpenAIError)` → 例外裸奔穿出，SSE 連 `error` 都來不及送 |
| C 前端／SW／網路 | — | 無任何訊號 |

B 是既有教訓的復發（「批次聚合：單一項的例外不該拖垮整批」——**邊界要攔所有失敗，不只你想到的那種**），
只是這次發生在串流路徑上。

## 二、可觀測性三刀（先讓截斷看得見，別急著再調大）

1. **讀 `finish_reason`**：`_post_stream` 解析每個 chunk 的 `finish_reason`，用 **generator 回傳值**傳上來；
   `OpenAIChatBackend.stream`／`FieldChat.reply_stream` 改成 `return (yield from …)` 原樣穿過。
   **選這個做法是為了零簽章變更**——注入的測試替身（普通 generator，回傳 None）照樣能跑，向後相容。
2. **迭代包進 try**：中途例外統一收成 `OpenAIError`（教訓 3）。
3. **`_pump(gen)`**（app.py module-level）：吐 token 並回 `(全文, 截斷原因)`——
   撞上限→`"length"`；中途斷但**已吐過字**→保留已收到的文字、`"connection"`、照送 `done`；
   一個字都沒吐→往上拋成 `error`。`_stream_gen` 的 except 加寬到 `Exception`。
   SSE `done` 多一個 `truncated` 欄；前端 `Message.truncated` → 回覆下方琥珀色提示。

**刻意沒做**：非串流的 `reply()` 仍沒讀 `finish_reason`（對稱缺口，範圍控制）。

## 三、⚠ 兩個自洽的假設，被 4 次 API 呼叫全部推翻

使用者說「回答太長」後，我提了兩個假設——**都用專案自己的概念寫成**，所以聽起來很像洞見：

- **假設 1**：34 條核心理解**全量注入**（實測 system prompt 10,613 字）把回答推長。
  還附了一個漂亮的觀察：「收進的資料走檢索 top-k、核心理解走全量灌，**同一個 prompt 裡兩套標準**」。
- **假設 2**：膜的 **8 條編號指令**被模型**逐條表演**給使用者看（＝「把品質準則列成檢查表 ≠ 得到品質」的背面）。

**實測（真後端 `gpt-5.6-luna`，同題、只變一個變數）：**

| 實驗一：場注入 | 接知識庫 | 不接知識庫 |
|---|---|---|
| 場內題（flow matching vs diffusion） | 2,941 字 | 3,157 字 |
| 場外題（煮麵放多少鹽） | 291 字 | 375 字 |

→ **接場反而略短，差距在雜訊等級。假設 1 沒有證據支持。**（四次 `finish_reason` 全是 `stop`，這輪沒重現截斷。）

| 實驗二：膜（場內題） | 字數 |
|---|---|
| 無 system（模型自然長度） | 3,000 字 |
| 現況的膜 | 2,732 字 |
| **膜 ＋ 一句長度指引** | **447 字** |

→ **拿掉 system 完全，模型自己就寫 3,000 字。膜沒有在推長，還壓了一點。假設 2 也倒。**

**真因**：模型對技術問題的預設就是長篇，而**膜從頭到尾沒有一句提到長度**——
**不是有東西在推長，是從來沒有人叫它短。**

## 四、修法：`_MEMBRANE` 加長度紀律（用實測過的原句）

> **長度紀律**：預設精簡。先用 3–5 句給出核心答案，只有在使用者要求或問題真的需要時才展開細節。
> 不要為了展示上面每一條原則而把它們逐條演出來——那些是你的判準，不是要寫給使用者看的段落。

**逐字用實測過的那句，不潤飾**——改字＝那次實驗就不算數了。

**真路徑驗證**（接場 34 條＋長度紀律，走 `FieldChat.reply_stream`）：**2,941 → 553 字（−81%）**，
`finish_reason='stop'`。且**行為沒掉**：答案仍從既有理解往下接（「你已經抓到的核心可以再補一句…」），
膜仍在擋過度簡化（「不代表所有 FM 和所有 diffusion 都等價」）。**短的是廢話，不是內容。**

**一刀治兩症**：447–553 字根本碰不到 4096——使用者把「太長」和「容易超過 4096」連起來的直覺是對的，
只是因果方向與我猜的相反。

## 五、測試

＋9 條、**369 全綠零回歸**（原 360）：8 條截斷可觀測（`finish_reason` 傳遞／`_post_stream` 中途斷收成
`OpenAIError`／`done` 標 length／中途斷保留半截標 connection／零 token 失敗走 error／正常不標）
＋1 條長度紀律（`_MEMBRANE` 必須含之，且 **bare 模式走另一條路也不能漏**）。
釘住長度紀律那條的用意：日後改措辭時，別讓整條靜默消失。
