# 部署與介面路線（Web → 容器化 → K8s → Helm）

> 怎麼冒出來的：2026-07-23 聊天。使用者問「能不能有 web 介面」，接著「最後想包成 K8s
> 和 Helm」。屬**未定案的方向**——先孵化，不急著蓋；哪天要動再 promote 到 vision 路線圖。

## 方向（使用者想要的終局）
把 LearnNews 從「CLI 批次工具」逐步推成「常駐服務」，最終以 **K8s ＋ Helm** 打包。
架構本來就留了這條路：plan 001 結構決策明寫「核心做成可獨立測試函式庫…**預留日後接 web
介面而不需重寫核心**」。Web／K8s 都只是**再加薄薄一層**，呼叫同一套 digest／pull 核心。

## 建議的漸進里程碑（每步薄、可獨立驗證）
1. **Web 介面**：看今日匯整＋點主題即時拉＋**圖內嵌**（終端看不到圖，web 解鎖配圖價值）。
2. **容器化**：Dockerfile（uv 建置、非 root、健康檢查）。
3. **K8s 清單**：Deployment（web）＋CronJob（每日 `digest`）＋Secret（金鑰）＋PVC（SQLite）。
4. **Helm chart**：把 3 模板化，`values.yaml` 可調 image／排程／模型／資源。
順序理由：K8s/Helm 是**最外層打包**，得先有「要打包的 workload（web＋映像）」；跳過會包出空殼。

## Web 的三種做法（待選）
- **A. 靜態產生**：`digest` 輸出 HTML，瀏覽器開（可排程每日產）。最簡、你自己看。
- **B. 本機小 server（傾向起點）**：輕量 web app，看匯整＋即時拉＋管理興趣。
- **C. 完整前後端**：正式框架＋API＋部署。偏離 YAGNI，現階段不需要。

## 三個關鍵決策（會影響設計，先記著）
1. **SQLite vs Postgres**：SQLite 靠 PVC（ReadWriteOnce）**單副本**對個人工具足夠、守 YAGNI；
   要**多副本**才需 Postgres。→ 建議先單副本 SQLite＋PVC，需要再換。
2. **金鑰/設定注入**：`Config.from_env` 已讀環境變數，所以 K8s 只要把 **Secret 掛成 env**，
   **核心幾乎不用改**（`.env` → k8s Secret，絕不進 image）。
3. **CronJob 時區/頻率**：每日匯整在使用者時區固定時間跑；Helm `values.schedule` 可調。

## 待解/開放問題
- Web 選 A 還是 B？B 用 **stdlib http.server（零相依，貼專案風格）** 還是 FastAPI（開發快）？
- Web 上「點一下就拉」＝即時 LLM 呼叫 → 需**快取/節流**避免狂打 API（成本）。

## ⚠ YAGNI 誠實註記（守憲章原則 IV）
K8s＋Helm 本質是**重基礎設施**。對**個人工具**而言，這是**刻意的部署目標／學習目的**，
**不是核心價值需求**——核心價值（分診＋溯源＋消化）用 CLI 已達成。記這筆是為了讓未來
讀者不要把 K8s 誤當「必要複雜度」。真要蓋時，每層仍要能justify。
