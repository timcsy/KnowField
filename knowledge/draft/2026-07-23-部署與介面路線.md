# 部署與介面路線（Web → 容器化 → K8s → Helm）

> 怎麼冒出來的：2026-07-23 聊天。使用者問「能不能有 web 介面」，接著「最後想包成 K8s
> 和 Helm」。屬**未定案的方向**——先孵化，不急著蓋；哪天要動再 promote 到 vision 路線圖。

## 方向（使用者想要的終局）
把 KnowField 從「CLI 批次工具」逐步推成「常駐服務」，最終以 **K8s ＋ Helm** 打包。
架構本來就留了這條路：plan 001 結構決策明寫「核心做成可獨立測試函式庫…**預留日後接 web
介面而不需重寫核心**」。Web／K8s 都只是**再加薄薄一層**，呼叫同一套 digest／pull 核心。

## 建議的漸進里程碑（每步薄、可獨立驗證）
1. **Web 介面**：看今日匯整＋點主題即時拉＋**圖內嵌**（終端看不到圖，web 解鎖配圖價值）。
2. **容器化**：Dockerfile（uv 建置、非 root、健康檢查）。
3. **K8s 清單**：Deployment（web）＋CronJob（每日 `digest`）＋Secret（金鑰）＋PVC（SQLite）。
4. **Helm chart**：把 3 模板化，`values.yaml` 可調 image／排程／模型／資源。
順序理由：K8s/Helm 是**最外層打包**，得先有「要打包的 workload（web＋映像）」；跳過會包出空殼。

## Web 的三種做法（待選）
- **A. 靜態產生**：`digest` 輸出 HTML，瀏覽器開（可排程每日產）。最簡、你自己看。
- **B. 本機小 server（傾向起點）**：輕量 web app，看匯整＋即時拉＋管理興趣。
- **C. 完整前後端**：正式框架＋API＋部署。偏離 YAGNI，現階段不需要。

## 三個關鍵決策（會影響設計，先記著）
1. **SQLite vs Postgres**：SQLite 靠 PVC（ReadWriteOnce）**單副本**對個人工具足夠、守 YAGNI；
   要**多副本**才需 Postgres。→ 建議先單副本 SQLite＋PVC，需要再換。
2. **金鑰/設定注入**：`Config.from_env` 已讀環境變數，所以 K8s 只要把 **Secret 掛成 env**，
   **核心幾乎不用改**（`.env` → k8s Secret，絕不進 image）。
3. **CronJob 時區/頻率**：每日匯整在使用者時區固定時間跑；Helm `values.schedule` 可調。

## 技術選型（2026-07-23 使用者定案）
- **後端：FastAPI**（async，即時拉不卡；同時好做 HTML 頁面＋JSON API；與 Python 核心無縫）。
  相依：fastapi、uvicorn、jinja2。
- **RWD/樣式：Tailwind**（使用者要 RWD／UI 方便）。MVP 先用 **Tailwind Play CDN**（零 build），
  日後正式再上 Tailwind CLI build。
- **⚠ 偏離零相依（誠實記）**：專案一路守零外部相依（stdlib＋OpenAI urllib）。這裡為了
  **RWD／UX 開發便利**刻意引入 web/CSS 框架——這是使用者明講的真需求，YAGNI 站得住
  （UX 是需求，不是為複雜而複雜）。核心函式庫仍零相依；框架只在 web 這層。

## ⚠ YAGNI 誠實註記（守憲章原則 IV）
K8s＋Helm 本質是**重基礎設施**。對**個人工具**而言，這是**刻意的部署目標／學習目的**，
**不是核心價值需求**——核心價值（分診＋溯源＋消化）用 CLI 已達成。記這筆是為了讓未來
讀者不要把 K8s 誤當「必要複雜度」。真要蓋時，每層仍要能justify。

## UI 打磨 ＋ 上線/多租戶路線（2026-08-06）
> 使用者覺得現在 Jinja2＋Tailwind 的 UI「醜、難用、不是 best practice」，提議 React 重寫；並問「未來要加帳號＋Google 登入」會不會改變做法。

> **⚠ 已推翻（2026-08-06）→ `history/075`**：下面「htmx＞React」的結論被使用者定案推翻——實作一輪 DaisyUI 後確認
> 「大多數 AI 產品的樣子＝shadcn/ui（React）」，且要上線＋PWA 分享（Android），故**改走 React＋Vite＋shadcn re-platform**。
> 憲章 IV 複雜度理由已記 history/075。下段保留為當時的分析（在「不上線、單人、DaisyUI 夠用」前提下仍成立）。

**UI 方向（已被 history/075 推翻，保留當時分析）：設計 pass ＋ htmx，不是 React 全重寫。**
- 「醜」是**設計工**（間距/字級/一致元件），跟 server-render vs client 無關；「難用」的真凶多半是**整頁重載**（表單 303 跳頁、脈絡斷）→ htmx 把它變 inline、零 build、守憲章 IV。
- **❌ React 全重寫**（rejected、**未 commit 故不進 history**）：每條 route 改吐 JSON API ＋ UI 全用 TSX 重畫 ＋ ~345 web 測（打 TestClient 驗 HTML）重寫 ＋ 整套 Node build 鏈——**幾週重現既有功能、零新使用者價值**（重寫陷阱），且撐開刻意壓到最小的相依面（憲章 IV）。要 React 得當**憲章級自覺決定**，不因「UI 醜」滑進去。
- **auth 反而更站得住 server-rendered**：Google 登入＝OAuth 伺服器端 redirect ＋ session cookie，server-rendered 最自然/最安全；SPA 要處理 token 儲存（localStorage XSS／cookie CSRF）反而更難。htmx 不影響 auth。

**上線/多租戶分階**（動機：別被看光＋服務他人＋共享；三件工程量差很大）：
- **A 登入牆**：Starlette `SessionMiddleware` ＋ Authlib（Google OIDC）＋ HTTPS（`knowfield.tew.tw` 前擺 Caddy 自動 TLS）＋密鑰進 `.env`（已 gitignore）。**單人即可安全上線、不需多租戶。**
- **B 多租戶**：每表加 `user_id`、每 query scope（或每人一 db）＝每人隔離的場。**最大改動、跟 UI 框架無關。**
- **C 共享**：見 [[共享的膜與跨base聯邦]]（聯邦、**非共編**；C-MVP＝跨場候選過自家閘門）。
- **誠實界線**：**單人自用先別建 auth/多租戶**（動每表＋每 query 的真工程）——要上線給別人再做；現在只要 UI 別擋住未來加 user_id（htmx 天然不擋）。
