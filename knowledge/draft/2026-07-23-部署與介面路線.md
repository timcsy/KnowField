## UI 打磨 ＋ 上線/多租戶路線（2026-08-06）
> 使用者覺得現在 Jinja2＋Tailwind 的 UI「醜、難用、不是 best practice」，提議 React 重寫；並問「未來要加帳號＋Google 登入」會不會改變做法。

> **⚠ 已推翻（2026-08-06）→ `history/075`**：下面「htmx＞React」的結論被使用者定案推翻——實作一輪 DaisyUI 後確認
> 「大多數 AI 產品的樣子＝shadcn/ui（React）」，且要上線＋PWA 分享（Android），故**改走 React＋Vite＋shadcn re-platform**。
> 憲章 IV 複雜度理由已記 history/075。下段保留為當時的分析（在「不上線、單人、DaisyUI 夠用」前提下仍成立）。

**UI 方向（已被 history/075 推翻，保留當時分析）：設計 pass ＋ htmx，不是 React 全重寫。**
- 「醜」是**設計工**（間距/字級/一致元件），跟 server-render vs client 無關；「難用」的真凶多半是**整頁重載**（表單 303 跳頁、脈絡斷）→ htmx 把它變 inline、零 build、守憲章 IV。
- **❌ React 全重寫**（rejected、**未 commit 故不進 history**）：每條 route 改吐 JSON API ＋ UI 全用 TSX 重畫 ＋ ~345 web 測（打 TestClient 驗 HTML）重寫 ＋ 整套 Node build 鏈——**幾週重現既有功能、零新使用者價值**（重寫陷阱），且撐開刻意壓到最小的相依面（憲章 IV）。要 React 得當**憲章級自覺決定**，不因「UI 醜」滑進去。
- **auth 反而更站得住 server-rendered**：Google 登入＝OAuth 伺服器端 redirect ＋ session cookie，server-rendered 最自然/最安全；SPA 要處理 token 儲存（localStorage XSS／cookie CSRF）反而更難。htmx 不影響 auth。

**上線/多租戶分階**（動機：別被看光＋服務他人＋共享；三件工程量差很大）：
- **A 登入牆**：Starlette `SessionMiddleware` ＋ Authlib（Google OIDC）＋ HTTPS（`knowfield.tew.tw` 前擺 Caddy 自動 TLS）＋密鑰進 `.env`（已 gitignore）。**單人即可安全上線、不需多租戶。**
- **B 多租戶**：每表加 `user_id`、每 query scope（或每人一 db）＝每人隔離的場。**最大改動、跟 UI 框架無關。**
- **C 共享**：見 [共享的膜與跨base聯邦](2026-08-03-共享的膜與跨base聯邦.md)（聯邦、**非共編**；C-MVP＝跨場候選過自家閘門）。
- **誠實界線**：**單人自用先別建 auth/多租戶**（動每表＋每 query 的真工程）——要上線給別人再做；現在只要 UI 別擋住未來加 user_id（htmx 天然不擋）。

## 部署技術棧定案（2026-08-07：Google 登入＋K8s/Helm＋mirrord＋全部 PG）
> 由來：使用者「為了部署做準備」。澄清後**主要是自己用、手機能開（PWA 已有）、公開網址不被看光**
> ——是**單人門鎖，不是多租戶**。逐項定案技術棧。

### ① 手機能用＝部署工作，非寫功能
PWA 階段 27 已做（可裝手機、離線殼）。缺的是**把它 host 在手機連得到的網址**（現在 localhost）＋HTTPS。

### ② 使用者機制＝單人 Google 登入門鎖（非多租戶、非共享的膜）
- Google OIDC（Authlib）＋session（httponly cookie）＋**allowlist = 使用者自己的 Google 帳號**。比自刻密碼穩
  （憑證安全外包 Google，不存密碼）。接既有「A 登入牆」，本次確認＝**單人 allowlist**。
- **釐清（別混）**：這是**單人門鎖**，**不是** [共享的膜與跨base聯邦](2026-08-03-共享的膜與跨base聯邦.md) 的多 base 聯邦，也還不是 B 多租戶（每表 user_id）。
- OAuth client 設定＋同意授權＝**使用者自己在 Google Cloud 做**（AI 不碰憑證動作）；密鑰進 env、不進 git。
- 「不被看光」只在**鎖是真的**時成立：HTTPS（否則路上被看光）＋真 session（非「網址難猜」的假隱私）＝結構上保證（原則 3）。

### ③ K8s/Helm＝使用者既有 cluster＋熟 → requirement-defensible
上方 YAGNI 警告（「⚠ YAGNI 誠實註記」節）**本次解除**：使用者已有 cluster、又熟，部署上去是**最低阻力**路，
非過度工程。SQLite-on-K8s 的坑因④⑤改用 PG 而消失。

### ④ mirrord read-only 開發（本地以遠端資料庫為主）
只用 read-only：dev **讀**遠端資料、**絕不寫回真實場**（接鐵律「dev 不碰真實場、臨時 db/動破壞前備份」）。
PG 下 read-only ＝ **read-only PG role**（寫入被 DB 拒絕＝結構保證，非自律）；MVCC 讓邊讀邊有人寫也拿到一致快照。

### ⑤ substrate 定案：**全部 PG**（supersedes 上「三個關鍵決策」①）
使用者定案「全部 PG」。理由：K8s＋想往分享/多人走 → PG 是**一致 substrate**（app 可無狀態多 replica、
RollingUpdate 正常；SQLite 的單寫者/PVC/Recreate 限制全消失），mirrord read-only 也更乾淨。
- **務實形狀**：prod PG ＋ **碰 DB 的整合測試打容器化 PG（testcontainers）**；**純核心測試（chunk/distill/rag）
  不碰 DB、保持零安裝秒跑**（守「離線 stub、TDD 零安裝」教訓——只有 DB 層才需 PG，不是每個測試都要）。
- **順序**：**PG 遷移排在 auth ＋ 領域分類之前**（那兩個要加表/查詢，在 PG 蓋一次、別 SQLite 蓋完再重港）。
  → 修正先前「領域分類先」的排序（見 [領域知識分類與場的分區](2026-08-07-領域知識分類與場的分區.md)）。
- **scope 守門**（過度擬合就收斂）：① **別把 pgvector 綁進遷移**——這次 job＝**SQLite→PG parity**（行為一樣、
  測全綠）；pgvector（檢索升級）等 parity 站穩再單獨切。② **這是憲章 IV 修憲**（「repository 零相依不變」被
  有意識推翻）——要留因果（history 轉移＋改憲章），是人閘門。
- **遷移 acceptance（待 promote）**：repository 全搬 PG、既有 344 測在「核心 DB-less ＋ DB 層 PG」下全綠、行為零回歸。
