## 為什麼（正中核心）
現在 `/search` 只把搜尋 API 的原始結果倒出來——沒做工具**自己最擅長的事**（消化、溯源、
排序）。洞見：**智慧搜尋＝把工具的核心本領套到 live 搜尋結果上**，本質就是「**RAG／pull
over 開放網路**」。零件全都有，只差串起來。

## 缺口盤點（複用密度極高）
| 動作 | 類型 | 複用零件 |
|---|---|---|
| 讀進 top-N 結果內文 | 處理 | `fetch_url`（2a／spec 006 已有） |
| 依相關度排序、濾雜訊 | 處理 | `Embedder`＋cosine（RAG 已有） |
| 合成一段有引用的繁中整理 | 處理 | RAG answerer（grounded、`[n]` 掛來源、渲染已有） |
| 去重 | 處理 | pull 的 dedup |
| 多角度分頭搜、讀完看缺口再搜 | **探索** | ❌ 新（agentic 迴圈，optional） |

## 核心（MVP，處理優先）
`/search` 打完 query → 除了列原始結果，多做：
1. **抓 top-N 結果內文**（`fetch_url`）。
2. **合成一段繁中「整理」**（RAG answerer）：逐點以 `[n]` 標到對應結果（Perplexity 式重點）。
3. **依相關度排序**結果（Embedder，可選）。
4. 頁面：**頂端「整理」＋下方原始結果清單（仍每則可「收進」）**。

＝「搜尋 → **讀完告訴你重點＋來源** → 你挑要留的收進」。新工只是串接，不重寫核心。

## 探索（optional，更深增量，先勾不做）
把一個 query 拆成 3–5 個角度分頭搜、讀完看缺口再搜（agentic／deep-research 式）。價值高但
**成本翻倍**（多次搜尋＋多輪 LLM）。**列 optional，MVP 先只做「處理」，探索之後再疊。**

## 守原則（硬約束）
- **教訓 7 grounded**：整理**只根據抓到的結果、逐點掛來源、不杜撰**（同 ask 紀律）——不是叫
  模型自由發揮。搜尋 API／抓取失敗要友善繁中（教訓 3）。
- **原則 5 人挑不變**：整理是**閱讀輔助**，不是替你決定；「**收進」仍是人冊封**（AI 撒網＋讀、
  人挑）。工具可標「這幾則最值得收」，但留哪些還是使用者按。

## 待解／開放問題（孵化重點）
1. **抓幾則內文**：top-N=3 還是 5？抓越多整理越全但越慢／越貴。傾向 3–4。
2. **整理與排序的成本**：一次 /search＝N 個 http get＋1 次 LLM（排序再加嵌入）。使用者觸發、
   可接受，但要不要讓「整理」預設開或按鈕才觸發（省額度）？
3. **整理 vs 原始結果的版面**：整理在頂、結果在下；整理的 `[n]` 要能捲到對應結果卡。
4. **抓不到內文的結果**：只用 snippet 進整理，或跳過？（教訓 3：友善標示、不噴錯。）
5. **與 pull 的關係**：pull 已做「消化＋去重＋排序」——智慧搜尋是否就是「pull over 開放網路」？
   要不要日後收斂成同一條管線（pull 吃一個 web-search source）？
