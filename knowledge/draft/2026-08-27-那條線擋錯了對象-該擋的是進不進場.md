# 那條線擋錯了對象——該擋的是**進不進場**，不是拿不拿得到

## 使用者要的

> 「我還在想開發這邊放入 Agent 的可能性，直接支援沙盒的 knowie⋯
>  總之我想要的是**推翻之前說的只看 knowledge**，我要的是可以真的執行幾乎所有的
>  knowie skill，因為這才是我平常習慣跟 knowie 互動的方式，**透過聊想法，最後
>  capture 成 draft**，這才是開發知識庫應有的樣子。而為了要使用 capture，
>  就需要**連不是 knowledge 的檔案也一起看**。」

## 那條線為什麼要移位

舊的結構性禁令：**場永遠看不到 code**（`github/app.py` 沒有 clone／tarball／zipball，
只逐 blob 抓 `knowledge/**.md`）。

而它擋的是「**拿得到**」，真正該擋的是「**進不進場**」。兩件事被綁成同一條，
於是它現在擋掉的是一個完全正當的用途。

⚠️ 判準（這個庫自己記過）：**一條檢查會擋掉好答案時，那條檢查的位置就是錯的。**
不是放寬它，是**問它本來想守什麼**——守的是「別人的 code 不會變成你的地基」，
而那件事發生在**落成來源那一刻**，不是在 fetch 那一刻。

**為什麼使用者的理由成立**：capture 的觸發是「你依賴了什麼」，而回憶單位是
*why ＋ 最小的 how/what*（根公理二）。那個 how/what 常常就是某一行 code、
某個 commit、某次測試紅掉。只給 `knowledge/`，capture 只記得下「我們談過這句話」，
記不下「**我為什麼相信它**」——根公理二直接壞掉。

## 三條替代線（一條換三條，不是拿掉）

1. **讀全開，寫只碰 `knowledge/**`。** 跟舊那條一樣可機械檢查（寫入工具對
   `knowledge/` 以外的路徑**沒有 code path**），而它守住真正重要的：
   **knowie 不改你的程式**。
2. **拿到的 code 不進檢索語料。** 這是舊那條線真正想說的話。
   ⇒ **code 是 agent 的工作材料，不是場的語料。**
3. **出海口只有 PR。** captured ≠ committed 不變：agent 提，人合。

## 讀全部 ≠ 需要沙盒——**這兩件要分成兩刀**

capture／judge／next／consolidate／migrate **全部只需要「讀整個 repo ＋ 寫
`knowledge/`」，沒有任意執行** ⇒ 要的是**工作區**，不是沙盒。

真正需要沙盒的只有一種：**跑那個專案的測試，去驗「這條知識跟 code 還對得上嗎」**。
它很有價值（那是知識腐爛的唯一 oracle），但它是第二刀——第一刀不必扛沙盒的部署複雜度
（k3s 上現在只有一個 web app ＋ PG，agent 要另一個執行面）。

## 已經量到的代價

- **尺寸**：`knowledge/` 是 61 個檔，整個 repo 是幾千個。實測**逐 blob 16.8s vs
  tarball 2.0s** ⇒ 現在**需要** tarball，而那正是被禁掉的那個 API。
  禁令一移位，可行性同時回來。
- **工作區要有 TTL**，留在磁碟／記憶體，**不要進 PG**
  （spec 080 才學到：一個專案 226 筆來源就會把使用者自己的 9 筆擠掉）。

## ⚠️ 「兩個場」會換一個形式回來

你在專案裡 capture 出來的 draft 要落在哪？落進你的 DB ⇒ 你又有兩份短期記憶了
（spec 076／078 那組兩天前才整個刪掉，理由是**兩套一定會漂，而漂掉的那套不會報錯**）。

⇒ 該落在**那個專案的 repo**：capture 產出一個 `knowledge/draft/*.md`，走 PR。
你的 DB 只留「我對這個專案做過什麼」。

ⓘ 這也順帶說清楚 spec 077 退役的是什麼：退的是「**用 GitHub 預填網址寫回**」那個
特定機制（1,000 字上限、跟 draft 綁死），**不是「寫回」這個方向**。

## 被逼出來的第三件事

開發那邊現在只有一次性的唯讀問答。要跑真正的 knowie 互動（聊 → capture → draft），
那個聊天需要**工具**（讀檔、grep、寫檔）⇒ 它從一次問答變成一個 **agent 迴圈**。
那才是 Codex SDK 真正解決的部分（沙盒、檔案工具、多輪 loop、PR），而不是沙盒本身。

而後端至今**刻意只依賴 OpenAI 相容 API**。多一個供應商相依是一個要明講的決定，
不是順手加的相依。判準：**先做不需要 SDK 的那一半**——如果 knowie 需要一整套 SDK
才跑得動，那反而是在說它沒有自己宣稱的那麼可移植。

## 共享與冷啟動：三種消費者，三份材料

⇒ **共享與 RAG 完全不變**，而且**應該**不變。code 不參與這兩件：

| 誰要用 | 材料 | 落不落庫 |
|---|---|---|
| **跨專案共享**（crosscheck、借來的判準） | 只有 `knowledge/`，且只有**已蒸餾過的判準** | 落（`ext_lessons`） |
| **檢索語料**（回答你的問題） | 只有 `knowledge/**.md` 落成的來源 | 落（`digest_entries`） |
| **agent 的工作材料** | 整個 repo | **不落**，TTL 用完就丟 |

理由不是保守：**共享的單位是判準（一句可以拿來判文字的話），不是檔案。**
跨庫比對之所以成立，是因為兩邊各自蒸餾過了才比得出「這兩句在說同一件事」。
實測也支持——**13 個庫算出 49 組，3 個庫只有 3 組** ⇒ 共享是超線性的，
而那個超線性來自**蒸餾密度**，不是資料量。丟幾萬個 code chunk 進去只會稀釋訊號。

## 冷啟動：`knowledge/` 是空的時候，唯一的 oracle 是 git

這其實是移那條線**最強的論證，比 capture 還強**——冷啟動的定義就是
`knowledge/` 不存在，只看它等於看一個不存在的目錄。連「要不要」都不用討論。

而材料不是 code 現狀（那是 knowie 明講不該重複的：code 已經是它自己的真相）。

### 三個順位——由便宜且準，往貴且稀有

1. **搬**：repo 裡**已經寫成散文的 why**——`docs/`、ADR、RFC、README 的「為什麼做這個」、
   CONTRIBUTING 裡的慣例。那是**這個專案自己的 why、已經過人的手**，只是沒有 knowie 的形狀。
   ⇒ 最便宜、最準，而且**完全沒有「別人的東西汙染我的場」的風險**。
   ⓘ 這也讓移那條線的理由更完整：舊禁令擋掉的不只是 code，**連 `docs/` 和 ADR 都拿不到**。
2. **出題 ＋ 找證據**：拿跨庫的 49 組共通判準當**提問**，回這個 repo 找證據。
3. **挖**：git history 的 **revert** 與反覆改動，補那些**從來沒被寫下來**的轉移
   ——「為什麼變成現在這樣」活在 commit 訊息、revert、以及前後的 diff 裡：
   **一次 revert ＝ 一個假設被推翻 ＝ 一條 `history/` 轉移**。最貴、收穫最少，但最獨特。

### RAG 出題，git 作答——而**只做其中一半，會壞得方向相反**

- **只挖 git** ⇒ **挖不到**：幾千個 commit，你不知道要找什麼。
  （RAG 剛好補這一塊：**它給你搜什麼**。）
- **只做 RAG** ⇒ **挖到別人的**：它翻的是別人蒸餾過的判準，所以**一定有話說**
  ——而那些話是別人的 why 掛上你這個專案的名字。

⚠️ 純 RAG 產出的**不是空的庫，是一個貌似合理的庫**。空的庫是誠實的；
貌似合理的庫是**第零天就開始腐爛**，而且**沒有任何消費者會發現它錯掉**。

⇒ 讓混合安全的就是下面那道閘門（每條帶出處）：RAG 愛提什麼都可以，
出處要求會殺掉所有沒有本地證據的東西。

ⓘ 乾淨的切法：**協定的骨架可以照抄，內容不行。**
`.knowie.json`、目錄結構、各層的 README 是**協定**不是主張，直接從別的庫複製是對的。

**而這是整條路上最容易造假的一步**：LLM 讀完一個 repo 可以寫出一整份看起來
非常像 knowie 的漂亮判準，而它們一條 why 都沒有——正好是這個庫記過的
「名字有了、底下什麼都沒有」。⇒ **每條產物硬性帶出處**（哪個 commit、哪個檔），
沒有出處的**直接丟掉**，不是留著讓人事後判斷。

### 而 git 生得出 `history/`，生不出 `experience`

轉移是**單一事件**，commit 與 revert 直接承載它。判準是**跨事件歸納**出來的——
今天那條「斷言是原始碼裡有這個字串時，先問改壞它的最短方式會不會留下那個字串」，
沒有任何一個 commit 包含它，它是看過三次攻擊沒撞紅之後才長出來的。

⇒ 預測：冷啟動生出來的庫會**有 `history/`、幾乎沒有 `experience`**。
而那是**對的形狀**，不是缺陷：experience 本來就該從 history 蒸餾，
那是兩條進料線裡「doing → 反流」那條，需要人在場。

ⓘ 尺寸：`knowledge/` 是 61 個檔，git log 是幾千個 commit ⇒ 你不能「讀」它，只能**搜**。
承載 why 的是極少數，而它們有跡可循：**revert · 訊息異常長的 · 同一個檔反覆被改的 ·
刪掉一個抽象或改名的**。從這四類進去比從頭掃 log 準得多。

## 拿不拿 git：跟著 skill 走的三檔

判準：**git history 的價值，跟這個庫已經反流了多少成反比。**
庫空的 → git 是唯一來源；庫活著、有人反流 → 只剩「上次反流到現在」那一小段；
反流得很勤 → 幾乎挖不出東西，因為 why 早就在 `history/` 裡，而且寫得比 commit message 好。

| skill | 要什麼 | 成本 |
|---|---|---|
| 一般（capture／next／judge 的腐爛偵測） | **工作樹快照**（tarball），不 clone 全史 | 實測 2.0s |
| `judge` 的「有沒有決定沒被記下來」 | `git log <邊界>..HEAD` — **只要增量** | 一小段 |
| `migrate` 順位 1–2（搬 `docs/`、出題找證據） | **工作樹快照**就夠 | 2.0s |
| `migrate` 順位 3（挖沒被寫下來的轉移） | 完整 history | 貴，但只跑一次 |

- **腐爛偵測要的是 code 現狀**（「知識說我們用 X，而現在沒有 X」），不是 git。
  git 只能在**已經發現不符之後**解釋它，而那時人通常自己就知道了。
- **那個「邊界」不用你給**：`git log -1 -- knowledge/` ＝ 最後一次動知識庫的時間點，
  之後的 commit 就是「還沒反流的那批」。

ⓘ 這個收窄最值錢的地方是成本：**一般情況維持在現在的量級**，只有 migrate 才深。

## 開放問題

- 開發模式那五格會多出第六種東西：**動作**（對這個專案跑一次 judge／capture）。
  動作有狀態（排隊／跑了 3 分鐘／失敗）——沿用抓取的 `pending/fetching/…/ok`，
  而**狀態不能在做完之前說 ok**（spec 080 才踩過）。
- 「幾乎所有 skill」裡，寫進三個核心檔的那些（judge 的整理、consolidate）
  一律是 PR，不能是 push——但**PR 本身也是一種 commit 的提案**，
  它跟 knowie 的「人做不可逆的」怎麼對齊？（傾向：PR ＝ 提案，merge ＝ 人的那一刀。）
- 工作區放哪：後端行程內的暫存目錄，還是 k3s 上的 job？前者簡單、後者才擋得住
  第二刀的沙盒需求。
- 跨庫判準當 prior（順位 2）**還是可能把別人的框架套在不適用的專案上**：
  出處閘門擋得掉「沒有證據」，擋不掉「湊得出證據」。
  傾向：那一批**標成借來的**（`⚠️ 借來的`，同 spec 071），讓人一眼看得出來源不是自己。

## 可能的驗收（給未來的路線圖項目）

1. 對一個**沒有 knowie 的**專案跑 migrate → PR 裡出現第一版 `knowledge/`
2. 跟一個專案聊一段 → capture → PR 裡是那個專案的 `knowledge/draft/*.md`
3. ⚠️ 寫入 `knowledge/` 以外的路徑 → **做不到**（不是被拒絕，是沒有那條路）
4. 那個 repo 的 code **沒有**出現在你的檢索語料裡
5. 換 owner／persona 看不到別人的工作區
6. migrate 的產物**每一條都指得回這個 repo 的一個 commit 或一份檔**；指不回的不該存在
   （**這道閘門就是讓「RAG 出題」安全的那一道**）
7. 一個**有 `docs/`／ADR 但沒有 knowie** 的專案 → 產物看得出是**搬**過來的，不是生成的
8. 跑 `judge` 時只抓 `git log -1 -- knowledge/` 之後那一段，不是全史
