# knowie 接進來：讀而不寫——而多專案讓**你自己**成為第二個 base

> 狀態：**draft／未定案設計（thinking-line）**。日期：2026-08-27。
> 怎麼冒出來的：使用者「我想把 knowie 整合進來，變成專案式的知識庫，然後可以有好幾個專案，
> 這些累積的經驗可以快速地餵養新的專案知識庫⋯這樣我們就有『互動/專案』的選擇可以切換了」，
> 後來收斂成 **「互動／開發」**。

## 一、**不要**把 knowie 搬進來——要「接」

knowie 最重要的性質是**它住在 repo 裡，跟程式碼同一個 commit**。
而這個論證你自己寫過，就在 `skills/ship-knowfield/SKILL.md` 的開頭：

> 這些都寫在我的私人記憶裡過——但那不是專案的小腦，**Codex／Gemini 看不到**，
> 換一台機器也沒有。所以它該在這裡。

把 knowie 搬進 KnowField 的資料庫，就是**把那個論證反著跑一遍**：
轉移記錄跟 diff 分家 · repo 裡的其他 AI 看不到 · 換台機器就沒有。
而且它撞上另一條剛立的判準：**抄一份會漂的真相，等於預約它過期的那天。**

⇒ 形狀：**knowie 留在 repo（事實來源），KnowField 讀它、檢索它、提議它——但不寫它。**
寫入仍然走 repo：AI 在 repo 裡寫、**人 commit**。
因為 **commit 就是那道人閘門，git 就是那個轉移記錄**——不需要再發明一套。

## 二、多專案解開了聯邦線最久的那個 blocker

聯邦那條線（C-MVP → room → AC）一直卡在同一句話：**「等第二個使用者」**。
而 C-MVP 的形狀是：

> 發布一條根因（帶出處）＋ **別人**把它當「候選」＋ 過自己的試金石＋自己冊封才收下。

把「別人」換成**你的另一個專案**——一模一樣。

⇒ **多專案讓你自己就是第二個 base。** 這跟 persona 讓你成為第二個 principal 是同一招，
用第二次。而它**完全不需要使用者機制**。

## 三、clone 之後能做到哪裡

先釐清一個前提：`skills/` 底下**只有 `SKILL.md`——它是給 AI 讀的 prompt，不是可執行程式**。
所以「clone 下來就能用 knowie 的 skills」隱含著：**要有一個能讀寫檔案、能 grep、能 commit 的 agent**。
⇒ 「整合 knowie」和「線上 Agent」不是兩題，是同一題。

| | KnowField 要有 | 能做 | 界線 |
|---|---|---|---|
| **A 唯讀索引** | git clone ＋ 讀檔 | 檢索 · 跨 base 候選 · 呈現 | 不能執行 skills |
| **B 讀 ＋ 提議 patch** | ＋ agent runtime | 跑 judge，產出 **diff** | **不能 commit** |
| **C 全自動** | ＋ 寫入 ＋ push | 自己 commit | ✗ 拆掉人閘門，違反原則 5 |

**B 是正確的終點**，而且它有一個很漂亮的性質：
**diff 就是提議，PR／`git apply` 就是那道人閘門**——git 本來就是。

### 界線不用重畫，knowie 自己畫好了

> **AI does the reversible, mechanical**: move, index, prune, detect, draft.
> **Human does the irreversible, semantic**: commit, amend root principles, anoint parent-concepts.

| 做得好（機械、可驗證） | 做得普通 | 不該做 |
|---|---|---|
| judge 的掃描——死連結／孤兒／缺來源／README／done:open（那份裡有 **12 處**是純 grep/ls） | 「判準 vs 做法」分類 · draft 該往哪推 | 改原則 · 冊封 · 決定哪份 draft 衰減 · commit |

## 四、哪些需要 RAG——有一條反直覺的

> ⚠️ **要「全部」的時候不要用 RAG。**

死連結、孤兒、缺來源要的是**全稱**（每一個），而 RAG 給的是 **top-k**——它是**取樣，不是列舉**。
用 RAG 做這些，你會得到一份**看起來很完整的漏報**。

**真的需要的**：跨 base 候選（5 個專案、500 條教訓 → 跟現在相關的）· 重複偵測（converge 判準需要它）。

ⓘ 但有個門檻：這個 base 全部 markdown 共 **12,253 行**——**整包塞得進 context**。
⇒ **單一 base 內，RAG 是過度工程；跨 base 才需要。**

## 五、通用 vs 特殊領域：用「在幾個 base 獨立撞到」測

knowie 的「判準 vs 做法」是**事後分類**（「拆掉綁定層就可測」會跟技術棧一起過期；
「一個會改變它所測東西的量測器不是在測它」會旅行）。而**如何形成**要另一個訊號：

- 只在 A 出現 → 可能特殊，也可能只是還沒在別處撞到
- **在 B 被獨立撞到** → 那是通用性的**強證據**

ⓘ 這正是根公理一「**一個概念，多個投影**」的**跨專案版**：
在多個專案裡都投影得出來的，才是真的母概念。

**升格到哪？** → **你的個人場**。專案 base 是「這個專案的 why」，
個人場是「**跨專案的你**」——而通用判準正是你的判斷，不是某個專案的事實。
⇒ 方向因此定死：**專案 → 個人場只走「通用化」這一條，而且要證據**，不是隨便倒。

ⓘ 反過來的**特殊性**也有機械訊號：教訓裡出現只在那個 repo 存在的識別字（`DomainsPage.tsx`）
⇒ 大概是特殊的。但那是**提議用的訊號，不是判決**——2026-08-27 才用一個代理指標擋掉「深度學習」
被使用者打回票，同一個坑不踩第二次。

## 六、線上 Agent：先不要當 runtime

技術上做得到（Codex SDK／Claude Agent SDK）。但四個硬問題：
**祕密**（clone 私有 repo 要 token ⇒ 新的、不可逆的攻擊面）·
**沙箱**（跑 grep/git ＝ 任意執行）· **成本**（背景跑 ⇒ 你看不到它在燒）·
以及最要緊的：**它會讓 KnowField 從「你的知識工具」變成一個 CI**。

⇒ 有一條便宜得多的：**KnowField 不當 runtime，當「發起者與收件匣」。**

```
KnowField 知道：有哪些 base、哪個該跑 judge、哪份 draft 快過期
      ↓ 產出一行指令
你在 Claude Code / Codex CLI 裡貼一行（agent 就在 repo 裡跑）
      ↓ diff / commit 回到 repo
KnowField 下次讀就看得到
```

零 runtime、零 token、零沙箱，而且 agent 待在它本來就該在的地方——**repo 裡，看得到程式碼**。
⇒ 而這也還是「AI 提議、人按」：KnowField 提議任務，你按下去跑。
若之後真要 hosted，正確形狀是**開 PR，不直接 push**。

## 七、UI：「互動／開發」

使用者給了三個對照（Gemini 即時通訊/Spark · Claude Code 💬/`</>` · 對話/工作）。
那個軸實際上分的是：**線性的、當下的來回** vs **有狀態、有產物、會回頭看的工作**。

⇒ 而「開發」那一側確實是後者（路線圖＝待辦 · draft · judge · diff）。
**所以「開發」比「專案」好**——它講的是**你在幹嘛**，不是東西放哪。

### ⚠️ 但這是「借形狀不借代價」第四次

前三次：資料夾（刪除的代價）· 雲端硬碟（「共用」的語意）· 論壇（排序）。
每次都是**那個比喻裡最順手的機制，正好是這裡最不能要的**。

雙模式的代價有兩個，而那三個工具**都沒解好**：

| 代價 | 判準 |
|---|---|
| **你會迷路**（「我寫在哪一邊？」） | **⌘K 必須跨模式**，結果要標來源。Gemini 的 Spark 跟即時通訊搜不到彼此，那就是這個病 |
| **撞見會消失**（分模式＝分場） | **⛓「通往哪裡」要能指到另一邊**：「這一區有 3 條連到你的個人場」，點下去跨過去 |

### 版面：分層，不要並列

那三個工具的切換都在**最頂端、logo 旁**——而那正是 persona 切換器現在的位置。
兩個切換器搶同一格會爆。⇒ 分層：

```
🧠 KnowField          [ 互動 | 開發 ]     ← 模式
─────────────────────────────────────
互動：  👤 工作 ▾  · 📂 知識庫 ▾ · ＋新互動 · 📚💬💡🧩
開發：  📁 KnowField ▾ · 📐路線圖 📖原則 🧪經驗 ✍️draft
        ⚡ 待辦：2 份 draft 九天沒動 · judge 上次跑於 8/27
```

**persona 不進開發模式**——專案 base 天然就是隔離的（它是另一個 repo），再疊一層可見性只是負擔。

### 邊界：寫在哪就算哪邊

「這條該算哪邊？」會一直發生。⇒ **寫在哪就算哪邊**；跨界只有一條路——
在多個 base 獨立撞到 → 提議升格到個人場（第五節）。
⇒ 這樣模式**不需要「移動」功能**，也就沒有「我到底搬過去了沒」那種狀態
——而那正是雙模式介面最常見的第三個坑。

## 八、冷啟動：`/knowie-seed`

冷啟動真正空的是 **experience**（principles 大半在 constitution 裡、vision 是專案特有的）。
而教訓是**撞出來的**，所以新專案一條都沒有。

```
1. 問 KnowField：給我適合這個專案冷啟動的通用判準
2. 篩：這條會改變某條判準怎麼寫嗎？有沒有提到只在別的 repo 存在的東西？
3. 逐條提議 → 人冊封 → 寫進新 base 的 experience
4. 每條**帶出處**（來自哪個 base、哪一次撞到）
```

KnowField 剛好就是那個「雲端」——它 clone 了所有 base，所以由它出 API，skill 去打它。
⇒ **這就是 C-MVP 的完整實現**，只是「別人的場」換成「你的其他專案」。

### ⚠️ 但冷啟動有一個它特有的陷阱

C-MVP 的原句是「過**你的**試金石 ＋ **你的**冊封才收下」。
**而一個空的 base 沒有試金石**——你還不知道這個專案會撞到什麼。

⇒ 大量收下通用判準，等於在**還不知道它們有沒有用的時候就先信了**。
那會長出一個「看起來很有經驗，但**沒有一條是自己撞出來的**」知識庫
——而 knowie 的全部價值就在於那些教訓是你撞出來的。

⇒ 判準：**借來的要標成借來的。**
`origin: borrowed from <base>`——**在這個專案真的撞到之前，它不算這個專案的經驗**；
撞到了才升格（補上這個 base 的來源）。

ⓘ 這是同一個機制**第三次**出現：spec 062 的 `self`／`self:judgment` · 信任鏈的三種終點 ·
現在是 `borrowed`。**來源不同的東西，認識論地位不同**——那條線已經是這個庫的骨架。

而且要**少**：knowie 說「保持少數高質量吸引子」⇒ 建議上限 10–15 條，不是把 116 條倒過去。

### 排序：冷啟動不能用相似度

相似度需要語料，而**冷啟動沒有語料**（那正是它冷的原因）。
⇒ 改用第五節那個訊號：**這條在幾個 base 裡被獨立撞到過。**

⚠️ 它**不是**馬太陷阱，但邊界很細：

| | |
|---|---|
| ✅ 算數 | 在 B 專案**獨立撞到**同一件事 ⇒ 通用性的證據 |
| ❌ 不算 | 被 C 專案**借過去** ⇒ 那只是流行度 |

**只算「撞到」，不算「借走」。** 否則推薦餵回計數、計數又餵回推薦
——那就是馬太，而且它會把一條只是好聽的判準推成所有新專案的共識。
