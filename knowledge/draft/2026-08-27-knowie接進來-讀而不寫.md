# knowie 接進來：讀而不寫——而多專案讓**你自己**成為第二個 base

> 狀態：**draft／未定案設計（thinking-line）**。日期：2026-08-27。
> 怎麼冒出來的：使用者「我想把 knowie 整合進來，變成專案式的知識庫，然後可以有好幾個專案，
> 這些累積的經驗可以快速地餵養新的專案知識庫⋯這樣我們就有『互動/專案』的選擇可以切換了」，
> 後來收斂成 **「互動／開發」**。

## 一、**不要**把 knowie 搬進來——要「接」

knowie 最重要的性質是**它住在 repo 裡，跟程式碼同一個 commit**。
而這個論證你自己寫過，就在 `skills/ship-knowfield/SKILL.md` 的開頭：

> 這些都寫在我的私人記憶裡過——但那不是專案的小腦，**Codex／Gemini 看不到**，
> 換一台機器也沒有。所以它該在這裡。

把 knowie 搬進 KnowField 的資料庫，就是**把那個論證反著跑一遍**：
轉移記錄跟 diff 分家 · repo 裡的其他 AI 看不到 · 換台機器就沒有。
而且它撞上另一條剛立的判準：**抄一份會漂的真相，等於預約它過期的那天。**

⇒ 形狀：**knowie 留在 repo（事實來源），KnowField 讀它、檢索它、提議它——但不寫它。**
寫入仍然走 repo：AI 在 repo 裡寫、**人 commit**。
因為 **commit 就是那道人閘門，git 就是那個轉移記錄**——不需要再發明一套。

## 二、多專案解開了聯邦線最久的那個 blocker

聯邦那條線（C-MVP → room → AC）一直卡在同一句話：**「等第二個使用者」**。
而 C-MVP 的形狀是：

> 發布一條根因（帶出處）＋ **別人**把它當「候選」＋ 過自己的試金石＋自己冊封才收下。

把「別人」換成**你的另一個專案**——一模一樣。

⇒ **多專案讓你自己就是第二個 base。** 這跟 persona 讓你成為第二個 principal 是同一招，
用第二次。而它**完全不需要使用者機制**。

## 三、clone 之後能做到哪裡

先釐清一個前提：`skills/` 底下**只有 `SKILL.md`——它是給 AI 讀的 prompt，不是可執行程式**。
所以「clone 下來就能用 knowie 的 skills」隱含著：**要有一個能讀寫檔案、能 grep、能 commit 的 agent**。
⇒ 「整合 knowie」和「線上 Agent」不是兩題，是同一題。

| | KnowField 要有 | 能做 | 界線 |
|---|---|---|---|
| **A 唯讀索引** | git clone ＋ 讀檔 | 檢索 · 跨 base 候選 · 呈現 | 不能執行 skills |
| **B 讀 ＋ 提議 patch** | ＋ agent runtime | 跑 judge，產出 **diff** | **不能 commit** |
| **C 全自動** | ＋ 寫入 ＋ push | 自己 commit | ✗ 拆掉人閘門，違反原則 5 |

**B 是正確的終點**，而且它有一個很漂亮的性質：
**diff 就是提議，PR／`git apply` 就是那道人閘門**——git 本來就是。

### 界線不用重畫，knowie 自己畫好了

> **AI does the reversible, mechanical**: move, index, prune, detect, draft.
> **Human does the irreversible, semantic**: commit, amend root principles, anoint parent-concepts.

| 做得好（機械、可驗證） | 做得普通 | 不該做 |
|---|---|---|
| judge 的掃描——死連結／孤兒／缺來源／README／done:open（那份裡有 **12 處**是純 grep/ls） | 「判準 vs 做法」分類 · draft 該往哪推 | 改原則 · 冊封 · 決定哪份 draft 衰減 · commit |

## 四、哪些需要 RAG——有一條反直覺的

> ⚠️ **要「全部」的時候不要用 RAG。**

死連結、孤兒、缺來源要的是**全稱**（每一個），而 RAG 給的是 **top-k**——它是**取樣，不是列舉**。
用 RAG 做這些，你會得到一份**看起來很完整的漏報**。

**真的需要的**：跨 base 候選（5 個專案、500 條教訓 → 跟現在相關的）· 重複偵測（converge 判準需要它）。

ⓘ 但有個門檻：這個 base 全部 markdown 共 **12,253 行**——**整包塞得進 context**。
⇒ **單一 base 內，RAG 是過度工程；跨 base 才需要。**

## 五、通用 vs 特殊領域：用「在幾個 base 獨立撞到」測

knowie 的「判準 vs 做法」是**事後分類**（「拆掉綁定層就可測」會跟技術棧一起過期；
「一個會改變它所測東西的量測器不是在測它」會旅行）。而**如何形成**要另一個訊號：

- 只在 A 出現 → 可能特殊，也可能只是還沒在別處撞到
- **在 B 被獨立撞到** → 那是通用性的**強證據**

ⓘ 這正是根公理一「**一個概念，多個投影**」的**跨專案版**：
在多個專案裡都投影得出來的，才是真的母概念。

**升格到哪？** → **你的個人場**（KnowField 的互動庫）。專案 base 是「這個專案的 why」，
個人場是「**跨專案的你**」——而通用判準正是你的判斷，不是某個專案的事實。
⇒ 方向因此定死：**專案 → 個人場只走「通用化」這一條，而且要證據**，不是隨便倒。

ⓘ **為什麼不是 `knowie` 那個 base**（它有 8 個 concept，看起來很像那個家）：
**`knowie` 是發布出去的**——它跟著 npm 套件走。把 13 個專案累積的判準放進去
＝把護城河送人。使用者裁決（2026-08-27）：「我不要 meta-base，我是想把這些當成是**個人的護城河**。」

ⓘ 反過來的**特殊性**也有機械訊號：教訓裡出現只在那個 repo 存在的識別字（`DomainsPage.tsx`）
⇒ 大概是特殊的。但那是**提議用的訊號，不是判決**——2026-08-27 才用一個代理指標擋掉「深度學習」
被使用者打回票，同一個坑不踩第二次。

## 六、線上 Agent：先不要當 runtime

技術上做得到（Codex SDK／Claude Agent SDK）。但四個硬問題：
**祕密**（clone 私有 repo 要 token ⇒ 新的、不可逆的攻擊面）·
**沙箱**（跑 grep/git ＝ 任意執行）· **成本**（背景跑 ⇒ 你看不到它在燒）·
以及最要緊的：**它會讓 KnowField 從「你的知識工具」變成一個 CI**。

⇒ 有一條便宜得多的：**KnowField 不當 runtime，當「發起者與收件匣」。**

```
KnowField 知道：有哪些 base、哪個該跑 judge、哪份 draft 快過期
      ↓ 產出一行指令
你在 Claude Code / Codex CLI 裡貼一行（agent 就在 repo 裡跑）
      ↓ diff / commit 回到 repo
KnowField 下次讀就看得到
```

零 runtime、零 token、零沙箱，而且 agent 待在它本來就該在的地方——**repo 裡，看得到程式碼**。
⇒ 而這也還是「AI 提議、人按」：KnowField 提議任務，你按下去跑。
若之後真要 hosted，正確形狀是**開 PR，不直接 push**。

## 七、UI：「互動／開發」

使用者給了三個對照（Gemini 即時通訊/Spark · Claude Code 💬/`</>` · 對話/工作）。
那個軸實際上分的是：**線性的、當下的來回** vs **有狀態、有產物、會回頭看的工作**。

⇒ 而「開發」那一側確實是後者（路線圖＝待辦 · draft · judge · diff）。
**所以「開發」比「專案」好**——它講的是**你在幹嘛**，不是東西放哪。

### 但這是「借形狀不借代價」第四次

前三次：資料夾（刪除的代價）· 雲端硬碟（「共用」的語意）· 論壇（排序）。
每次都是**那個比喻裡最順手的機制，正好是這裡最不能要的**。

雙模式的代價有兩個，而那三個工具**都沒解好**：

| 代價 | 判準 |
|---|---|
| **你會迷路**（「我寫在哪一邊？」） | **⌘K 必須跨模式**，結果要標來源。Gemini 的 Spark 跟即時通訊搜不到彼此，那就是這個病 |
| **撞見會消失**（分模式＝分場） | **⛓「通往哪裡」要能指到另一邊**：「這一區有 3 條連到你的個人場」，點下去跨過去 |

### 版面：分層，不要並列

那三個工具的切換都在**最頂端、logo 旁**——而那正是 persona 切換器現在的位置。
兩個切換器搶同一格會爆。⇒ 分層：

```
🧠 KnowField          [ 互動 | 開發 ]     ← 模式
─────────────────────────────────────
互動：  👤 工作 ▾  · 📂 知識庫 ▾ · ＋新互動 · 📚💬💡🧩
開發：  📁 KnowField ▾ · 📐路線圖 📖原則 🧪經驗 ✍️draft
        ⚡ 待辦：2 份 draft 九天沒動 · judge 上次跑於 8/27
```

**persona 不進開發模式**——專案 base 天然就是隔離的（它是另一個 repo），再疊一層可見性只是負擔。

### 邊界：寫在哪就算哪邊

「這條該算哪邊？」會一直發生。⇒ **寫在哪就算哪邊**；跨界只有一條路——
在多個 base 獨立撞到 → 提議升格到個人場（第五節）。
⇒ 這樣模式**不需要「移動」功能**，也就沒有「我到底搬過去了沒」那種狀態
——而那正是雙模式介面最常見的第三個坑。

## 八、冷啟動：`/knowie-seed`

冷啟動真正空的是 **experience**（principles 大半在 constitution 裡、vision 是專案特有的）。
而教訓是**撞出來的**，所以新專案一條都沒有。

```
1. 問 KnowField：給我適合這個專案冷啟動的通用判準
2. 篩：這條會改變某條判準怎麼寫嗎？有沒有提到只在別的 repo 存在的東西？
3. 逐條提議 → 人冊封 → 寫進新 base 的 experience
4. 每條**帶出處**（來自哪個 base、哪一次撞到）
```

KnowField 剛好就是那個「雲端」——它 clone 了所有 base，所以由它出 API，skill 去打它。
⇒ **這就是 C-MVP 的完整實現**，只是「別人的場」換成「你的其他專案」。

### ⚠️ 但冷啟動有一個它特有的陷阱

C-MVP 的原句是「過**你的**試金石 ＋ **你的**冊封才收下」。
**而一個空的 base 沒有試金石**——你還不知道這個專案會撞到什麼。

⇒ 大量收下通用判準，等於在**還不知道它們有沒有用的時候就先信了**。
那會長出一個「看起來很有經驗，但**沒有一條是自己撞出來的**」知識庫
——而 knowie 的全部價值就在於那些教訓是你撞出來的。

⇒ 判準：**借來的要標成借來的。**
`origin: borrowed from <base>`——**在這個專案真的撞到之前，它不算這個專案的經驗**；
撞到了才升格（補上這個 base 的來源）。

ⓘ 這是同一個機制**第三次**出現：spec 062 的 `self`／`self:judgment` · 信任鏈的三種終點 ·
現在是 `borrowed`。**來源不同的東西，認識論地位不同**——那條線已經是這個庫的骨架。

而且要**少**：knowie 說「保持少數高質量吸引子」⇒ 建議上限 10–15 條，不是把 116 條倒過去。

### 排序：冷啟動不能用相似度

相似度需要語料，而**冷啟動沒有語料**（那正是它冷的原因）。
⇒ 改用第五節那個訊號：**這條在幾個 base 裡被獨立撞到過。**

它**不是**馬太陷阱，但邊界很細：

| | |
|---|---|
| ✅ 算數 | 在 B 專案**獨立撞到**同一件事 ⇒ 通用性的證據 |
| ❌ 不算 | 被 C 專案**借過去** ⇒ 那只是流行度 |

**只算「撞到」，不算「借走」。** 否則推薦餵回計數、計數又餵回推薦
——那就是馬太，而且它會把一條只是好聽的判準推成所有新專案的共識。

## 九、開發模式要不要套 Codex SDK？——不用，但要一張符號索引

先拆一個容易混的東西：**誰**需要理解 codebase。

| KnowField 在開發模式做的事 | 需要理解 codebase 嗎 |
|---|---|
| 檢索 knowie markdown · 跨 base 候選 · 冷啟動 · 顯示路線圖 | ❌ |
| **判斷「這條知識還成立嗎」** | ✅ **只有這個** |

而那正是 judge 的 §2：「**Against ground truth (code)**: are the principles actually followed?
milestones actually done? **the lessons' pitfalls still real?**」
⇒ **碰程式碼是為了驗證知識，不是為了寫程式。** 而寫程式那半在 repo 裡的 agent 手上，
它本來就有整個 codebase。

### SDK 給的不是「理解」，是 agent 骨架

Codex SDK／Claude Agent SDK 給的是 agent 迴圈、工具呼叫、沙箱、session。
**它們沒有給你一個神奇的 codebase 索引**——理解仍然來自模型 ＋ 工具 ＋ context。
⇒ 期待「套上 SDK 就會理解 codebase」是錯的；你得到的是**一個可以跑 agent 的地方**，
而那正是第六節建議先不要的東西。

### 真正需要的小得多，而且它是 knowie 的**第一個真 oracle**

knowie 的立論是「**why 記憶沒有 oracle**」——所以它會爛而沒人發現。
但有一類 rot 是**機械可判的**：

> 教訓寫著「`DomainsPage.tsx` 的 `beginDrag` 會…」——**那個檔案／那個函式還在嗎？**

**符號索引**（檔案 → 符號 → 位置，tree-sitter／ctags 級別，不需要 LLM）就回答得了，而且不會幻覺。
⇒ judge 現在抓得到死連結（markdown 之間），但抓不到**知識指向已經不存在的程式碼**
——同一種病，只是跨到了另一邊。

**這不是推測——實測過了（2026-08-27，十行腳本）：**

| | |
|---|---|
| 帶具體檔名／函式名的教訓 | **77 / 116** |
| 被點名的檔案 | **41 個** |
| **已經不存在的** | **1 個**：`digest/builder.py`（**兩條**教訓指著它） |

而它死得很典型：那個檔在 `5cb07b9`「砍鷹架 Stage 2：移除新聞分診死碼」被刪掉，
跟著退役的分診子系統一起走了；`_canonical` 現在整個 repo 都找不到。

⚠️ **而那兩條教訓本身沒死**（「聚合混來源資料，比較前先正規化」是判準，它會旅行）
——**死的是錨**。⇒ 所以正確的處置不是刪教訓，是**重新指**（指到 history/048 或那次刪除的 commit）。
根公理二要的是「why ＋ 最小的 how」——how 那條腿斷了，教訓還在但**重建不回當時的認知**。

### 對 codebase 來說，grep 常常勝過 embedding

同第四節那條的另一面：**程式碼的相關性是結構性的（誰呼叫誰），不是語意相似的（誰看起來像誰）。**
「找出所有呼叫 `set_knowledge_domain` 的地方」要的是**全稱** ⇒ 符號跳轉 ＋ grep 勝過向量檢索，而且便宜得多。

### ⇒ 建議：不套 SDK，做兩件小的

| | 是什麼 | 買到 |
|---|---|---|
| **① 符號索引** | clone 之後掃一次 | **知識過期的機械偵測**——knowie 的第一個真 oracle |
| **② 技術棧指紋** | 讀 `package.json`／`pyproject.toml`／`go.mod` | 跨 base 遷移時知道「這條來自 React 專案，而我這個是 Go」 |

真正需要理解程式碼的工作（bootstrap 一個沒有 knowie 的舊專案、judge 的判斷部分）
交給 repo 裡的 agent。KnowField 只**發任務、收 diff**。
ⓘ 而且安全性差一個數量級：**唯讀 clone ＋ 建索引**沒有任意執行、沒有寫入、沒有 push 權限。
⇒ 再次指向：**A（唯讀索引）先做。**

### 一個要盯著的風險

符號索引很容易被當成「KnowField 也懂程式碼了」，然後就想讓它做更多。
**但它只回答一個問題——「這個東西還在嗎」。** 它不知道那個函式現在**做什麼**，也不該假裝知道。
⇒ 判準：**這個 oracle 的定義域是什麼？** 超出去的判斷（「這條教訓還對嗎」）**仍然是語意的**，
要人或要 repo 裡的 agent，不是這張表。

## 十、實測、分層共享，以及**複利到底在哪一段**

### 實測（2026-08-27，13 個 base）

| | |
|---|---|
| base | **13**（不是 10） |
| 教訓 | **1,337 條** |
| concept | **53 個**（散在 7 個 base；另外 6 個 base 是 **0**） |
| 分布 | semorphe 427 · VizGPT 421 · cella 135 · KnowField 116 · wewayfinders 73 · code-battle 70 · 其餘 7 個 ≤27 |

⇒ 這就是為什麼看不到複利：**大的兩個各自累積了 400+，小的還在冷啟動，中間沒有路。**

**字面比對（bigram Jaccard ≥ 0.24）只找到 6 對／12 條（0.9%）**——
而其中 **3 對是複製**（cella ↔ GeneralAffairs 的 G1/G2/G3 幾乎逐字）。
真正獨立撞到的只有 3 對，但它們長這樣：

| | |
|---|---|
| `[wewayfinders]` 判準寫在同一個檔案裡，也擋不住三十行外的自己 | `[semorphe]` 一條寫在同一個檔案裡的規則，擋不住三十行以外的自己 |
| `[VizGPT]` 一個判準的**精度**決定它看得見什麼 | `[wewayfinders]` 比對的「**粒度**」決定它看得見什麼 |

⚠️ **通用判準的旅行方式，正是「換成當地的詞重新講一次」**——`精度` vs `粒度`、
`調參數` vs `固化`，共用字幾乎是零。⇒ **0.9% 不是複利率，是字面比對的天花板**，
而我又一次拿代理指標去測一個它測不到的東西（這個月第三次）。

⇒ **這是整份 draft 裡第一個「hub 真的加了東西」的證據**：跨 base 匹配**必須是語意的**，
而 1,337 條 × embedding 正是 KnowField 已經有的管線；一個在 repo 裡的 skill
把 O(n²) 塞進一個 prompt 不可靠。

### concept 層的重疊更明顯，而且證據就在眼前

```
[code-battle]  沒有東西會叫的失敗就是不會被修的失敗
[KnowField]    沉默的失敗不會自己現形
```

**同一個母概念，共用字幾乎是零。** 而 `code-battle` 那 11 個 concept 幾乎全是通用判準
（「一條核准得了相反決策的原則在那裡不算原則」「一旦計分量測就會被玩」
「送進模型的自然語言是原始碼不是設定」），**跟「程式對戰」一點關係都沒有**。

⇒ **concepts 比 experience 更該共享**，而理由是結構性的：
knowie 判斷 concept 的測試是「**它投影到三個視角嗎**」——**一個真的母概念本來就跨脈絡**；
而 experience 是「我撞到什麼」，它天生綁著現場。
ⓘ 跨 base 還給了母概念**第一個外部證據**：同一個母概念在 N 個 base 各有投影
⇒ 那是 **pruning-power test 的跨專案版**。

### 分層：哪些共享、怎麼共享

| 層 | 共享嗎 | 形式 |
|---|---|---|
| `skills/` | ✅ **已經在做** | knowie 的走工具散佈、專案的留 base ⇒ **現成的通用／特殊分界** |
| `concepts/` | ✅ **最該做** | 母概念本來就跨脈絡 |
| `principles` | **分層** | 工作方式的（constitution）通用／產品的特殊——**現在的兩檔分法已經在做** |
| `experience` | 篩過 | 只有判準型會旅行 |
| `episodes` `history` | ❌ 不複製 | 但 borrowed **要指得回去** |
| `draft` `vision` | ❌ | — |

ⓘ `skills/` 那一格示範了一件微妙的事：`ship-knowfield` 是**特殊的**（k3s、helm、這個 repo），
但它裡面那條「出貨要核對 pod 的實際 digest」是**通用的**。
⇒ **skill 是做法，裡面的判準才是判準。**

### 「不複製但要指得回去」＝ 信任鏈的跨 repo 版

seed 過去的判準，它的**現場**（episode）與**因果**（history）留在原 base
⇒ 在新 base 就是「**沒有現場的結論**」，而根公理二要的是「why ＋ 最小的 how」。

⇒ borrowed 要帶一條**跨 repo 的指標**，而那需要一個**穩定位址格式**（git remote ＋ path ＋ commit）。
ⓘ 這其實就是**信任鏈換一個尺度**——個人場裡已經做過一次（來源 → 互動 → 理解）。

### 結構：個人場是**中樞**，不是又一個 base

```
專案 base ×13  ──升格（要證據：多處獨立撞到）──▶  個人場（護城河）
      ▲                                              │
      └──────── seed（標 borrowed）─────────────────┘
```

⇒ KnowField 的角色因此清楚了：**它不是「又一個知識庫」，它是那個中樞**——專案 base 是葉子，個人場是根。
而「互動／開發」那個切換也因此更成立：**互動 ＝ 你的護城河**，**開發 ＝ 當下那個專案**。

技術上不用新型別：升格上來的就是**理解**，`origin` 多一種 `from:<base>`（那一欄 spec 062 就在了）。

### 而真正的複利在**回頭**那一段

前面幾節一直把複利講成「把判準傳過去」。**那只是利息。**

> **複利在反證回饋**：一條 borrowed 的判準在新專案**被反證**了 ⇒ 不是刪掉它，
> 是**回饋到個人場**——「這條有邊界，在 X 情境不成立」。

⇒ 於是每 seed 一次，那條判準就更準一點。**13 個專案用過的判準，跟寫下來就沒再碰過的判準，是兩種東西。**
⇒ 而這要求 borrowed 是**可追蹤的**（哪些專案借過哪條）——那是 `borrowed from` 的第二個用途。

### 護城河的自我檢查

北極星第一條是「用信任過濾，不用廣度」——護城河**就是**那個過濾器，所以「只看到你已經相信的」不是 bug。
但要有出口，而你已經有兩個：**膜**（gradient oracle 對自己 adversarial，防 folie à deux）＋
**借來的要標成借來的**。

⇒ 而第二條在這裡有一個額外的用途，是一個很便宜的健康訊號：

> **一條被借了 8 次、卻一次都沒被撞到的判準，是可疑的**——它可能只是好聽。

⇒ 那讓護城河**可以自我檢查**，而不是只會長大。

## 十一、語意實測：複利是真的，而**儀器校驗救了這個結論**

（2026-08-27，1,393 條標題／概念名 × `text-embedding-3-small`，13 個 base，只比跨 base。）

### 儀器差點給出相反的答案

第一版設門檻 0.78，結果是「跨 base 相符 8/1340，概念 0/53」——**幾乎沒有複利**。
在下結論前拿一個**我已知答案的案例**去校驗：

| 配對 | cosine |
|---|---|
| 肉眼判定同一個母概念：`沒有東西會叫的失敗` ↔ `沉默的失敗不會自己現形` | **0.581** |
| 隨機無關的跨 base | 0.27–0.42 |
| 措辭幾乎一樣的 | 0.88–1.00 |

**「同一個判準、不同的詞」離雜訊只有 ~0.17**
⇒ **0.78 報的是儀器的答案，不是這個知識庫的答案。**
（這是這個月第四次拿代理指標測它測不到的東西——但這次在下結論前驗了。）

### 用對的門檻，複利是真的

```
門檻 0.62｜跨 base 群 49 個｜涵蓋 157 條｜跨 ≥3 base 16 群｜跨 ≥4 base 3 群
```

最強的一群，**四個 base 各自撞到**：

> `[VizGPT]` 一個檢查若會靜默失敗，它比沒有檢查更糟 ·
> `[wewayfinders]` 一道「提醒，不計為失敗」的檢查，等於沒有那道檢查 ·
> `[semorphe]` 型別檢查的沉默有三種來源 ·
> `[code-battle]` 繞過一個檢查時，必須同時留下它仍然存在的位置與還原條件

### 而最該在意的是這三群——**今天才學會的，兩個 base 早就寫下來了**

| 群 | |
|---|---|
| **警告不是實作** | `[KnowField]` 一條寫對的警告只保護它被實作到的那一半（**今天 spec 064**）· `[VizGPT]` 寫在正確位置的警告防不了「沒去讀它」· `[wewayfinders]` 文件裡的警告擋不住那份文件自己過期 |
| **量測工具會說謊** | `[KnowField]` 量測工具報的 0 可能是工具在說謊 · `[VizGPT]` 驗常數時不能用被驗對象自己的工具 · `[semorphe]` 量測工具的第一版會安靜地量錯 |
| **量了一件錯的事** | `[VizGPT]` 一個判準可能不是「量錯」，而是「**量了一件錯的事**」· `[semorphe]` 一組全部由自己定義的判準，量的是自洽不是正確 |

⇒ **複利不是抽象的。** 這一整個 session 有好幾個小時在重新發現 VizGPT 與 semorphe 已經寫下來的東西
——第三群那條，正好就是我今天犯了四次的那個錯。**那就是「看不到複利」的具體成本。**

### ⇒ 判準：相似度是**篩子**，不是判準

0.62 把 1,393² 降到 **49 群／157 條**——**十分鐘看得完**。

⇒ 所以 seed **不該是「自動算出通用性分數」**，該是**一個 49 項的複審佇列**：機器提議、人判、人冊封。
（同 spec 065／069 的形狀：提議要附**可查證**的東西，最後一步是人。）

⚠️ 而且要誠實記著：**recall 是有限的**——那對 0.581 的真配對，任何合理門檻都抓不到。
⇒ 這個工具**找得到一部分，不是全部**，介面不該讓它看起來像全部
（同「要『全部』的時候不要用 RAG」——這裡剛好相反：**這件事本來就只能取樣，所以更要說清楚**）。
