# 從對話生文章：情境要進得來，沒依據的東西不能跟著進來

> 狀態：**第一刀已兌現**（vision 階段 39，出貨 2026-08-22，spec `specs/043-article-from-conversation/`，commit `dba4628`；
> 轉移見 [history/105](../history/105-從對話生文章-兩個數字改掉兩版設計.md)）。**第二刀（對話當情境）仍在 draft**。
> 日期：2026-08-21。design（新提案）＋ 一個被當場否決的設計（記在內文）。
> 怎麼冒出來的：使用者問「能不能直接從對話去生文章？前提是對話已經有相對應的核心理解了，
> 只是用這樣的脈絡下去生的文章可能更有情境」。這是 2026-08-07「知識的輸出」那條線的**反方向**——
> 那邊是核心理解 → 文章，這裡問的是對話能不能當生成的入口。
> ⚠️ 本檔全程 chat only，**沒有任何程式碼被改**；下面的事實都是讀出來的，附行號。

## 一、先接地：這條線大半已經在庫裡了

**由來是雙向的，反向查詢早就存在。** `src/knowfield/store/repository.py:673`：

```
def conversation_referrers(self, cid: int) -> list[dict]:
    """哪些核心理解以這段對話為由來（why_node.conversation_id=cid）。回 [{id, claim}]。
```

寫入端在 `:658`（`promote_conversation` → `UPDATE why_nodes SET conversation_id=%s WHERE id=%s`）
與 `:579`（`save_conversation`）。⇒ 使用者說的前提「這段對話已經有相對應的核心理解」
**是可查詢的布林值**，不必靠人記得、也不必新建資料關係。

**現行生成路徑裡，`topic` 的唯一作用是檢索查詢。** `src/knowfield/output/article.py:93`：

```
ranked = _rank_by_topic(nodes, topic, embedder)
body   = [w for w in ranked if (getattr(w, "kind", "") or "") in _BODY_KINDS][:top_k]
```

節點來自 `web/app.py:597` 的 `repo.list_why_nodes("anointed")`——**只有已冊封的進得來**，
而該路由的 docstring（`app.py:585`）明寫守衛：「只採已證實/推論、結構化 References、**不回灌場**」。

## 二、所以這是兩刀，而第一刀沒有帶進任何新東西

| | 做什麼 | 新風險 |
|---|---|---|
| **第一刀：對話當檢索** | 不用 `_rank_by_topic` 猜哪 8 條相關，直接用 `conversation_referrers(cid)` 取這段對話**確實冊封出來的**那幾條 | **無**。生成的輸入仍然只有已冊封節點，只是換了選節點的方式，而且選得更準——那是人親手冊封的，不是向量猜的 |
| **第二刀：對話當情境** | 對話內容影響文章的框架、動機、例子 | **有**。見下 |

第一刀就已經交付使用者要的一大半：文章會剛好講他剛剛在聊的那幾條，挑選與順序都對得上。
⇒ **可以只做第一刀就出貨**，第二刀單獨走一次規格。

## 三、⚠️ 我提的過濾被使用者一句話拆掉，而拆得對

**我的提案**：第二刀只餵**使用者自己的 turn**，不餵 AI 的回覆。理由是 (a) 情境幾乎都在人的話裡，
(b) 把 AI 散文餵回 AI 生成正是 model collapse 那條線，而「不回灌場」擋的就是這個。

**使用者的回覆**：「如果只有我自己講的話，常常是沒有依據的。」

**為什麼這一句就夠**：我用「**誰講的**」當切分軸，但風險住在「**有沒有依據**」那一軸，
而這兩軸正交。於是兩種過濾各漏一邊——

- 全對話 → 漏未冊封的 **AI** 主張（假權威 ＋ 回灌）
- 只有人的 turn → 漏未冊封的 **人的** 主張（沒依據）

**而未冊封的人話不是中性的。** 對話走過 distill → 候選 → 人挑，所以未冊封 ＝
「從沒被提為候選」＋「**提了、你看過、明確沒選**」。後者當情境餵回去，
等於把剛丟掉的東西從後門撿回來，而且這次前面沒有候選清單擋著。

⇒ 記為**被否決的設計**：「以說話者身分過濾對話」。理由如上。

## 四、真正的分界：問題不需要依據，主張才需要

使用者那句「沒依據」只對**主張**成立。這些東西沒有真假可言：

- 「我不懂為什麼 X 要這樣」——問題
- 「我是從影片模型的角度在想這個」——角度
- 「這裡我卡住了」——卡點

而這恰好就是「情境」的全部。**一段對話有價值不是因為它對，是因為它是你的**——
它記錄了你當時想知道什麼；而「想知道什麼」不需要依據。

## 五、候選形狀：對話 → brief → 文章

不是「過濾對話」，是把對話**收斂成一份簡報**，而簡報的 schema **結構上放不下主張**：

```
要回答的問題：（必須是問句）
角度：
讀者程度：
用哪幾條核心理解：（＝ conversation_referrers）
```

現行 API 本來就吃 `topic` / `length` / `level`（`app.py:591`、`:593-594`），
所以這是把 `topic` 換成更厚的一份東西，**生成端不動**。

### ⚠️ 這道閘門的性質是「可見」，不是「不可能」

schema 擋不住偽裝成問句的主張——「為什麼殘差**其實是**一種記憶機制？」就是一句夾帶。
真正擋住它的是**人會看到這份 brief 再按生成**：五個問句掃一眼就查得完，
讀整段對話抓夾帶則不划算。這是 AI 提議、人冊封的同一個分工。

⇒ 寫規格時**不得**把它寫成結構性保證。（處理方式同 spec 041 FR-003 那段誠實邊界：
關直接路徑、記間接路徑，不假裝全封。）

## 六、順帶三件

- **沒有核心理解時**：`conversation_referrers` 回空 → 入口不要只是灰掉，要說
  「這段還沒精選出核心理解，先精選」並把精選鍵擺在那。**死路變成下一步**。
- **文章要存 `conversation_id`**：這篇的情境從哪來要可稽核，且與 spec 041「帶著這篇聊」天然接得起來。
- **標題另取**：對話標題是「問題」，文章標題該是「主張」，不要沿用。

## 七、這把 08-07 的迴圈補上第三段

聊 → 冊封 → **生文章** → 帶著文章聊 → 聊……

⚠️ 但 spec 041 FR-003 記過的間接路徑會短一節：對話 A 塑形的文章被帶進對話 B、B 再蒸餾出候選。
041 強制「帶著這篇聊」開新對話（FR-001c），所以 A≠B；但這個環變緊了，
**升上路線圖時要重新標一次這條邊界**，不能沿用 041 的措辭當已解。
