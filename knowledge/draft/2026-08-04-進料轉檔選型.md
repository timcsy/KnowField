# 進料轉檔與 RAG 選型（進料層任務 2 的設計輸入）

> 狀態：draft／設計輸入。日期：2026-08-04。來源＝三段研究：①舊專案 GeneralAffairs 的 RAG/轉檔經驗萃取（過膜）、
> ②2026-08 web SOTA 研究、③**Mistral Document AI 繁中實測（親跑，紮實）**。掛給 `[[進料層重定位]]` 設計任務 2。

## A. 轉檔器選型：Mistral Document AI（已實測，最紮實的一段）

用 `azure/mistral-document-ai-2512`，**掛在現有 LEARNNEWS gateway、同一把 key、`POST /v1/ocr`、Bearer**——零新後端設定（合憲章 IV 零相依、[[有吸引子的場]] 的 gateway 路線）。實測兩份：
- **英文（Attention Is All You Need）**：數學保成 **LaTeX**（`softmax(QK^T/√d_k)V`）、表格成 markdown 表、雙欄正確線性化、章節齊全。瑕疵：標題階層不穩、複雜表雙層表頭被拆兩行、`\operatorname` 字母被空開。
- **繁中（108保險全攻略，49 頁美編電子書）**：**輸出繁體、忠實**（OCR 讀既有字形→保繁，**不需 OpenCC**；OpenCC 是給會生簡體的**語音轉錄**用的，那條之後測 `gpt-transcribe` 再驗）。正文頁乾淨、章節/清單/長段還原好；**美編頁**有零星字元誤認（「填寫」→「墳窩」、「不踩雷」→「不踩當」）。

**結論**：一次呼叫 → 乾淨（繁體）markdown 含結構，品質可用。這是任務 2 轉檔主路徑。

## B. 實測挖出的坑（＝硬設計約束）

1. **單份 30 頁上限**（Azure 這個部署）：49 頁被擋（`document_parser_too_many_pages`）。長文件**必須先切成 ≤30 頁段、逐段 OCR、再併 markdown**。→ 正好對上 GeneralAffairs spec 006 教訓「Mistral >30 頁自動切檔」。
2. **笨切法會爆脹**：poppler `pdfseparate+pdfunite` 切前 10 頁 → 45MB（每頁共用的大背景圖被複製）。切檔要用**會共用資源的工具**（pypdf/pikepdf/qpdf/mutool），不能笨切。
3. **兩條輸入路**：(a) PDF 走 `document_url`（可 base64 data URI），要正確 ≤30 頁切檔；(b) **每頁 render 成 PNG → `image_url`**（避開切檔爆脹、可控 DPI、逐頁計費）。今天走 (b) 成功。原生數位 PDF 走 (a) 乾淨；美編/掃描重的走 (b) 高 DPI 較準。
4. **DPI 是準確度旋鈕**：150dpi 美編頁有零星錯字，200–300dpi 應更準（代價：圖更大）。
5. **成本看不到**：gateway 回 `credits: None`，這端看不到每頁單價；每頁＝一次計費 OCR 呼叫，實務要留意量。

## C. 切塊（最高優先，且模型不幫你做）

反覆出現的結論：**「查不到」的 root cause 通常在切塊，不在 embedding/query**（GeneralAffairs feature 016：0.014 分那個坑；feature 002：1869 行切 7 大塊→向量化 28GB OOM）。所以任務 2 的真工程在這裡：
- **中文按字元數切**（他們用 400＋40 overlap），不能用空白分詞（中文無空格→OOM/爛粒度）。
- **靠章節編號切**（Mistral 的標題階層不穩，但 `3.1`/`3.2.1` 這種編號可靠）；**公式塊、markdown 表格不能從中間切開**。
- **粒度配 top_k 一起調**（太細會在排序被擠掉）。
- 幾何解釋見 [[有吸引子的場]] 高維段：一塊混多主題→向量是平均→落在模糊質心，所以要「一塊一個意思」讓向量指向乾淨方向。

## D. 檢索決定：維持向量，不建 grep-first

- LearnNews（029）**本來就是向量 cosine**。GeneralAffairs 後期一度退到「grep 優先＋向量 fallback」，但那是**成本優化**（個人 KB 少 query），不是品質裁決——純向量是他們數字裡最好的單一法。
- 使用者已**擁抱向量**，理由紮實：**高維近正交＝容量**（能容納很多語意特徵），grep 是離散符號匹配、接不到「同義/換句話」。對知識/理解工具，向量是對的主力。→ **不做 grep-first**（先前 backlog 那條劃掉）。
- **rerank / hybrid（sparse+RRF）暫不上**：小語料單人＝過度擬合（收斂）。語料長大、純向量命中掉了再說（他們的路徑證明這是真的下一步、但不是現在）。

## E. decompose-to-text 主幹（SOTA 確認 + 邊界）

- 「所有模態→文字→統一 embedding」在 production 完勝原生多模態 embedding（Ragie/NotebookLM「2× 快、6× 便宜」）。**確認我們的路。**
- **邊界（老實）**：財報那類**視覺密集**文件，page-as-image late-interaction（ColPali/ColQwen，84% vs 62% recall）已超越純文字。但①要 GPU、每頁千級向量，②多數 OpenAI 相容 gateway **只給文字 embedding**，③我們內容是文章/論文、非財報密集。→ **在我們約束下 decompose-to-text 仍是務實正解**，不是絕對 SOTA。

## F. SOTA 快照（2026-08，會過期，別當永久事實）

- **文件解析塌縮成單一 VLM 一次過**（MinerU2.5、olmOCR2、docling Granite-258M…），但多要自架 GPU；受管版＝**Azure Foundry 上 Mistral Document AI**（我們用的）。
- **原生多模態 ASR 勝 Whisper**（gpt-transcribe/Gemini，WER 7.6% vs 17.6%），省掉轉錄 pipeline。→ 影音進料（後段階段）改「一次呼叫」。
- **Embedding 新 SOTA＝Qwen3-Embedding**（贏 OpenAI/Google）；我們用 gateway 的 text-embedding-3-small＝「menu 問題」，不是重寫。
- **RAG-vs-長脈絡收斂到 hybrid**：檢索有界證據→長脈絡推理；「naive RAG 才死了」。**我們 `/chat` 已是這形狀。**
- **Anthropic Agent Skills（2025-10）** 有文件 skill，但多是「做 Office 檔」，不是「解析成 markdown 餵 RAG」。
- **一句**：價值從「自建 pipeline」搬去「一次強模型呼叫＋編排」＝**這是 harness 問題**，正合 LearnNews 極簡路線。

## G. 別照抄（他們處境的解，不是我們的）

自架 parser（MinerU 等）、whisper/SenseVoice/ffmpeg 影音重工、pgvector、ColPali 視覺檢索、Cohere rerank、PII/consent schema、MinIO vault——**多用戶/大語料/雲部署**的解。連他們 R10 都自我克制（「不要對所有文件套 Contextual Retrieval」）。我們照抄＝把別人的問題買回家。

## H. 進料管道（reframe：來源→管道，「貼上」優先）＋已 promote 階段 25

**關鍵 reframe（2026-08-04 討論）**：任務 2 不是「六種檔案格式」，是「**進料管道**」——常見知識來源攤開多半塌回**文字**：

| 來源 | 本質 | 最佳路 | 存取限制→貼上能繞？ |
|---|---|---|---|
| AI Chat（ChatGPT/Claude） | 文字（含 md/code） | **貼上** | 登入牆＋無通用匯出→貼上完美繞過 |
| 論文 | PDF（arxiv 開放）或文字 | **PDF（已驗）**/貼上 | 期刊付費→機構權限下載 PDF |
| YouTube | **逐字稿（文字）** 非影片 | 抓/貼逐字稿 | 多半有字幕→貼逐字稿；無字幕才 ASR（罕見） |
| 社群（X/Threads） | 短文字 | **貼上** | 反爬＋登入→只能貼上（且一句話不值得收，過膜） |
| Blog（Medium/知乎） | HTML 文章 | 開放→抓正文；付費→**貼上** | 軟付費牆＋JS→貼上繞過 |

**「全選複製貼上」是正解不是 hack**：它把**人自己的瀏覽器當存取層**——你已登入、JS 已跑、付費牆對你已開，只是把**已呈現在你眼前的合法內容**交給工具。繞過一切（登入/付費/JS/反爬）、零相依、每來源都吃、ToS 更乾淨（被盯的是自動爬蟲、不是個人手動複製）。
**但貼上不是銀彈**：①貼純文字會掉結構（表格/公式糊）→ 結構豐富但開放的（論文）走 PDF 較好、存取難但結構輕的（AI Chat/社群/付費文）走貼上；②手動摩擦；③收前仍要過膜（一句話不值得進場，「預設流走」）。

**四張嘴、一條 pipeline**：
```
[貼上框] [URL 抓取] [瀏覽器擴充] [手機分享/分享選字]   ← 四種進料「嘴」
    └────────┴──────────┴─────────────┘
                     ↓
   HTML/文字 → markdown → 切塊 → embed → 029 檢索       ← 同一條 pipeline
   （結構豐富的 PDF/論文另走 Mistral Document AI）
```

**優先序**：①貼上（通用、驗 pipeline 的第一刀）②PDF（已驗、結構好）③URL 抓正文（開放 Blog）④YouTube 逐字稿（＝文字問題、跳過 ffmpeg/whisper 重工）⑤真·音訊/影片（拿不到逐字稿才需，罕見、最後）。

**瀏覽器擴充**（討論結論）：是對的**終點**、不是**起點**。擴充跑在已登入瀏覽器、看得到完整 DOM → Readability.js 抓正文＋Turndown 轉 md → POST `localhost/ingest`；**JS 函式庫住擴充裡、不進 Python 核心**（合零相依）。但它是**第二產品面**（另一套 JS 專案/維護），而**難的是 pipeline 不是抓取**——**先做貼上框（20 行）驗完 pipeline，擴充當之後的省力層、餵同一 pipeline**。省 3 秒摩擦 vs 一整個專案＝先用貼上框量真實收料頻率再決定（過度擬合檢查）。

**手機**（誠實限制）：**Android Chrome 不支援擴充**（Firefox Android 部分支援）、**iOS 擴充要包原生 App 上架**＝高摩擦。手機正解＝**系統「分享」鍵**，而 LearnNews 是 web app → 用 **PWA Web Share Target** 幾乎免原生碼。**但手機分享多半只給網址** → server 端 fetch 是未登入、**繞不過付費牆**；要繞牆得**分享「選取的文字」**（帶得走內容）。

→ **已 promote 成 vision 階段 25**（2026-08-04），第一刀＝**貼上＋PDF**；其餘（URL/YouTube/擴充/手機分享/Office/影音）列 out-of-scope、各自後續 spike。
