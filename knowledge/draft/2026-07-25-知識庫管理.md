# 知識庫管理（前端策展／修剪）

> 怎麼冒出來的：2026-07-25 使用者問「前端能不能有管理的功能？」。點破一個缺口：工具目前
> 全是**進水**（digest/pull/ingest/訂閱），沒有**修剪**——能一直加，卻不能瀏覽/改/刪已收的。

> **促成狀態（2026-07-25）**：**已 promote → vision 階段 7**（web `/library` 管理種子：瀏覽/刪除/
> 重分類），帶驗收，見 `history/029`；spec 開發中。本 draft 續作 in-flight 設計理由（來源管理面
> 仍孵化、耦合 `來源訂閱` draft），故不退場。

> **母概念**：管理＝**人工修剪這個場**——退掉信錯的吸引子（＝手動衰減）、調權重、拔掉被污染
> 的水源。是 [有吸引子的場](../concepts/有吸引子的場.md) 裡「吸引子會死/superseded」的**人為版本**，
> 也是 optimizer 分工裡**人**那半（不只冊封，也再冊封/退場）。

## 核心洞見：管理＝原則 5 的「另一半」
「權重由人冊封」不只**加**吸引子，也含**退**吸引子、**改**權重。管理把主權（原則 5／憲章 VI）
**操作化**。**沒有修剪，KB 遲早變雜物抽屜。**

| 已能（進水） | 缺的（修剪/管理） |
|---|---|
| ingest 收種子 | 瀏覽/刪除/重新分類種子 |
| 訂閱來源（`來源訂閱` draft） | 停用/刪除來源 |
| 加興趣（✅ `/interests`） | 看系統學到的畫像（`興趣畫像` draft） |
| 問答/匯整 | 看不到「我的 KB 裡到底有什麼」 |

## 該有的管理頁（增量做）
1. **知識庫/種子管理（最大缺口、最有價值）**：列出種子（標題/來源類/日期/原文連結）、**刪除**、
   **改品質層**（解說文↔一般）。KB 一大就需要。
2. **來源管理** `/sources`：列出、啟用/停用、刪除（接 `來源訂閱` draft 的「加來源」）。
3. **興趣**：已有 `/interests`；可補「檢視學到的畫像」（歸 `興趣畫像` draft）。

## 很好做
- `/interests` 已示範 web CRUD（列出＋表單＋刪除）→ 其他管理頁**照抄**。
- Repository 資料都在（`list_corpus_entries`、`list_sources`）；新工只有**列出/刪除端點＋頁面**。
- 刪種子＝從種子容器移除 entry＋清 `entry_embeddings`（直接）。

## 守原則
- 原則 5／憲章 VI：主權＝可檢視/修改/覆寫/**刪除**自己冊封的。
- **範圍**：管理＝組織/刪除/重分類，**不重寫消化內容**（不需編輯散文本體）。

## 待解／開放問題
1. 刪種子要不要連 embedding 一起清？（要，否則孤兒向量）。刪來源要不要連它帶進的匯整條目？
   （不刪匯整——那是歷史流；只停未來抓取）。
2. 重分類（explainer↔ordinary）改 `source_class` 即可（複用 spec 006 權重）。
3. 呈現：一個「我的知識庫」總覽（種子＋來源＋興趣三區），還是各自分頁？
4. 批次操作／搜尋（KB 大了要能找/篩）——後續。

  來源管理跟上（依賴 `來源訂閱`），興趣已有。帶驗收＋雙向連結，再 speckit。
