# 來源訂閱（追蹤站台／部落格／作者）

> 怎麼冒出來的：2026-07-25 使用者問「某個網站/部落格/作者很值得關注，怎麼新增？」。
> 屬未定案設計，先孵化。與 `趨勢熱詞發現`（web search 活水）是兄弟——都在拓寬「流」的進水口。

> **母概念**：`sources` 定義**流（flow）從哪來**；訂閱一個站/作者＝**冊封一個高品質的持續
> 水源**。見 [有吸引子的場](../concepts/有吸引子的場.md)。這是原則 5「權重由人冊封」的又一投影。

## 三種「追蹤」的粒度（都由人冊封，原則 5）
| 追什麼 | 機制 | 性質 |
|---|---|---|
| 主題/關鍵字 | **興趣清單**（interest） | 過濾方向 |
| 一篇文章 | **種子**（`ingest`，spec 006） | 一次性的點 |
| 站台/部落格/作者 | **來源訂閱**（source）← 本 draft | **持續的水源** |

種子＝舀一瓢；訂閱＝接一條水管（之後每次 digest 自動帶新內容）。

## 三種「進水口」（流的來源）
- **固定名冊**＝預設水源（arXiv/HF/精選電子報）。
- **訂閱站台/作者**＝**冊封的高品質持續水源**（信任的泉眼）← 本 draft。
- **web search**＝臨時撒的大網（反濾泡，見 `趨勢熱詞發現` draft）。
→ 都是「冊封流的來源」，差在持續性與信任度。

## 好消息：架構大半現成
- `sources` 表、`upsert_source`、**RSS adapter**（現有 Import AI/Last Week in AI/Ars Technica 即是）、
  digest 抓所有啟用來源——**全有**。
- **已有 skill**：`knowledge/skills/evaluate-and-add-source`（實測可用性→挑高訊號→加來源→驗證）。
  ＝**AI/dev 版**的「加來源」；使用者現在就能靠它追一個部落格（叫 AI 跑 skill）。
- **缺口只有**：自助 **runtime `sources add <url>`** ＋ **RSS 自動探測**（給首頁自動找 feed）。

## 三種情況，難度不同（誠實）
1. **有 RSS 的站/部落格**：最簡單。`sources add <rss-url>` 或首頁探測
   `<link rel="alternate" type="application/rss+xml">`。RSS adapter 現成。
2. **沒 RSS 的**：兜底——(a) email-ingestion（Kill the Newsletter→Atom，見來源研究 episode）、
   (b) 爬文章列表頁（脆、ToS：優先未登入公開頁）。
3. **作者（跨平台）**：最難——作者非單一 feed，而是散在 arXiv/部落格/推特。做法＝**組合**
   （arXiv 作者查詢＋部落格 RSS＋…），本質更像**一條存起來的搜尋**，非一根水管。

## 品質分層免費複用
複用 spec 006 的 `source_class` 權重：**信得過的作者/部落格標成高品質來源**，其內容檢索自動加權。
「追一個好作者」＝「給它一個高權重的持續水源」。

## 守原則
- 原則 5 人冊封：使用者選要追哪些站/作者（主權）。
- 原則 3 溯源：訂閱來的每則帶原文連結（本就是）。
- YAGNI/零相依：RSS 探測用 stdlib；email-ingestion/爬取為兜底、後續才做。

## 待解／開放問題
1. `sources add` 的 UX：CLI `sources add <url>`？web「追蹤」按鈕？加時可標品質層（高品質/一般）。
2. RSS 自動探測：給首頁 URL → 抓 HTML → 找 `<link rel=alternate rss>`；找不到 → 提示 email-ingestion。
3. 使用者加的來源存哪：`sources` 表已可（DEFAULT_SOURCES 只是種子集）；要區分「內建 vs 使用者加」嗎？
4. 作者跨平台：先只做「站/部落格 RSS」，作者當**組合來源**留後續？
5. 與 `evaluate-and-add-source` skill 的關係：skill＝AI 版評估加來源；runtime 指令＝使用者自助。
   兩者共用 sources 表；runtime 版可否複用 skill 的「實測可用性」檢查？
