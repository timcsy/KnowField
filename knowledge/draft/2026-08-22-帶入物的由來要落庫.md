## 二、⚠️ 核心發現：37/38/39 的使用量在結構上量不到

`conversations` 的欄位：`id, title, messages, why_node_id, created_at, temporary, last_activity_at, chapters`。

**沒有任何欄位記錄「這段對話是帶著文章／來源開的」。**

而 spec 041 FR-003 **刻意**讓帶入物不進 `messages`（那是對的——擋 model collapse 的閘門），
結果就是它在儲存層**零痕跡**。

⇒ 「帶著這篇聊」被用了幾次，`audit-field-usage` **永遠查不到**。
⇒ 而 audit 的判準是「哪個功能的消費者數是 0」——這三刀在報告上會**永遠是空白**，
而空白**分不出「沒人用」和「量不到」**。

這是 `experience.md:555`「判一份知識死沒死，看『如果它錯了，誰會發現』」套在功能上的樣子。

### 而且我自己的理由就指向溯源

`history/101` 記的那個裁決理由是：

> 混進既有對話會讓那段對話的「由來」變得不純

⚠️ 我用**溯源**當理由做了隔離，卻**沒把那個由來記下來**。隔離做完了，記錄沒做。

## 三、⚠️ 擋在前面的是一個沒人蓋的地基：專案不會加欄

`schema.py:148`：

> 註：不含舊 SQLite 檔的 `_migrate` 補欄（新庫從零起、SCHEMA 已含所有欄）

`CREATE TABLE IF NOT EXISTS` 對既有表是 **no-op** ⇒ 正式庫那 28 段對話所在的表**不會長出新欄**，
新程式一寫就炸。spec 039 沒踩到，是因為它加的是**新表**。

**這件事已經卡住兩個東西**：

1. spec 043 的「文章存 `conversation_id`」——被列 out of scope，理由就是它。
2. 本檔要記的帶入物由來。

⇒ 不是投機性基礎建設，是**已經有兩個具體需求擋在後面**。

## 四、候選形狀

### ① 可攜的加欄路徑

`ALTER TABLE … ADD COLUMN` 兩後端都支援，但 **`IF NOT EXISTS` 只有 PG 有**（SQLite 沒有）。
⇒ 走「先問有哪些欄、缺的才加」：

- SQLite：`PRAGMA table_info(t)`
- PG：`SELECT column_name FROM information_schema.columns WHERE table_name=%s`

宣告式一張表（`(表, 欄, 型別)`），`init_db` 冪等地補。**否決 try/except 硬加**——
把「已存在」跟「真的錯了」混成同一件事，是沉默失敗的作法。

### ② 記什麼

`conversations` 加兩欄：`carried_kind`（`''`／`article`／`source`）、`carried_ref`（文章 id 或來源 url）。

- **只在 INSERT 時寫，永不更新**——由來是「它從哪來的」，不會改。
  `autosave_temporary` 的 UPDATE 分支一個字都不動。
- ⚠️ **這是元資料，不是內容**：MUST NOT 進 `messages`、MUST NOT 改變送給模型的脈絡。
  041 FR-003 的閘門完全不受影響。

### ③ ⚠️ 不要長成計數器 UI

`experience.md:585`「自動化只移走製造成本，沒移走呈現成本——自動又可見的東西不是零成本」。
⇒ **存但不顯示**；只有跑 audit 時才浮出來（audit skill 紀律 2「要看才跑，不常駐」）。

## 五、被否決的做法

- **把帶入物寫進 `messages`** → 直接破 041 FR-003 的閘門。不考慮。
- **前端自己記使用次數（localStorage）** → 換一台機器就沒了，而且沒有人會去讀。
- **先跑 audit 再說** → 現在跑只量得到階段 36，另外三刀一片空白，而那個空白沒有解釋力。
