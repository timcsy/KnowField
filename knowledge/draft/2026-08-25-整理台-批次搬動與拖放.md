# 整理台：搬得動 ≠ 整理得動，而 108 件證明差別在哪

> 狀態：**已兌現**（vision 階段 45，出貨 2026-08-25，commit `7f35010`；
> 轉移見 [history/115](../history/115-在空集合上出貨-而測試是我自己餵的初始狀態.md)）。本檔留為設計理由。
> 日期：2026-08-25。design（使用者提出，選項已裁決）。
> 怎麼冒出來的：階段 44 出貨當天，使用者問「**現在要如何把知識整理到領域裡面？**」
> ——我去查，答案是**幾乎沒辦法**。

---

## 一、⚠️ 我在空集合上出貨了一個功能

階段 44 的 commit message 寫「知識搬得動」。那句話只對**已經在某個領域裡的對話**成立，
而正式庫裡那樣的東西是 **0 件**：

| | 未歸屬／總數（正式庫） | 現在的 UI |
|---|---|---|
| 對話 | **31/31** | `DomainsPage` 只算 `unfiled.length` 顯示數字，**清單沒列出來** |
| 核心理解 | **75/75** | 沒有入口（而後端 `move_knowledge` 早就支援 `why_node`） |
| 文章 | **2/2** | 同上 |

「搬到…」那個下拉只掛在 `inDomain(selected.id)` 的項目上
⇒ **整理的起點動作（把未歸屬的東西搬進去）在介面上不存在。**

⚠️ 這跟「量錯欄位」不同：我的 API 測試全對，實跑也真的搬動了——
**因為我實跑時自己先用 SQL 把資料放進領域裡**，等於自己餵了一個現實中不存在的初始狀態。
⇒ 教訓的形狀：**驗收的起始狀態要是使用者真正的起始狀態**，
而使用者的起始狀態幾乎永遠是「什麼都還沒做」。

## 二、108 件 → 批次不是便利，是可行性

108 件 × （開下拉 ＋ 選）＝ **216 次點擊**。
這跟 FR-004 那個「搬一段跳 15 條詢問 → 第二次就沒人用」是**同一條判準**：
**互動次數超過某個量，功能等於不存在。**

⇒ 核心不是拖放，是兩件：**看得到全部待整理的** ＋ **一次處理一批**。
拖放是體驗，使用者選了要（2026-08-25 裁決：多選批次 ＋ 拖放）。

## 三、⚠️ 批次糾纏的關鍵細節：同批成員之間不算糾纏

單件版本的判準是「相鄰知識的領域**不同且非空**」。批次下這個判準**會誤報**：

> 把 A（對話）和 B（它的理解）一起搬到「數學」。
> A 的鄰居是 B，B 現在在別的領域 ⇒ 單件判準說這是糾纏。
> **但搬完之後兩者都在數學，根本沒有分開。**

⇒ 正確的判準是「**搬完之後**兩端會不會在不同領域」，不是「現在」。
實作上＝**先把整批的目標領域套上去，再算糾纏**；同批成員一律排除。

＋ 同一條理解可能同時是好幾件的鄰居 ⇒ **詢問清單要去重**，
否則搬 10 件會列出 30 行看起來像 30 個問題。

## 四、不變的兩條護欄

- **只算直接連結**（FR-004）——批次不改變這條，只是把 N 次偵測的結果**併成一次詢問**。
- **連帶只走一層**（FR-005）——批次連帶時，被連帶的項目**不會**再連帶它們的鄰居。
  ⚠️ 批次很容易讓人以為「反正都在搬了，順便遞迴吧」——那正是「搬走半個場」的入口。

## 五、形狀

左邊領域樹（＋「未歸屬」也是放置目標）· 右邊待整理清單（可篩 全部／對話／理解／文章）
· 勾選多個 → 拖到樹上放開，或按「搬到選取的領域」→ **一次**糾纏詢問。

需要一支新 API：**整理台的清冊**（`kind` / `id` / `label` / `domain_id` 的扁平清單）。
**不要去擴 `/api/roots` 和 `/api/articles`**——那兩支是給各自的頁用的，
為了整理台加欄會讓三個消費者綁在一起（同 spec 045「兩個欄位讀錯一個」的家族）。

## 六、來源的身分是 **url**，不是整數 id

使用者補充：「**每個領域都有自己的子領域、來源、對話、核心理解、文章**」——五種，不是三種。
而**來源**打破了前三種的形狀：

`list_source_groups()` 是 `... FROM digest_entries GROUP BY de.url` ⇒
**一個「來源」＝一個 url ＝多個塊**。它沒有自己的 id，`first_id` 只是 `MIN(id)`。

- ⇒ `digest_entries` 加 `domain_id`，**用 url 一次設整組塊**（跟 `set_source_meta` 同形狀）。
- **否決用 `first_id` 當代表**：那會讓同來源其他塊沒有領域，而 `MIN(id)` 在新增塊時還會變
  ——一個會自己漂移的主鍵。

⇒ `_KIND_TABLE` 從 `kind → 表` 變成 `kind → (表, 鍵欄位)`，`kid` 型別變成 `int | str`。

**來源的鄰居**：從它冊封的理解（`why_nodes.source_entry_id` 對到該 url 的塊）
＋ 帶著它開的對話（`conversations.carried_kind='source'` 且 `carried_ref=url`，spec 044 存的）。
`source_entry_id` **預設 0 不是 NULL**——本週才因為 `IS NOT NULL` 恆真報錯過一次，要用 `> 0` 過濾。

## 七、裁決：批次端點**取代**單件端點，不並存

單件的 `/api/knowledge/{kind}/{kid}/{tangles,move}` 昨天才上線，而 `kid` 是路徑參數
⇒ 來源的 url 塞進路徑要編碼，很醜；而且批次版本能力是它的超集。

⇒ **刪掉單件那兩支**，前端單件操作＝送一個元素的清單。
留著會變成「同一件事兩套介面」——使用者兩次都選拿掉那個（spec 045、spec 047）。

## 被否決的

- **自動分類** → 沿用階段 43／44 的裁決：猜出來的歸屬看起來跟真的一樣。
- **只做多選、不做拖放** → 使用者明確選了要拖放。
- **批次時逐件詢問** → 就是 216 次點擊換一個包裝。
