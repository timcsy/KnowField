# 場的使用審計（KnowField）

**為什麼存在**：`experience.md`「主動審計既有產物 ＝ 最強的照妖鏡」——

> 真實使用是照妖鏡，但**被動等回饋只照得出「當下步」的瑕疵**；**累積型**的漏要靠**主動攤開既有
> 產物的數據**才照得出。審計 ≠ 等回饋，是另一種、且更早的照法。

這件事已經手動做過兩次（2026-07-29 的對話審計 → `history/064`；2026-08-18 的 knowie-judge），
第三次之前固化，免得每次重造。

它同時是 experience「**死的知識不是靜止的知識，是沒有任何消費者會發現它錯掉的知識**」在產品面的
量測工具：一個功能有沒有消費者，是數字問題，不是感覺問題。

## 三條紀律（違反了這個 skill 就不該存在）

1. **唯讀。** 只 SELECT。任何寫入都不屬於這裡。
2. **要看才跑，不常駐。** 不做儀表板、不進任何頁面。理由是 experience「自動化只移走製造成本，
   沒移走呈現成本——自動又可見的東西不是零成本」；一份天天出現在你眼前的審計報告，
   自己就會變成它要抓的那種雜訊。
3. **輸出只回答「哪條軸錯了」，不授權砍。** experience「一個沒人用的功能，多半不是需求不存在，
   是把旋鈕裝在錯的軸上」——數字是問題的開頭，不是判決。

## 步驟

### 1. 確認你在量哪個資料庫

⚠️ **本機 dev DB 的數字不是使用證據**。真實使用在 prod。

```bash
echo "${KNOWFIELD_DATABASE_URL:-（未設 → 預設本機 knowfield.db）}"
```

要量 prod 就先設 `KNOWFIELD_DATABASE_URL` 指向 prod DSN。報告裡**一定要標出資料來源**，
否則下一個讀的人會把 dev 數字當結論。

### 2. 跑審計

走 `Repository` 而不是直接開 sqlite3——它是雙後端 adapter（`history/086`），
直接開 sqlite3 的話 prod 就跑不了。

```bash
uv run python knowledge/skills/audit-field-usage/audit.py
```

### 3. 讀報告：看「沉默」不是看「總量」

判準不是哪個數字大，是**哪個功能的消費者數是 0 或 1**。

- 一個功能出貨了、而它的消費動作計數是 0 → 它現在是死的（不代表該砍，見紀律 3）
- 一個功能只有製造動作、沒有消費動作 → 典型的「旋鈕裝錯軸」：東西產出來了，但沒有人回頭用它
- 製造 ≫ 消費（例如暫時對話很多、升永久很少）→ 那個比值就是它的訊噪比

### 4. 反流

審計照出來的東西**不會自己回到知識庫**。跑完接：

- 有結論（某功能沒消費者、某條軸錯了）→ `/knowie-capture` 落 `draft/`
- 真的改了某個決定 → 那是轉移，進 `history/`（**不是**「我們審計過了」這種完成句）
- 蒸餾出可複用的判準 → `experience.md`（要人點頭）
