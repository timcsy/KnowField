### 把重量級相依藏在可插拔介面後，預設離線 stub

- **理論說**：分診管線需要 embedding（去重／排序）與 LLM（摘要），計畫原列
  sentence-transformers 與 anthropic 為相依——預期實作與測試都需先安裝這些重量級套件。
- **實際發生**：實作環境無法保證安裝這些套件、也不宜在測試中打真實 API；若硬綁，
  TDD 會變成「先裝好幾百 MB 才能跑第一個測試」，且測試不確定（打網路）。
- **解決方式**：把 embedding／摘要都抽象成介面（`Embedder`／`Summarizer`），MVP 預設
  用確定性、零相依的 `HashingEmbedder`／`StubSummarizer`；真實後端作為可選 extras 插拔。
  結果 49 個測試零安裝、離線、確定性通過，且 CLI 還能真實跑通 HF Papers。
- **教訓**：把外部重量級相依藏在窄介面後、預設一個離線確定性實作——TDD 才能零安裝、
  快、可重現；真實後端等要用時再插拔。這也正是「先簡單、YAGNI」（憲章原則 IV）。
- **補面（真實側才是坑，2026-07-25）**：stub 側好寫，**真實那一側若只寫通用殼**（如 Bearer
  ＋泛 payload）**很可能對不上任何真實提供者、卻看似完成**——各家認證格式不同（Bearer header／
  body `api_key`／自訂 header）。預設形狀要**對準一個具體提供者**、且留注入點（如 `poster`）供測試。
  出處：web 搜尋接 Tavily 時，原 Bearer 對不上（金鑰要放 body）——見 `history/034`。
- **來源**：`history/002-架構選型與務實偏離.md`、`specs/001-daily-triage-digest/`

### 真實 LLM 會把提示的格式鷹架字面吐出來

- **理論說**：提示裡寫「第一行＝一句定位，第二行＝一句為何值得看」，預期模型會照著
  產出乾淨的兩行內容。
- **實際發生**：接真實 OpenAI 格式後端一跑，模型把鷹架字面吐進內容——輸出變成
  「第一行＝這篇在談…」「為何值得看：第二行：…」，且**時有時無、不一致**，離線
  stub 測試完全抓不到（stub 不會這樣）。
- **解決方式**：雙重防線——(1) 提示改為明令「直接輸出，不要加任何標籤／編號」；
  (2) 解析端 `_clean_line` 剝除殘留前綴，且**標籤字須後接分隔符才剝**（否則會誤刪
  內容裡本就以「定位」開頭的正常句——這個 bug 我第一版就踩到）。
- **教訓**：格式化 LLM 輸出時，別只靠提示；解析端要有防禦性後處理。且「用 stub 測到
  綠燈」≠「真實模型行為正確」——**接真實後端後一定要再跑一次真的驗證**。
- **來源**：`history/004-真實後端改用-OpenAI-格式-API.md`、commit `50205bc`

### 外部後端失敗不該炸掉整個指令

- **理論說**：接了真實 OpenAI 格式後端，正常情況會回 embedding／摘要，指令順利完成。
- **實際發生**：驗證拉模式時，API 回 **403 `allocation_quarantined`**（額度因前面連續呼叫
  被暫時隔離）。`OpenAIError` 一路往上冒，把整個 `pull` 指令炸成 Python traceback——
  使用者看到的是堆疊而非人話（違反原則 V）。
- **解決方式**：在 CLI 層（`pull_cmd`／`digest_cmd`）攔截 `OpenAIError`，印出乾淨的繁中
  訊息＋退出碼 1，並提示「可稍後重試，或設 `LEARNNEWS_BACKEND=offline`」。
- **教訓**：任何**外部相依**（API、網路、限流）都會失敗；在**邊界**（CLI／進入點）
  攔成可行動的訊息，別讓底層例外冒到使用者面前。可插拔介面讓「切離線」成為現成的退路。
- **來源**：`history/008-拉模式完成.md`、commit `223901a`

### 確定性 ≠ 直覺：離線 embedder 的雜湊碰撞

- **理論說**：離線 `HashingEmbedder` 是確定性的，共享詞元的字串（如「新聞」對「新聞…」）
  應有明顯正相關 cosine，測試相關性可放心用任意字串。
- **實際發生**：階段 5 寫測試時，`cosine("新聞 …", "新聞")` 竟得 **0.0**——短字串的少數詞元
  剛好與其他 token 雜湊**碰撞抵消**（空字串更是零向量）。兩個新測試假性失敗，乍看像 bug，
  其實是測試 fixture 選錯字串。
- **解決方式**：改用**經實測會匹配**的字串（如 "agent"，cosine≈0.28–0.45），別把相關性
  斷言建在未驗證的任意短字串上；必要時先跑一段小 script 量 cosine 再定 fixture。
- **教訓**：「確定性」不等於「行為符合直覺」。對這種近似元件，測試前先**實測它對你的
  fixture 的實際輸出**，別假設。這也是「用 stub 綠燈 ≠ 真實正確」的另一面。
- **延伸（RAG 真跑 T025，2026-07-24）**：同一個坑的第二面——**離線與真實 embedder 的 cosine
  尺度不可比**。離線 stub 測試全綠，但真實 `text-embedding-3-small` 的門檻 0.10 太低（命中≈0.6、
  無關問題也有 0.22），導致「查無」還列一堆來源。**任何靠 cosine 絕對值的門檻都得對實際
  embedder 校準**（改成依 backend 分流：openai≈0.30／離線≈0.05）。凡「離線可跑」的近似元件，
  上真實後端前務必**實測尺度**再定閾值——這種 bug stub 測試永遠抓不到，只有真跑抓得到。
- **來源**：`history/010-可讀文章式消化完成.md`、commit `3f82e03`；`history/021`（T025 真跑）、
  `specs/005-rag-qa/research.md` R5

### 對外部 API 別在迴圈裡逐一呼叫——批次＋並行

- **理論說**：功能對就好；每個候選各自呼叫一次 embedding、每則各自呼叫一次消化，
  邏輯清楚。
- **實際發生**：web 主題深挖對數十上百個候選**逐一序列**呼叫 embedding API →
  **115 秒**，還被當成異常用量**觸發額度隔離**（403）。逐則消化又是 6 次序列 LLM 呼叫。
- **解決方式**：**批次**——embedding 改 `embed_many`，一次 API 呼叫嵌入多筆（115s→37s）；
  **並行**——消化用執行緒池同時打（I/O bound，as_completed，37s→~20s）。
- **教訓**：外部 API 呼叫**能批次就批次、能並行就並行**，別在迴圈裡逐一同步呼叫——不只
  慢（N 倍延遲），還可能被服務端當成濫用擋掉。這是延遲與穩定性的雙重地雷。
- **來源**：`history/015-web效能與即時進度.md`、commits `fb7d6bd`、`416e476`

### 慢操作要給即時進度，而非假 spinner

- **理論說**：慢的請求加個轉圈圈 spinner 就好。
- **實際發生**：主題深挖要 ~20s，一開始只有計時器輪播的**假階段訊息**——使用者仍「不知道
  挖到哪」，因為那不是真進度。
- **解決方式**：改 **SSE 串流**——伺服器逐步推**真實**事件（抓到 N 候選→去重 M→排序→
  **每篇文章寫好即推**），前端邊收邊顯示；頁面秒開、結果一張張冒出。
- **教訓**：慢操作的體驗關鍵是**真實、增量的進度**（已知就顯示），不是假動畫。能串流就
  串流（SSE/分段回應），讓使用者看到系統確實在推進、推進到哪。
- **來源**：`history/015-web效能與即時進度.md`、commit `60c4d72`

### 溯源／grounding 要在程式結構上保證，不靠模型自律

- **理論說**：要 RAG 答案「掛來源」，就在 prompt 裡叫模型「逐點標來源」，模型會照做。
- **實際發生**：做 RAG MVP（spec 005）時意識到——**模型會漏標、標錯、甚至編造來源**。若
  「答案有哪些來源」由模型自報，溯源（原則 3「無來源不出貨」）就建在流沙上。
  **實證背書**：2026 研究顯示商用模型**引用幻覺率 11–57%**、且「**正確 ≠ 忠實**」（模型會事後
  合理化引用）——所以「叫模型標來源」本質不可靠（見 `episodes/2026-07-23-競品與來源研究快照.md`）。
- **解決方式**：**來源清單由程式端從『實際檢索到的條目集合』生成**，不是解析模型輸出。
  `RagService` 只把 top-k 檢索結果編號傳給 answerer，回傳的 `sources` 直接來自那個集合——
  模型就算漏標 `[n]`，來源仍真實、可回原文。查無相關時**程式端直接不呼叫合成後端**、不產
  任何內容。
- **教訓**：凡「可信度靠某個保證」（溯源、標籤、不杜撰），就**把保證做進程式結構**，別依賴
  模型自律。同型前例：AI 圖的「AI 示意・非原文」標籤由程式加（非模型）、根因萃取的候選要
  標「推斷＋掛證據」。**模型負責生成，程式負責守約。**
- **真跑再撞一次（2026-07-25，history/027）**：問「AI原理」→ 模型回「沒有相關材料」，程式卻
  照列 6 個來源（自相矛盾）。就是同一個坑的反面——**模型自報的訊號（『無材料』）也要程式
  『接住』**（偵測到就轉 no_material、不列來源），否則「模型說一套、程式做另一套」。附帶：
  模型會**因問題廣泛而過度拒答**，prompt 要明令「部分相關就作答、只有完全無關才說沒材料」。
- **再一面（2026-07-25，history/030）**：同一原則不限模型——**存取／唯讀邊界也要做進資料層，
  不靠 UI**。知識庫管理的「每日流唯讀」由 repo 方法 `WHERE digest_id=種子容器` 結構保證
  （傳流的 id→不動作），而非「UI 不顯示刪除鈕」——後者一個手工 POST 就繞過。**保證做進
  最底層，別靠上層（模型／UI）自律。**
- **來源**：`history/021-RAG-MVP-實作完成.md`、`specs/005-rag-qa/research.md` R4、
  `concepts/有吸引子的場.md`（根因萃取紀律）；`history/030-知識庫管理完成.md`（唯讀邊界）

### 擴充已出貨功能時，選「免動既有資料結構」的設計，即使略醜

- **理論說**：加種子這種新語料，乾淨做法是開一張獨立的 `seeds` 表，語義清爽。
- **實際發生**：增量 1 的 `entry_embeddings` 主鍵是 `digest_entries.id`；獨立 `seeds` 表的 id
  會**跟它撞**，得改**已出貨**的嵌入表結構（加 kind 欄或改鍵）——侵入正在用的功能、要遷移。
- **解決方式**：讓種子存進**哨兵「種子容器」digest**、復用 `digest_entries` → `entry_id` 仍
  唯一 → **嵌入表免動、免遷移**。語義略醜（種子假裝成 digest），以哨兵 date＋`--today` 排除緩解。
- **教訓**：擴充已出貨功能時，**遷移風險 > 優雅**——優先選不動既有資料結構/不改已出貨表的
  設計，把「醜但隔離」的成本記在明處（research/history），勝過「漂亮但要動全表」的風險。
- **來源**：`history/025-種子ingest完成.md`、`specs/006-seed-ingest/research.md` R1

### 把品質準則「列成檢查表」給 AI ≠ 讓 AI 追求品質

- **理論說**：根因萃取提示裡把 7 條試金石（含「追問不撞牆」）列清楚，模型就會照著挖到底、
  給出有本質的深 why。
- **實際發生**：模型把試金石當**通過即可的檢查表**，給一個過得去的**表面 why** 就交卷——
  使用者回饋「本質的 why 太少，都是表面的，缺 aha」。準則列了，品質沒到。
- **解決方式**：把「**追求那個品質**」本身設成任務——提示改成「目標＝挖到 bedrock、逼出 aha；
  **遞迴追問**『那這個又為什麼』到撞原始層，**不到底不准停**；看到霧詞＝再挖一層」。並讓深度
  **可視化**（why 階梯，表面→bedrock）＋**可誠實放棄**（挖不到回 no_material，勝過編假深洞見）。
- **教訓**：對 AI 生成，**列品質準則 ≠ 得到品質**——準則只是判準，模型會找「剛好通過」的最省解。
  要品質，就把**追求品質的動作**寫成任務本身（遞迴/往下挖/不到底不停），並讓產物**顯示自己的
  深度**（可視化）＋**允許誠實承認不足**（no_material）。通用於整理／消化／擴展等各 AI 生成步驟。
- **來源**：`history/041-根因萃取挖到bedrock.md`、`concepts/有吸引子的場.md`（試金石 6、aha）

### 聚合混來源資料，比較前先正規化

- **理論說**：把各來源抓到的條目丟進去重／排序，挑「發布時間最早」的當代表，`min(...)` 就好。
- **實際發生**：`published_at` 混時區——atom/arxiv 用 `fromisoformat`→**aware**、rss/None/web→**naive**；
  同一去重群組混到 aware＋naive，`min()` 拋 `can't compare offset-naive and offset-aware datetimes`，
  **整份 digest 崩**、重整整個失敗（使用者看到的還是舊匯整）。
- **解決方式**：排序鍵**正規化**——aware `astimezone(utc).replace(tzinfo=None)` 轉 naive UTC 再比。
- **教訓**：跨來源的資料**型別/格式各異**（時區有無、None、單位、大小寫）；任何 `min/max/sort/==`
  前**先統一正規化**，否則邊界一混就炸。是「餵進最底層前先歸一」的家族。
- **來源**：`history/048-web活水news模式與時區崩潰修正.md`、`digest/builder.py` `_canonical`

### 批次聚合：單一項的例外不該拖垮整批

- **理論說**：`build` 逐來源抓取，攔 `SourceUnavailable` 就夠——來源掛了標缺漏、繼續。
- **實際發生**：攔截**只抓預期的一種**（`SourceUnavailable`）。一個來源丟出**非預期**例外
  （上例的 `TypeError`）就漏網、往上炸掉整份 digest——一個壞來源拖垮全部。
- **解決方式**：per-來源攔截**加寬**——除了友善的 `SourceUnavailable`，再加一個 `except Exception`
  → 標缺漏、記錄、繼續。壞一個跳一個，不崩整批。
- **教訓**：批次聚合／扇出的**例外攔截面要夠寬**——別只攔「你想到的那種」。**單點失敗隔離**：
  一個壞項→標記跳過，整批照常。（教訓 3「邊界攔外部失敗」的延伸：邊界要攔**所有**失敗，不只一種。）
- **來源**：`history/048-web活水news模式與時區崩潰修正.md`、`digest/builder.py` build 迴圈

### 提案-批准迴圈 ≠ 打到需求（被設計優雅與流程順暢牽著走）

- **理論說**：跟著漂亮的母概念（`有吸引子的場`）＋順暢的 spec-kit 節奏走，一輪輪 specify→
  plan→tasks→implement，使用者每次都說「好／都加／做完」——看起來方向對、在穩定交付。
- **實際發生**：20 個 spec 之後，使用者說「這工具好像沒幫到我，需求都沒被打到」，且坦承**從沒
  自己打開過它**。回頭看：我一直**提案、他一直批准**，但「點頭同意」≠「需求被打到」。我被
  「和概念自洽」＋「流程有進度」的雙重舒適牽著走，一路加**下游 KB 深度**（場、關聯、根因、來源
  推薦），卻沒先證明上游最基本的價值——結果全是沒人去開的目的地。
- **解決方式**：停止提功能，**從使用者真實的一天重新推導**——問「上週你自己開過它嗎」（答：沒有）、
  「哪個時刻你會冒出需求」。一問就定位到真需求（當下、手機、反逢迎），且判明先前方向是被優雅
  帶偏。捕捉成 re-route draft（`draft/2026-07-28-反逢迎的當下副手.md`）。
- **教訓**：**「使用者批准提案」是最危險的偽訊號**——它讓「自洽且有進度」冒充「有用」。真正的
  驗收訊號只有一個：**使用者會不會在沒人要求時，自己伸手用它。** 每隔幾輪就用它校準；**別讓
  設計的優雅或流程的順暢代替「打到需求」的證據**。動手前先問「這改變使用者真實動線裡的什麼」。
- **如何應用（解方，2026-07-28 實證）**：上面是**診斷**；解方是**大賭注/轉向前，先跑最便宜的手動
  探針驗「真實有用」，過了才 promote＋蓋**。做法：把功能拆成獨立的賭注（如「這份綜合有沒有幫到你」
  vs「你會不會在手機上伸手」），**用手動 dry-run 驗最核心那個賭注、零 build**——探針同時會**撞出
  真實實作風險**（光靠批准永遠不會浮現）。實證：spec 021 前對 Claude Opus 5 手動跑一次「反逢迎綜合」，
  使用者答「有用」＋撞出兩個真風險（伺服器抓被擋、query 品質），**才** promote。手動探針＝可執行規格。
  接上 principle 6（過度擬合檢查：蓋最小一塊撞現實）。出處：`history/056`/`057`、`draft/2026-07-28-反逢迎的當下副手.md`。
- **來源**：`draft/2026-07-28-反逢迎的當下副手.md`（2026-07-28 診斷對話）
