### 把重量級相依藏在可插拔介面後，預設離線 stub

- **理論說**：分診管線需要 embedding（去重／排序）與 LLM（摘要），計畫原列
  sentence-transformers 與 anthropic 為相依——預期實作與測試都需先安裝這些重量級套件。
- **實際發生**：實作環境無法保證安裝這些套件、也不宜在測試中打真實 API；若硬綁，
  TDD 會變成「先裝好幾百 MB 才能跑第一個測試」，且測試不確定（打網路）。
- **解決方式**：把 embedding／摘要都抽象成介面（`Embedder`／`Summarizer`），MVP 預設
  用確定性、零相依的 `HashingEmbedder`／`StubSummarizer`；真實後端作為可選 extras 插拔。
  結果 49 個測試零安裝、離線、確定性通過，且 CLI 還能真實跑通 HF Papers。
- **教訓**：把外部重量級相依藏在窄介面後、預設一個離線確定性實作——TDD 才能零安裝、
  快、可重現；真實後端等要用時再插拔。這也正是「先簡單、YAGNI」（憲章原則 IV）。
- **補面（真實側才是坑，2026-07-25）**：stub 側好寫，**真實那一側若只寫通用殼**（如 Bearer
  ＋泛 payload）**很可能對不上任何真實提供者、卻看似完成**——各家認證格式不同（Bearer header／
  body `api_key`／自訂 header）。預設形狀要**對準一個具體提供者**、且留注入點（如 `poster`）供測試。
  出處：web 搜尋接 Tavily 時，原 Bearer 對不上（金鑰要放 body）——見 `history/034`。
- **來源**：[history/002-架構選型與務實偏離.md](history/002-架構選型與務實偏離.md)、`specs/001-daily-triage-digest/`

### 真實 LLM 會把提示的格式鷹架字面吐出來

- **理論說**：提示裡寫「第一行＝一句定位，第二行＝一句為何值得看」，預期模型會照著
  產出乾淨的兩行內容。
- **實際發生**：接真實 OpenAI 格式後端一跑，模型把鷹架字面吐進內容——輸出變成
  「第一行＝這篇在談…」「為何值得看：第二行：…」，且**時有時無、不一致**，離線
  stub 測試完全抓不到（stub 不會這樣）。
- **解決方式**：雙重防線——(1) 提示改為明令「直接輸出，不要加任何標籤／編號」；
  (2) 解析端 `_clean_line` 剝除殘留前綴，且**標籤字須後接分隔符才剝**（否則會誤刪
  內容裡本就以「定位」開頭的正常句——這個 bug 我第一版就踩到）。
- **教訓**：格式化 LLM 輸出時，別只靠提示；解析端要有防禦性後處理。且「用 stub 測到
  綠燈」≠「真實模型行為正確」——**接真實後端後一定要再跑一次真的驗證**。
- **來源**：[history/004-真實後端改用-OpenAI-格式-API.md](history/004-真實後端改用-OpenAI-格式-API.md)、commit `50205bc`

### 外部後端失敗不該炸掉整個指令

- **理論說**：接了真實 OpenAI 格式後端，正常情況會回 embedding／摘要，指令順利完成。
- **實際發生**：驗證拉模式時，API 回 **403 `allocation_quarantined`**（額度因前面連續呼叫
  被暫時隔離）。`OpenAIError` 一路往上冒，把整個 `pull` 指令炸成 Python traceback——
  使用者看到的是堆疊而非人話（違反原則 V）。
- **解決方式**：在 CLI 層（`pull_cmd`／`digest_cmd`）攔截 `OpenAIError`，印出乾淨的繁中
  訊息＋退出碼 1，並提示「可稍後重試，或設 `KNOWFIELD_BACKEND=offline`」。
- **教訓**：任何**外部相依**（API、網路、限流）都會失敗；在**邊界**（CLI／進入點）
  攔成可行動的訊息，別讓底層例外冒到使用者面前。可插拔介面讓「切離線」成為現成的退路。
- **來源**：[history/008-拉模式完成.md](history/008-拉模式完成.md)、commit `223901a`

### 確定性 ≠ 直覺：離線 embedder 的雜湊碰撞

- **理論說**：離線 `HashingEmbedder` 是確定性的，共享詞元的字串（如「新聞」對「新聞…」）
  應有明顯正相關 cosine，測試相關性可放心用任意字串。
- **實際發生**：階段 5 寫測試時，`cosine("新聞 …", "新聞")` 竟得 **0.0**——短字串的少數詞元
  剛好與其他 token 雜湊**碰撞抵消**（空字串更是零向量）。兩個新測試假性失敗，乍看像 bug，
  其實是測試 fixture 選錯字串。
- **解決方式**：改用**經實測會匹配**的字串（如 "agent"，cosine≈0.28–0.45），別把相關性
  斷言建在未驗證的任意短字串上；必要時先跑一段小 script 量 cosine 再定 fixture。
- **教訓**：「確定性」不等於「行為符合直覺」。對這種近似元件，測試前先**實測它對你的
  fixture 的實際輸出**，別假設。這也是「用 stub 綠燈 ≠ 真實正確」的另一面。
- **延伸（RAG 真跑 T025，2026-07-24）**：同一個坑的第二面——**離線與真實 embedder 的 cosine
  尺度不可比**。離線 stub 測試全綠，但真實 `text-embedding-3-small` 的門檻 0.10 太低（命中≈0.6、
  無關問題也有 0.22），導致「查無」還列一堆來源。**任何靠 cosine 絕對值的門檻都得對實際
  embedder 校準**（改成依 backend 分流：openai≈0.30／離線≈0.05）。凡「離線可跑」的近似元件，
  上真實後端前務必**實測尺度**再定閾值——這種 bug stub 測試永遠抓不到，只有真跑抓得到。
- **延伸（先實測再斷言，2026-08-07）**：同一坑的第三面——**別對外部系統的行為想當然，先唯讀查真實資料／實測**。
  來源進料除錯時至少三次假設錯：「抽取器太弱」（其實重抓就補全）、「OCR 不支援 pages/回圖」（其實是 gateway 沒轉、
  改完就會）、「瀏覽器看到 raw 公式＝真 bug」（其實是 **stale SW 快取**假象）。每次都靠**唯讀查 `knowfield.db`／
  離線重跑正則／真跑 gateway** 才翻案。教訓：**動手修前，先讓真實資料／實測說話**——省下修錯方向的整輪工。
- **來源**：[history/010-可讀文章式消化完成.md](history/010-可讀文章式消化完成.md)、commit `3f82e03`；`history/021`（T025 真跑）、
  `specs/005-rag-qa/research.md` R5；`history/081`（先實測再斷言）

### 對外部 API 別在迴圈裡逐一呼叫——批次＋並行

- **理論說**：功能對就好；每個候選各自呼叫一次 embedding、每則各自呼叫一次消化，
  邏輯清楚。
- **實際發生**：web 主題深挖對數十上百個候選**逐一序列**呼叫 embedding API →
  **115 秒**，還被當成異常用量**觸發額度隔離**（403）。逐則消化又是 6 次序列 LLM 呼叫。
- **解決方式**：**批次**——embedding 改 `embed_many`，一次 API 呼叫嵌入多筆（115s→37s）；
  **並行**——消化用執行緒池同時打（I/O bound，as_completed，37s→~20s）。
- **教訓**：外部 API 呼叫**能批次就批次、能並行就並行**，別在迴圈裡逐一同步呼叫——不只
  慢（N 倍延遲），還可能被服務端當成濫用擋掉。這是延遲與穩定性的雙重地雷。
- **來源**：[history/015-web效能與即時進度.md](history/015-web效能與即時進度.md)、commits `fb7d6bd`、`416e476`

### 慢操作要給即時進度，而非假 spinner

- **理論說**：慢的請求加個轉圈圈 spinner 就好。
- **實際發生**：主題深挖要 ~20s，一開始只有計時器輪播的**假階段訊息**——使用者仍「不知道
  挖到哪」，因為那不是真進度。
- **解決方式**：改 **SSE 串流**——伺服器逐步推**真實**事件（抓到 N 候選→去重 M→排序→
  **每篇文章寫好即推**），前端邊收邊顯示；頁面秒開、結果一張張冒出。
- **教訓**：慢操作的體驗關鍵是**真實、增量的進度**（已知就顯示），不是假動畫。能串流就
  串流（SSE/分段回應），讓使用者看到系統確實在推進、推進到哪。
- **來源**：[history/015-web效能與即時進度.md](history/015-web效能與即時進度.md)、commit `60c4d72`

### 溯源／grounding 要在程式結構上保證，不靠模型自律

- **理論說**：要 RAG 答案「掛來源」，就在 prompt 裡叫模型「逐點標來源」，模型會照做。
- **實際發生**：做 RAG MVP（spec 005）時意識到——**模型會漏標、標錯、甚至編造來源**。若
  「答案有哪些來源」由模型自報，溯源（原則 3「無來源不出貨」）就建在流沙上。
  **實證背書**：2026 研究顯示商用模型**引用幻覺率 11–57%**、且「**正確 ≠ 忠實**」（模型會事後
  合理化引用）——所以「叫模型標來源」本質不可靠（見 [episodes/2026-07-23-競品與來源研究快照.md](episodes/2026-07-23-競品與來源研究快照.md)）。
- **解決方式**：**來源清單由程式端從『實際檢索到的條目集合』生成**，不是解析模型輸出。
  `RagService` 只把 top-k 檢索結果編號傳給 answerer，回傳的 `sources` 直接來自那個集合——
  模型就算漏標 `[n]`，來源仍真實、可回原文。查無相關時**程式端直接不呼叫合成後端**、不產
  任何內容。
- **教訓**：凡「可信度靠某個保證」（溯源、標籤、不杜撰），就**把保證做進程式結構**，別依賴
  模型自律。同型前例：AI 圖的「AI 示意・非原文」標籤由程式加（非模型）、根因萃取的候選要
  標「推斷＋掛證據」。**模型負責生成，程式負責守約。**
- **真跑再撞一次（2026-07-25，history/027）**：問「AI原理」→ 模型回「沒有相關材料」，程式卻
  照列 6 個來源（自相矛盾）。就是同一個坑的反面——**模型自報的訊號（『無材料』）也要程式
  『接住』**（偵測到就轉 no_material、不列來源），否則「模型說一套、程式做另一套」。附帶：
  模型會**因問題廣泛而過度拒答**，prompt 要明令「部分相關就作答、只有完全無關才說沒材料」。
- **再一面（2026-07-25，history/030）**：同一原則不限模型——**存取／唯讀邊界也要做進資料層，
  不靠 UI**。知識庫管理的「每日流唯讀」由 repo 方法 `WHERE digest_id=種子容器` 結構保證
  （傳流的 id→不動作），而非「UI 不顯示刪除鈕」——後者一個手工 POST 就繞過。**保證做進
  最底層，別靠上層（模型／UI）自律。**
- **再一面（2026-08-07，history/083）**：同一原則到了「知識的**輸出**」端——**生成文章的 References 由程式從
  佐證 `evidence_urls` 結構化組**（`_references`），LLM 只寫正文、不碰引用清單。輸入端（RAG 溯源）與輸出端
  （文章 references）是**同一保證的兩端**：可信度做進程式結構，不論資料流向哪邊都不靠模型自律。
- **來源**：[history/021-RAG-MVP-實作完成.md](history/021-RAG-MVP-實作完成.md)、`specs/005-rag-qa/research.md` R4、
  [concepts/有吸引子的場.md](concepts/有吸引子的場.md)（根因萃取紀律）；[history/030-知識庫管理完成.md](history/030-知識庫管理完成.md)（唯讀邊界）

### 擴充已出貨功能時，選「免動既有資料結構」的設計，即使略醜

- **理論說**：加種子這種新語料，乾淨做法是開一張獨立的 `seeds` 表，語義清爽。
- **實際發生**：增量 1 的 `entry_embeddings` 主鍵是 `digest_entries.id`；獨立 `seeds` 表的 id
  會**跟它撞**，得改**已出貨**的嵌入表結構（加 kind 欄或改鍵）——侵入正在用的功能、要遷移。
- **解決方式**：讓種子存進**哨兵「種子容器」digest**、復用 `digest_entries` → `entry_id` 仍
  唯一 → **嵌入表免動、免遷移**。語義略醜（種子假裝成 digest），以哨兵 date＋`--today` 排除緩解。
- **教訓**：擴充已出貨功能時，**遷移風險 > 優雅**——優先選不動既有資料結構/不改已出貨表的
  設計，把「醜但隔離」的成本記在明處（research/history），勝過「漂亮但要動全表」的風險。
- **來源**：[history/025-種子ingest完成.md](history/025-種子ingest完成.md)、`specs/006-seed-ingest/research.md` R1

### 把品質準則「列成檢查表」給 AI ≠ 讓 AI 追求品質

- **理論說**：根因萃取提示裡把 7 條試金石（含「追問不撞牆」）列清楚，模型就會照著挖到底、
  給出有本質的深 why。
- **實際發生**：模型把試金石當**通過即可的檢查表**，給一個過得去的**表面 why** 就交卷——
  使用者回饋「本質的 why 太少，都是表面的，缺 aha」。準則列了，品質沒到。
- **解決方式**：把「**追求那個品質**」本身設成任務——提示改成「目標＝挖到 bedrock、逼出 aha；
  **遞迴追問**『那這個又為什麼』到撞原始層，**不到底不准停**；看到霧詞＝再挖一層」。並讓深度
  **可視化**（why 階梯，表面→bedrock）＋**可誠實放棄**（挖不到回 no_material，勝過編假深洞見）。
- **教訓**：對 AI 生成，**列品質準則 ≠ 得到品質**——準則只是判準，模型會找「剛好通過」的最省解。
  要品質，就把**追求品質的動作**寫成任務本身（遞迴/往下挖/不到底不停），並讓產物**顯示自己的
  深度**（可視化）＋**允許誠實承認不足**（no_material）。通用於整理／消化／擴展等各 AI 生成步驟。
- **來源**：[history/041-根因萃取挖到bedrock.md](history/041-根因萃取挖到bedrock.md)、[concepts/有吸引子的場.md](concepts/有吸引子的場.md)（試金石 6、aha）

### 聚合混來源資料，比較前先正規化

- **理論說**：把各來源抓到的條目丟進去重／排序，挑「發布時間最早」的當代表，`min(...)` 就好。
- **實際發生**：`published_at` 混時區——atom/arxiv 用 `fromisoformat`→**aware**、rss/None/web→**naive**；
  同一去重群組混到 aware＋naive，`min()` 拋 `can't compare offset-naive and offset-aware datetimes`，
  **整份 digest 崩**、重整整個失敗（使用者看到的還是舊匯整）。
- **解決方式**：排序鍵**正規化**——aware `astimezone(utc).replace(tzinfo=None)` 轉 naive UTC 再比。
- **教訓**：跨來源的資料**型別/格式各異**（時區有無、None、單位、大小寫）；任何 `min/max/sort/==`
  前**先統一正規化**，否則邊界一混就炸。是「餵進最底層前先歸一」的家族。
- **來源**：[history/048-web活水news模式與時區崩潰修正.md](history/048-web活水news模式與時區崩潰修正.md)、`digest/builder.py` `_canonical`

### 批次聚合：單一項的例外不該拖垮整批

- **理論說**：`build` 逐來源抓取，攔 `SourceUnavailable` 就夠——來源掛了標缺漏、繼續。
- **實際發生**：攔截**只抓預期的一種**（`SourceUnavailable`）。一個來源丟出**非預期**例外
  （上例的 `TypeError`）就漏網、往上炸掉整份 digest——一個壞來源拖垮全部。
- **解決方式**：per-來源攔截**加寬**——除了友善的 `SourceUnavailable`，再加一個 `except Exception`
  → 標缺漏、記錄、繼續。壞一個跳一個，不崩整批。
- **教訓**：批次聚合／扇出的**例外攔截面要夠寬**——別只攔「你想到的那種」。**單點失敗隔離**：
  一個壞項→標記跳過，整批照常。（教訓 3「邊界攔外部失敗」的延伸：邊界要攔**所有**失敗，不只一種。）
- **復發於串流路徑（2026-08-14，`history/092`）**：同一形狀第二次——`_post_stream` 的 `try` 只包住
  `urlopen`，**迭代 `for raw in resp` 在 try 外面**；`_stream_gen` 又只攔 `(SourceUnavailable, OpenAIError)`。

### 提案-批准迴圈 ≠ 打到需求（被設計優雅與流程順暢牽著走）

- **理論說**：跟著漂亮的母概念（`有吸引子的場`）＋順暢的 spec-kit 節奏走，一輪輪 specify→
  plan→tasks→implement，使用者每次都說「好／都加／做完」——看起來方向對、在穩定交付。
- **實際發生**：20 個 spec 之後，使用者說「這工具好像沒幫到我，需求都沒被打到」，且坦承**從沒
  自己打開過它**。回頭看：我一直**提案、他一直批准**，但「點頭同意」≠「需求被打到」。我被
  「和概念自洽」＋「流程有進度」的雙重舒適牽著走，一路加**下游 KB 深度**（場、關聯、根因、來源
  推薦），卻沒先證明上游最基本的價值——結果全是沒人去開的目的地。
- **解決方式**：停止提功能，**從使用者真實的一天重新推導**——問「上週你自己開過它嗎」（答：沒有）、
  「哪個時刻你會冒出需求」。一問就定位到真需求（當下、手機、反逢迎），且判明先前方向是被優雅
  帶偏。捕捉成 re-route draft（[draft/2026-07-28-反逢迎的當下副手.md](draft/2026-07-28-反逢迎的當下副手.md)）。
- **教訓**：**「使用者批准提案」是最危險的偽訊號**——它讓「自洽且有進度」冒充「有用」。真正的
  驗收訊號只有一個：**使用者會不會在沒人要求時，自己伸手用它。** 每隔幾輪就用它校準；**別讓
  設計的優雅或流程的順暢代替「打到需求」的證據**。動手前先問「這改變使用者真實動線裡的什麼」。
- **如何應用（解方，2026-07-28 實證）**：上面是**診斷**；解方是**大賭注/轉向前，先跑最便宜的手動
  探針驗「真實有用」，過了才 promote＋蓋**。做法：把功能拆成獨立的賭注（如「這份綜合有沒有幫到你」
  vs「你會不會在手機上伸手」），**用手動 dry-run 驗最核心那個賭注、零 build**——探針同時會**撞出
  真實實作風險**（光靠批准永遠不會浮現）。實證：spec 021 前對 Claude Opus 5 手動跑一次「反逢迎綜合」，
  使用者答「有用」＋撞出兩個真風險（伺服器抓被擋、query 品質），**才** promote。手動探針＝可執行規格。
  接上 principle 6（過度擬合檢查：蓋最小一塊撞現實）。出處：`history/056`/`057`、[draft/2026-07-28-反逢迎的當下副手.md](draft/2026-07-28-反逢迎的當下副手.md)。
- **來源**：[draft/2026-07-28-反逢迎的當下副手.md](draft/2026-07-28-反逢迎的當下副手.md)（2026-07-28 診斷對話）

### 內部概念詞彙別洩漏到產品對外表面

- **理論說**：把 knowie／concept 的詞彙（場、冊封、根因、grounded、derived、場-增量）直接用在使用者
  對話與介面裡——覺得精準、自洽、與整個專案模型一致。
- **實際發生**：使用者實際開 `/chat` 用了，回饋「別一直口口聲聲說『冊封』，不了解這專案的人會覺得
  莫名其妙」。而且**測試全綠、我自己審 code＋看真後端輸出時也沒察覺**——因為我泡在專案詞彙裡、
  對它免疫了。
- **解決方式**：把「**內部模型詞彙**」和「**產品對外語言**」分開——system prompt 明令輸出用自然口語、
  不用內部術語、不貼「**grounded**」這種標籤；**行為一字不改**（分把握程度／分「能證明-觀察到-只是類比」
  ／攔過度抽象／建議存但人決定），只換表達。使用者可見文案（導覽、按鈕、提示）同步 de-jargon。
- **教訓**：概念詞彙是給**模型／內部設計**用的，**不是給使用者看的**；對外表面一律用一般人看得懂的話。
  且「詞彙洩漏」這種瑕疵**我對它免疫（泡在裡面）、測試也照不出**——**只有真實使用者的眼睛照得出來**。
  這是「提案-批准 ≠ 打到需求」的解方在 UX 上的延伸：**真實使用才是驗收**，連用詞都一樣。
- **深化（2026-08-03，第二次冷讀）**：這不只是「黑話」，是**「路徑依賴的語言」——任何「只因你走過那段
  討論才覺得自然」的詞**（根因/由來/落點/佐證/暫存…）。使用者：「不是有經過我們的討論，會覺得這詞怪怪的、
  彆扭、不是平常會說的。」**免疫比想的更深**——連我（AI）都把「佐證」自評成「勉強可留」，是**使用者再冷讀
  一次才抓到**。→ 兩個更硬的點：(1) **修法＝內外分家**：`knowledge/` 概念名＋碼（`why_nodes`/`anoint`）**不動**，
  只改**使用者看得到的字**（根因→核心理解、冊封→精選、佐證→來源）——**不是把概念改笨，是內外分層**；
  (2) **建造者（含 AI）無法自審「自不自然」**，必得靠一雙**沒被討論汙染的眼睛冷讀**——所以流程上要**主動找
  使用者冷讀產品表面**，別等自己發現（自己永遠不會）。
- **來源**：commit `0583b65`、`specs/022-field-chat/`（spec 022 de-jargon，2026-07-29）；根因→核心理解/佐證→來源
  re-language（2026-08-03，使用者冷讀回饋）。

### 引擎好 ≠ 收料好（產物累積面的漏）

- **理論說**：`/chat`（引擎）能幫使用者深長推導、逐段冊封根因；spec 023 的存檔（收料）人閘門、選擇性、
  預設流走——測試全綠、單輪流程都對，收料應該也沒問題。
- **實際發生**：審使用者自己存的 19 段對話／24 根因照出兩個漏——① 同一段對話因「每冊封一條就連同存一次」
  被**複製了 15 份**（打臉「不囤積」）；② 根因收到第 32 句就停、對話卻聊到第 70 句，**最原創的尾段沒被蒸餾**。
  引擎面很好（15 條根因是真蒸餾），漏全在**下游收料**：去重／收尾／命名跟不上，金子被埋。
- **解決方式**：#1 `save_conversation` 依內容指紋冪等（同段回既有、連結改存 why_node 側，多對一）；
  #2 純函式 `distill_gap`＋只提醒不自動收的「尾段未收」提醒。（#3 命名/章節切分待議。）
- **教訓**：「單輪功能對」＋「測試綠」**不保證產物累積衛生**——**跨多次操作、人閘門之後的累積**（重複、
  半途而廢、命名凍住）是另一層，測試與單輪流程都照不出。是「真實使用才是驗收」在**產物累積面**的新投影。
  **反囤積要在每個收料層都做**：後來「整理→精選」也復發同構的重複（候選沒去重→收進同一條兩則），解＝
  正規化去重的**縱深防禦三道**（解析同次去重／整理標「已收」／精選冪等），最後一道保證庫裡不重複（`history/070`）。
- **來源**：[history/064-對話收料的漏完成.md](history/064-對話收料的漏完成.md)、`specs/025-capture-hygiene/`、commit `d0d8ec4`；復發＝`history/070`。

### 要停留在脈絡的操作，別用整頁重載（原地 AJAX）

- **理論說**：整理是 POST→回一頁；只要把對話內容一起帶回、重新渲染，使用者就在原地，沒差。
- **實際發生**：使用者說「整理完會跳回主頁」。其實對話內容有保留（messages=hist），但**整頁重載**讓卷軸彈回頂、
  串流狀態重建、候選出現在別的位置——**體感上就是被丟出正在聊的脈絡**。「內容有保留」≠「脈絡有保留」。
- **解決方式**：整條整理→精選改**原地 AJAX**（`?as=json` 回資料、client 就地渲染），全程不 navigate；無 JS 才走
  `<noscript>` 整頁 fallback。
- **教訓**：**要讓人停在當下脈絡的操作，別用整頁重載**——即使資料無損，scroll/焦點/動態狀態的重建本身就是
  「跳走」的體感。這是「真實使用才是驗收」又一次：只有真的在聊的人，才分得出「內容保留」和「脈絡保留」的差別。
- **來源**：[history/070-整理去重與原地精選.md](history/070-整理去重與原地精選.md)；使用者 2026-08-04「收完會跳回主頁，我不要這樣」。

### 主動審計既有產物 ＝ 最強的照妖鏡（別只等「用一用照出」）

- **理論說**：真實使用會照出瑕疵——所以讓使用者去用、等他回饋就好。
- **實際發生**：上面兩個漏**不是**使用者「用一用」自己撞出來的，是**使用者請 AI 去讀他存的東西**、
  我把 19 段對話／24 根因攤成數據（每段輪數、問句序列、根因落點）才照出的。被動等回饋，這種**累積型**
  的漏（囤積、收尾缺口）使用者自己很難察覺——它不在「當下這一步」，在「累了很多步之後的全貌」。
- **解決方式**：把「**主動審計既有產物**」當成一種例行——像 `knowie-judge` 之於知識庫那樣，對**使用者的場**
  也定期攤數據體檢（長度分佈、重複、收尾缺口、命名鮮度）。
- **教訓**：真實使用是照妖鏡，但**被動等回饋只照得出「當下步」的瑕疵**；**累積型**的漏要靠**主動攤開既有
  產物的數據**才照得出。審計 ≠ 等回饋，是另一種、且更早的照法。
- **來源**：[history/064-對話收料的漏完成.md](history/064-對話收料的漏完成.md)；使用者 2026-07-29「你去看看我現在聊的」審計請求。

### 「每個 X 都不一樣」→ 先找「X 藏在少數標準載體裡」（按載體不按實例）

- **理論說**：不同網站的內容/數學格式各異，要支援就得**一站一個處理器**（知乎、Medium、Wikipedia…）＝無限跑步機。
- **實際發生**：修「貼上知乎缺數學」時，讀真剪貼簿發現——**LaTeX 好端端在複製的 HTML 裡，只是躲在標準載體之一**：
  `data-tex`（知乎）、`<annotation encoding="application/x-tex">`（KaTeX/MathML 標準）、`<script type="math/tex">`
  （MathJax v2）、公式圖 `alt`/`?tex=`（Wikipedia 等）。**全網就那四五種載體，不是無限種。** 圖片（懶載 `data-*`）、
  雜訊（`nav`/`footer`/`aria-hidden`）同理——都是標準 pattern。
- **解決方式**：**按「標準載體」抽取、不按站**（一次寫、covers 大半個網路）；長尾（奇葩站）交給**兩層 fallback**：
  LLM 清理 ＋ 貼上框手動編輯。三層架構會收斂，不隨網站數膨脹。
- **教訓**：碰到「每個 X 都不一樣、要不要一個一個處理」時，先問「**X 是不是其實藏在少數標準載體裡？**」——
  按載體抽取，把「無限特例」收斂成「有限泛化」；再配 fallback 接長尾，避免 per-instance 跑步機（過度擬合檢查）。
  這也是**真實使用才驗收**（真貼知乎才照出數學躲在 `data-tex`）＋收斂紀律的合流。
- **來源**：[history/072-來源管理與rich-paste完成.md](history/072-來源管理與rich-paste完成.md)（數學缺字修復串）；`src/knowfield/ingest/web.py` 的載體抽取；
  使用者 2026-08-04「這件事可以泛化嗎？」。

### 進料層真正的 job：接住脈絡讓人敢關分頁（不是建語料）——捕捉品質＝敢放下的信任

- **理論說**：收進＝為 `/chat` 建 RAG 語料；把內容存好就對了。
- **實際發生**：使用者揭露真動機——**「看到好網站就開很多分頁、不敢關，因為那有我的脈絡；要記錄下來才敢關。」**
  分頁＝外部化的脈絡；不敢關＝怕脈絡消失。工具真正的 job 是「**一個可信的地方，讓人卸下脈絡、放心關分頁**」，
  不是多一個文章庫。這也回頭解釋：前面拼命修數學/圖片/標題/去框**不是龜毛，是在建「信任」**——捕捉品質爛→
  不敢放手→繼續囤分頁。**收進原因/脈絡欄因此是皇冠、不是選填配角**（我一度誤判成 gold-plating，修正）。
- **解決方式**：① 摩擦極小（一次關十個分頁→每個「一鍵＋一句 why」；剪貼簿一鍵、自動標題/日期都服務此）。
  ② **反囤積界線**：別把「囤分頁」變成「囤知識庫」（無底收件匣＝把囤積搬家、底層焦慮沒解）。用產品自身哲學
  （captured≠committed／預設流走，spec 028 暫存衰減同精神）：**解脫在「放下」不在「永久典藏」——安心卸載＋
  誠實衰減**（大多流走是健康的，真回頭用到的才複利）。
- **教訓**：問「工具的 job 是什麼」比「功能對不對」更根本——**進料層的 job 是接住脈絡讓人敢放手，不是建語料**。
  由此：(a) 捕捉品質是「敢放下的信任前提」，值得投資到「夠信任」為止（非無限打磨）；(b) 幫人放下囤積的工具，
  自己**絕不能變成新的囤積**——要配「預設流走」。呼應原則 6 反囤積、「有吸引子的場」預設衰減。
- **來源**：使用者 2026-08-04「不敢關分頁是因為那有我的脈絡…這工具剛好適合做這件事」；[draft/2026-08-04-進料轉檔選型.md](draft/2026-08-04-進料轉檔選型.md)。

### 有結構化來源時，解析 > 辨識

- **理論說**：論文進料走 Mistral OCR（PDF→markdown）一次搞定，統一路徑最省事。
- **實際發生**：arxiv OCR 版數學是「看圖辨識 LaTeX」，密集下標/符號會猜錯；且 OCR 端點連圖都吐不出來。
  改走 **arxiv HTML 版**——它的數學是**作者原始 LaTeX（source）**、figure 是真 `<img>`，一次全對。
- **教訓**：**有結構化來源（HTML/source/API 欄位）就別讓 AI 去「辨識」**——解析是確定性、可重現；辨識再準也是猜，
  對承重內容（數學/符號/程式碼）尤其。取捨順序：**結構化 source > 解析 > 辨識**；辨識只在拿不到 source 時（掃描件、無 HTML 版）當退路。→ arxiv 定 `HTML → ar5iv → PDF-OCR` fallback（`history/081`）。
- **來源**：[history/081-來源進料品質-arxiv路線與數學圖標題.md](history/081-來源進料品質-arxiv路線與數學圖標題.md)；commits `f3e3fa9`／`0839609`。

### 確定性修承重內容 > 丟 AI「整理」

- **理論說**：來源結構有雜訊（標題分錯層次、隱形字元）→ 仿「貼上」丟給 AI 整理最省力。
- **實際發生**：貼上的 `clean_markdown` 鐵律本就是「只剝雜訊、逐字保留、不改寫」（守溯源）；但對 URL/PDF ①已結構抽取過、
  效益邊際 ②**AI 碰密集 LaTeX 極易砸壞剛用四層 bug 修好的數學**（承重內容）③成本＋損溯源。
- **教訓**：**結構性問題用確定性規則修**（標題層次重映射、清控制字元），**別把承重內容交給 AI「整理」**——
  AI「逐字」對數學是最弱保證、卻是最要命的地方。呼應反逢迎的膜（AI 不亂改冊封物）＋捕捉鐵律。AI 只在**真髒的貼上頁**選用清理（預設關）。
- **來源**：`history/081`；commit `70a5d8d`；[draft/2026-08-04-進料轉檔選型.md](draft/2026-08-04-進料轉檔選型.md)（貼上 clean 鐵律）。

### CJK 輸入法組字中的 Enter 不該送出（isComposing）

- **理論說**：Enter-送出的輸入框，`onKeyDown` 判 `e.key === "Enter"` 就送，直覺又乾淨。
- **實際發生**：中文（日文/韓文同理）輸入法**組字中**按 Enter 是**確認選字**，卻被當成送出——使用者選字選到一半、
  文章主題還沒打完就被送出去生成。這對非 CJK 開發直覺是隱形的坑（英文沒有組字階段）。
- **解決方式**：`onKeyDown` 加 `!e.nativeEvent.isComposing`（＋`e.keyCode !== 229` 給舊瀏覽器 fallback）——
  **組字中的 Enter 一律放行給輸入法、不 preventDefault、不觸發送出**；組字結束後的 Enter 才送。
- **教訓**：**任何 Enter-送出的輸入框，CJK app 必須擋 `isComposing`**——這是會反覆重犯的坑（每新增一個輸入框

### 驗證 DB 寫入要跨連線——單連線 smoke 會假綠

- **理論說**：把資料層從 SQLite 遷到 PG，寫個 smoke test 建 Repository、塞資料、讀回來，過了就代表 port 對。
- **實際發生**：port 時把 `add_why_node`/`save_article` 收斂成 `return self._insert_id(...)`，**不小心把
  `commit()` 掉了**。smoke test 在**同一個連線**塞完立刻讀——PG 未提交的資料在**同連線內可見**，所以 smoke 全綠、
  假象「port 正確」。真正的 API 場景是「請求端連線寫、另一端連線讀」，跨連線讀不到未提交資料 → 候選數 0，整套測試才露餡。
- **解決方式**：port 後**跑完整測試套件**（它天然跨連線：API 一個 Repository 寫、測試另開 Repository 讀）；
  smoke test 不足以驗 DB 層。補回 `add_why_node`/`save_article` 的 `commit()`。
- **教訓**：**PG（非 autocommit）每個寫入路徑都要顯式 commit**；而**驗證寫入必須跨連線**——單連線的「塞了又讀到」
  是最會騙人的假綠（未提交也讀得到）。呼應本專案骨幹「答案對到 ground truth、別信自報的綠」。
- **相關**：與「驗證要走與正式路徑完全相同的管線」同族——那條是管線步驟差異造成**假紅**，這條是連線邊界差異造成**假綠**。
- **來源**：[history/084-全部PG-資料層遷移定案.md](history/084-全部PG-資料層遷移定案.md)；commit `e7dcbec`；`specs/034-postgres-migration/`。

### 具體路由要註冊在 catch-all mount 之前，否則被吃掉

- **理論說**：加登入的 `/auth/login|callback` 路由，寫在 `create_app` 裡就會生效。
- **實際發生**：SPA 用 `app.mount("/", …)` 當 catch-all（非檔案 fallback index.html）。新 `/auth/*` 路由註冊在**它之後**
  → 「/」catch-all 先比對到、把 `/auth/callback` 也吃掉 → callback 沒跑、session 沒建。詭異的是**擋人有效、登入無效**
  （gate middleware 在路由層之前所以擋得住，但要跑的 /auth 路由被 mount 遮蔽）→ 測試現象「登入後仍 401、Set-Cookie 空」。
- **解決方式**：把 `/auth` 路由（`setup_auth`）移到 SPA `mount("/")` **之前**。
- **教訓**：**catch-all（`mount("/")`／萬用路由）永遠放最後**；任何具體路由都要在它之前註冊，否則靜默被吞。
  debug 訊號：「middleware 攔截正常、但具體 handler 沒被呼叫」≈ 路由被更早的 catch-all 比對走了。
- **來源**：[history/085-單人Google登入門鎖.md](history/085-單人Google登入門鎖.md)；commit `d11b5e0`；`src/knowfield/web/app.py`（setup_auth 順序）。

### 測試不能讀開發者本機 .env——會撈到真實設定、汙染測試

- **理論說**：`Config.from_env` 讀 `.env` 很方便，測試也用它建 app 就好。
- **實際發生**：使用者填好 `.env`（含真實 Google 登入 auth 設定）後，跑測試——`from_env` 的 `load_dotenv(".env")`

### prod 部署是另一個環境——這些差異本地/測試照不到，逐一驗

- **理論說**：本地跑得起、測試全綠，push 上去就會動。
- **實際發生（首次上 k3s 一次踩四個，`history/087`）**：全部是**上 prod 才炸、本地/測試看不到**的環境差異——
  ① **映像平台**：Mac build 出 arm64、節點 amd64 → `no match for platform`。② **執行期 vs 測試相依**：`httpx` 只在 test

  → OAuth redirect_uri 組成內部 http → `redirect_uri_mismatch`。④ **惰性初始化**：`init_db` 首次碰 DB 才建 schema
  → 遷移/探針時撲空。
- **解決方式**：各自對症（`buildx --platform`、httpx 進 runtime deps、`--proxy-headers`、遷移前先 init_db）。
- **教訓**：**「本地綠 ≠ prod 綠」，部署是新環境，差異要當 checklist 逐項實測**——
  (a) **映像平台**對上節點架構；(b) **執行期相依**別靠測試環境剛好有（庫的 runtime import 要進 runtime deps，不是 dev extra）；
  (c) **反向代理**：scheme/host 靠 `--proxy-headers`＋Host 透傳，OAuth/絕對 URL 才對；(d) **惰性初始化**：schema/種子若
  lazy，遷移或探針要先觸發。呼應「別信自報的綠」——**測綠只證本地那個環境**。

### upsert 綁「實體 id」，別綁「狀態旗標」

- **理論說**：autosave 只該碰暫存對話（保護人存的永久對話不被自動改），所以 `UPDATE … WHERE id=? AND temporary=1`。
- **實際發生**：接回**已存檔（永久）**對話繼續聊 → 那句 UPDATE 因 `temporary=1` 不成立 → 落到 INSERT → **另開一筆暫存**
  （＝「繼續聊跑到暫存」「promote 後又冒暫存」的同一根因）。狀態旗標把「同一段對話」的 upsert 給拆了。
- **解決方式**：upsert 以**實體 id** 為鍵（`WHERE id=?`）、就地更新、保留其狀態；只有「查無 id」才新建。
- **教訓**：**upsert/更新要綁不變的實體識別（id），別綁會變的狀態旗標**——否則狀態一翻，同一實體就分岔成兩筆。
  想「保護永久不被亂改」要用權限/來源區分，不是把 upsert 的鍵綁在狀態上。
- **來源**：`history/088`；commit `7a97b48`；`repository.autosave_temporary`、`ChatPage.tsx`。

### 前端互動：桌面開發的直覺照不到手機/真實使用

- **實際發生（上線後一次踩三個，`history/088`）**：① **hover-gated 控制項在手機隱形**——⋮ 用 `opacity-0 group-hover`，

  「點不下去」。③ **送出訊息沒即時回饋**——使用者那句等回答完才出現（樂觀更新缺失）。
- **解決方式**：① 觸控裝置控制項**常駐可見**＋**長按**當替代手勢；② 彈出層 **portal 到 body＋fixed 定位**（脫離 overflow 容器）、

### 上線後維運：遷移要含 DB 以外的檔案；別在使用者線上用時部署

- **理論說**：把 DB 遷過去、服務起來就完成上線了。
- **實際發生（`history/087`/`088`）**：① 只遷 DB、**漏搬 media/（圖片、PDF）** → 使用者看到「資訊不見了」（破圖/無預覽）。

### 部署要核對「pod 實際 digest」——別信「rollout 成功」（push 會靜默失敗）

- **理論說**：改碼→`buildx --push`→`rollout restart`→`healthz 200`，每步成功就是上線了。
- **實際發生（燒掉一小時，`history/089`）**：連續數次全綠，但線上**完全沒更新**——`docker login ghcr.io` 的 **token 過期**，
  `buildx --push` 於是 **build 成功、push 靜默失敗**（結尾無 `pushing manifest done`，但整體 exit 0 不明顯），
  rollout 每次拉到**同一個舊 digest**、還回報「successfully rolled out」。一路被騙，以為是各種功能 bug。
- **解決方式**：① 部署後**核對 `kubectl get pod -o jsonpath=…imageID` 的 digest ＝ 這次 build 的 digest**（或在 pod 內
  驗一個新碼才有的符號）；② 用 **git sha 當唯一不可變 tag**（`:latest` 被覆蓋看不出新舊、還可能拉到 stale）；
  ③ token 會過期 → 部署前重登 registry。
- **教訓**：**CD 每一步的「成功」都可能是假的——要驗『線上實際跑的版本』這個 ground truth，不是驗『我以為推了』**。
  尤其 `latest` tag＋mutable registry＋快取，三重不透明。呼應「別信自報的綠」的部署版：**驗 digest，不驗 log**。
- **來源**：`history/089`；`deploy/README`；症狀＝pod imageID 一小時不變、`Config.from_env().chat_max_tokens` AttributeError。

### 手機/SOTA 排版：閱讀內容全寬無框，可點項才用卡片

### 「大部分正常、有時跳走」＝時機競態；修法是驗結果、不是驗「我觸發過」

- **理論說**：MathJax 渲染在內容更新後排一次 debounce typeset 就夠了——呼叫過就會渲染。
- **實際發生**：數學**偶爾**卡成 raw LaTeX，重整就好、難重現。根因是 DOM **陸續晚到**（MathJax 還在載／
  圖片 reflow／串流換節點／長對話陸續 mount），晚到的節點在那次 typeset **之後**才進 DOM；而全域 timer
  又被別處 `clearTimeout` 取消 → 沒有第二次機會。「偶發」不是難重現的小毛病，是**競態的診斷簽名**。
- **解決方式**：typeset 後**查 DOM 有沒有漏網**（`.mathcopy:not([data-typeset])`），有就 400ms 後再跑、
  最多 4 次。成立前提＝**`typesetPromise` 對已渲染是 no-op ⇒ 冪等才敢重試**。
- **教訓**：① 症狀「大部分正常、有時不對」→ 先當**競態**查（誰晚到、誰把重試取消了），別當隨機。
  ② 更通用的骨幹：**驗結果，別驗「我做了那個動作」**——這是本專案第三次撞到同一面：
  跨連線驗 DB 寫入（`history/084`，單連線讀得到未提交＝假綠）、驗 pod 實際 digest 而非 rollout log
  （`history/089`，push 靜默失敗）、驗 DOM 實際渲染而非「我呼叫過 typeset」（本條）。
  ③ 敢用「收斂式重試」的前置條件是**操作冪等**；不冪等就別重跑，要改用一次性正確。
- **來源**：`history/091`；commit `7aaa310`；`frontend/src/components/Markdown.tsx`。

### 沒人用的功能，先問「是不是搞錯了維度」再砍——膜（判準）與場（脈絡）是正交的

- **理論說**：原則 6 說「自由發散、把關只在膜」，`concepts/有吸引子的場` 說三態有「沙盒」——
  那產品上就給一顆「🧠 腦力激盪」toggle，開了更放得開、不撒網，讓使用者能進沙盒。概念自洽、實作乾淨。
- **實際發生**：**沒人用**（連使用者自己都沒按過）。追問「它想解什麼」才發現：它放寬的是**膜**，
  而膜正是使用者當初說「會一直不斷想使用」的唯一理由——**做一顆「讓工具比較不誠實」的開關等於自廢武功**。
  且膜本來就不壓制發散（自由是**預設**，不是要申請的模式），所以那顆按鈕在解一個不存在的問題。
- **解決方式**：不是砍掉了事，而是換維度重做——**保留膜、可關的是場**：`bare` 模式（🔌 不接知識庫）
  這輪不注入核心理解、不撒網、不查收藏，但**反逢迎人格照舊**（守衛測斷言 system 仍含「好聽話」）。
  真需求是「問跟我的場無關的事時，注入 24 條核心理解只是雜訊、還讓答案硬要攀親帶故」。
- **教訓**：**一個沒人用的功能，多半不是需求不存在，是把旋鈕裝在錯的軸上**——砍之前先問「它想解的需求是什麼、
  正確的維度是哪一條」，否則連同那個 reframe 一起丟掉。這次拆出來的正交軸：
  **膜＝判準／人格（永不可關，關了就沒有這個產品）** vs **場＝脈絡／內容（可按需關）**——
  原本綁在 `build_field_system_prompt` 裡沒分開過。
  ＋原則 6 的讀法變精準：**「把關只在膜」≠「一定要接場」**。
  ＋「真實使用才是驗收」的新一面：它照得出的不只是**缺**什麼，還有**多**了什麼（該退場的）。
- **來源**：`history/090`；commit `988cdd2`；`src/knowfield/chat/field_chat.py`（`_BARE_NOTE`）、
  `tests/unit/test_field_chat.py::TestBareMode`。

### 找不到「推手」時，先問「是不是根本沒人設限」——用自家概念寫成的假設最像真的

- **理論說**：使用者說「AI 回答太長、理解有負擔」→ 一定有東西在**把它推長**，找出來拿掉就好。我提了兩個
  假設，**都用專案自己的概念寫成**，所以聽起來很像洞見：① 34 條核心理解**全量注入**（實測 system prompt
  10,613 字）把回答撐長——還附了個漂亮觀察「收進資料走檢索 top-k、核心理解走全量灌，**同一個 prompt 裡
  兩套標準**」；② 膜的 **8 條編號指令**被模型**逐條表演**給使用者看（＝「品質準則列成檢查表」那條的背面）。
- **實際發生**：4 次 API 呼叫**把兩個假設全部推翻**。場注入：接場 2,941 字 vs 不接 3,157 字（**接場反而略短**，
  差距在雜訊等級）；膜：**無 system 3,000 字** > 現況膜 2,732 字（**膜不但沒推長，還壓了一點**）。
  真因是模型對技術題的預設就是長篇，而**膜從頭到尾沒有一句提到長度**——**不是有東西在推長，是從來沒有人叫它短。**
  加一句「長度紀律」：2,732→**447** 字；走真路徑（接場＋長度紀律）2,941→**553** 字（−81%），
  而且接場行為與膜的擋過度簡化**都還在**——短掉的是廢話，不是內容。
- **解決方式**：`_MEMBRANE` 加「長度紀律」，**逐字用實測過的那句、不潤飾**（改字＝那次實驗就不算數）；
  ＋一條測試釘住「膜必須含長度紀律」（含 bare 模式那條路），防日後改措辭時整條靜默消失。
- **教訓**：
  1. **歸因先問邊界條件**：症狀是「太長／太多／太慢」時，先問「**有沒有人設過上限**」，再去找「誰在推」。
     找加害者是預設反射，**這次答案是找缺席者**。
  2. **用專案自己的概念寫成的假設，最像真的、也最難自我證偽**——它自洽、有洞見感、還能引用既有原則背書。
     這是原則 6 的 folie à deux 在**除錯**上的投影：**反逢迎不只要對使用者，也要對自己的診斷**。
  3. **破法便宜到不像話**：4 次 API 呼叫就否掉兩個假設，省下我原本要動的「注入策略」大工程（那還帶著
     「地基本來就該一直在場」的概念張力）。**能實測就別推理**——接「手動探針驗賭注」的除錯版。
- **來源**：`history/092`；`src/knowfield/chat/field_chat.py`（`_MEMBRANE` 長度紀律）、
  `tests/unit/test_field_chat.py::TestSystemPrompt::test_has_brevity_discipline`。

### 死的知識不是靜止的知識，是沒有任何消費者會發現它錯掉的知識

- **理論說**：知識庫健不健康，看它有沒有在動——有沒有持續寫入、有沒有跟著專案更新。
- **實際發生**：本次 `/knowie-judge` 實測：**93 條 `history/` 沒有任何檔指向**、`episodes/` 100% 孤兒、
  `vision.md` 勾選比 226:6。那 93 條天天隨 commit 移動、一點都不靜止——但沒有任何取用路徑會碰到它們，
  所以**就算內容錯了也不會有人發現**。同一天使用者對「暫時對話存檔」的回報（「沒什麼意義，反而麻煩」）
  是同一件事在產品面的樣子：自動存了、也在動、也有衰減，但沒有消費者。
- **解決方式**：把「有沒有消費者」變成**可機械量測**的東西——連結一律寫成 markdown（`[[ ]]` 和反引號路徑
  推導不出圖，掃出來的孤兒率是假的），再逐層算孤兒率。修完 `history/` 孤兒 100%→26%、`draft/` 56%→7%。
- **教訓**：**判一份知識死沒死，不看它動不動，看「如果它錯了，誰會發現」**。沒有那個誰，寫得再勤都是死的。
- **不適用的時候**：有 oracle 的那一半（code、schema、測試）不吃這條——編譯器和測試就是它們的消費者。
  這條專講沒有 oracle 的知識。

### 否決要跟接受一樣便宜，否則增生沒有相對應的凋亡

- **怎麼撞到的**：用細胞比喻盤跨專案知識庫的失敗模式時撞到癌症那一支——**癌細胞不是特別會分裂，
  是它聽不見周圍叫它停的訊號**。回頭量自己的庫，證據就在眼前。
- **實際發生**：寫一條 `history/` 是免費的（做完順手就寫，93 條裡 30 條是「完成」型），
  而退役一條要重讀、判斷、寫理由。於是**增生有管道、凋亡沒有**：`vision.md` 累到 991 行、勾選比 37:1，
  27 份 draft 只有 2 份真的被放掉。不是產出太多，是抑制那一側從來沒建。
- **解決方式**：這次用一張里程碑索引把退役那側批次補做（991→132 行），但**那是補救不是機制**——
  下次還是會長回來，除非否決的成本降到跟接受一樣。
- **教訓**：**看一個系統會不會失控，不要數它產出多快，要比「加一個」和「退一個」的成本差**。
  差得越多，垃圾累積得越穩定，而且看起來都像產能。
- **不適用的時候**：**不可逆**的否決（刪掉唯一副本、砍掉沒備份的資料）不該便宜。這條講的是可逆的那種

### 自動化只移走製造成本，沒移走呈現成本——自動又可見的東西不是零成本

- **理論說**：暫時存檔改成**自動**（每輪 upsert、閒置 7 天自動刪，spec 028 / 階段 23），
  人工負擔就消失了。閘門不存在，就不會有摩擦。
- **實際發生**：使用者真實用過之後回報「**實際用起來沒什麼意義，反而會覺得麻煩**」。
  閘門確實不存在，麻煩卻在——因為它進了 `/conversations` 主清單，跟永久存檔混在一起、
  還帶著首句截斷的便宜標題。**省下的是「決定要不要存」，付出的是每次找東西都要先撥開一堆不打算留的。**
  7 天 TTL 又卡在最壞的位置：太短，救不到階段 18 要解的「半年後回看根因」；夠長，足以把清單塞滿。
- **解決方式**：⚠️ **尚未定案**——診斷是旋鈕裝在「存活期限（暫時/永久）」這條軸上，
  該裝的是「**可見性**（要不要出現在你面前）」；同樣自動存、同樣衰減，但不進主清單。
  砍或改的判準見 [draft/2026-08-18-暫存的真實使用回報與連接密度.md](draft/2026-08-18-暫存的真實使用回報與連接密度.md) 的誠實測試。
- **教訓**：**把一件事自動化，只移走了它的製造成本；只要它還出現在你每天要看的地方，呈現成本原封不動。**
  autosave 的價值在它隱形——一旦可見，它就從保險變成雜訊。
- **不適用的時候**：需要人在當下知情的東西不能隱形（隱形＝偷偷替人做決定）。這條只適用於
  「先全存、之後再判斷」這類延後決策的東西。

### 驗證要走與正式路徑完全相同的管線，否則照出來的是驗證腳本的 bug

- **怎麼撞到的**：簡→繁功能寫完，要對真實來源（知乎 Flow Matching，50 塊）做端到端驗證。
  我用 `"\n\n".join(chunks)` 把塊拼回來——看起來跟正式路徑等價。
- **實際發生**：驗證報告顯示「正文有簡體字沒轉到」。追下去發現殘留的 `这`／`变换` 被吞進了
  行內數學的保護區。再追：`chunk_markdown` 有 40 字元 overlap，`join` 沒去重疊，
  於是第二塊從**數學式中間**開始（`t\{ f_i \right\}$`），`$` 總數變成奇數、配對錯位，
  把一段正文當成公式保護起來。**換成正式路徑用的 `stitch_chunks` 之後，`$` 是偶數（322），
  殘留歸零、161 個行內數學全數保留。**——實作從頭到尾都是對的，錯的是我的驗證腳本。
- **解決方式**：驗證一律呼叫**與正式路徑相同的函式**（這裡是 `stitch_chunks`），
  不自己重寫一個「應該等價」的版本。差一個函式，照出來的就是另一個系統。
- **教訓**：**一個與正式路徑不同的驗證管線，量到的不是正式路徑**。它的失敗訊號指向它自己，
  而你會拿去改實作——那才是真正的代價：不是白花時間，是**照著假訊號改對的東西**。
- **同一個根，後來又撞到兩次（2026-08-18 同日）**：

     **永遠匹配不到**。舊 server 續佔 port、新的起不來就默默退出，而我以為在看新版，
     驗證出來的三個「修正沒生效」全是舊碼跑的。⇒ **一個沒被確認過的停止指令等於沒有停止**；
     重啟後要 `ps aux | grep -c` 確認是 0。
  2. 那條壞掉的 `pkill` **就寫在我自己剛建的 skill 裡**——照著它做才炸出來。
     ⇒ 一份沒有被**照字面執行過**的操作文件，等於還沒被驗證。
  3. **前端型別檢查用錯指令**（2026-08-21，這次一路燒到 CI）：我用 `npx tsc --noEmit` 驗，

     `tsc --noEmit` vs `tsc -b`。**每一次我都以為自己挑的是「等價」的指令。**
- **不適用的時候**：刻意要隔離某一層來定位問題時（單元測試、二分法除錯），差異是**目的**不是缺陷。
  這條講的是「宣稱驗證了端到端」的那種驗證。

  這條是**管線步驟**差異造成假紅。同一個根：**驗證環境與正式環境的任何差異，都會變成假訊號**。

### 一個「先探針再建」的閘門，價值不在它放行的時候，在它擋下來的時候

- **理論說**：需求形狀從使用者的用詞就推得出來。他說「希望可以**對照**」，那要的就是並置——
  這個推論還很漂亮：「『對照』兩個字就是證據：要的不是替換，是並置。」整套設計（逐塊並置、
  複用切塊當對齊單位、階段名叫「翻譯**與對照**」）都從它長出來。
- **實際發生**：設計源自己對這個推論不放心，在出口寫了「**賭注過了才 promote**」——要求先做一次
  零 build 的手工對照給使用者看。今天把賭注攤開（他自己收進的來源、產品既有的切塊、真的翻譯、
  數學保護 34/34），他看完的答覆是「**全文翻譯**」。**那個漂亮的推論是錯的。**
- **解決方式**：整條轉移記進 `history/095`，把 draft 那句 reframe 標為已推翻並列出連帶失效的設計，
  roadmap 項重寫。⚠️ **推論錯了但不是全錯**——原文為真相、承重保護、標 AI 翻譯這幾條仍成立，
  逐項標「推翻／保留」比整篇作廢誠實，也讓下一個人知道哪些還能用。
- **教訓**：**從使用者的用詞反推出來的需求形狀，是假設不是證據**——他描述的是他當下能想到的解法，
  不是他要解的問題。判準：**這個設計的地基，是使用者驗過的，還是我從他一句話推出來的？
  後者 → 先花最小的成本讓他看到實物再說**。而一個擋下來的閘門**沒有可見的產出**，
  所以最容易被當成多餘的流程砍掉——它的價值恰好是那個沒有被蓋出來的錯東西。
- **不適用的時候**：可逆且便宜的東西不必先探針（做了不對就改）。這條針對的是**會長出一整套介面**
  的設計前提——蓋下去才發現方向錯，成本在介面不在邏輯。
- **相關**：與「提案-批准迴圈 ≠ 打到需求」同族——那條講**批准 ≠ 打到**，這條講**用詞 ≠ 需求**，
  同一個根：使用者說的話不等於使用者要的東西，而中間那段要用實物去接。

### 一條沒有被錯誤實作撞過的測試，不知道自己在測什麼

- **怎麼撞到的**：spec 038 的即時進度（FR-003）。初版實作把進度累積起來、全部翻完才一次吐出

      v2  驗「第一個事件是不是 stage」    → 綠（順序對、時機錯）

  前者只證明測試會執行，後者才證明它在測東西。判準：**我能不能寫出一個通過這條測試、
  但明顯是錯的實作？寫得出來 → 這條測試還沒完成。**
- **不適用的時候**：純資料轉換的往返不變式（`restore(*mask(t)) == t`）本身就是強斷言，

- ⚠️ **第三種失敗：攻擊打錯地方。** 同一份程式碼常有兩條相似路徑

- ⚠️ **第二種失敗：攻擊本身是 no-op。** 撞不紅有兩種原因——測試沒牙齒，

  ⇒ **撞不紅時，先確認攻擊真的改變了產物**，再去懷疑測試。
- **相關**：與「驗證要走與正式路徑完全相同的管線」同族——那條是驗證**管線**沒接地，
  這條是驗證**斷言**沒接地。同一個根：一個沒被挑戰過的驗證，量到的是它自己。

### 切塊的用途決定了合法的切點——換了用途就要重切

- **理論說**：這篇文章已經被 `chunk_markdown` 切好了（給檢索用），翻譯直接沿用那些塊就好，
  省事又一致。
- **實際發生**：畫面上出現「條件式 **Generat**」和落單的「**離子**」。追下去有兩層：
  1. `stitch_chunks` 靠**精確字串比對**去除塊間 40 字元重疊——那對原文成立，但每塊
     **獨立翻譯**後重疊段會翻成不同中文、比對失敗，兩份都留下（殘影）。
  2. 更深的一層：`chunk_markdown` 會**從單字中間切**（實測 124 個接縫有 **55 個**是）。
     `Conditioned Generation` 被切成 `Conditioned Generat` ＋ `ion`，後者獨立翻譯成「離子」。
- **解決方式**：不再重用檢索塊。先拼回全文，再用 `split_units` 切成**翻譯單位**
  ——切在段落邊界，過長段落退而切在空白處，**絕不從單字中間切**，且重組逐字還原。
- **教訓**：**同一份切塊在不同用途下有不同的「合法切點」**。檢索容得下切在字中間
  （embedding 照樣算）、容得下重疊（提高召回）；翻譯兩者都致命，因為每塊會被當成
  **完整的一段話**獨立處理。判準：**沿用既有切塊之前，先問「新用途對切點的要求，
  和舊用途一樣嗎」**——不一樣就得重切，省下的那點事會在接縫上加倍還回來。
- **不適用的時候**：新用途對切點**更寬鬆**時（例如只是計字數）當然可以沿用。
  這條防的是「更嚴格卻沿用」。
- **相關**：與「驗證要走與正式路徑完全相同的管線」是同一天的兩面——那條是我用
  `join` 代替 `stitch_chunks` 而量錯，這條是我沿用 `chunk_markdown` 而做錯。
  **同一組函式，一次用錯在量測、一次用錯在生產。**

### 同一個機制換一個用途，判準要跟著換——不能整套照搬

- **怎麼撞到的**：`protect.mask/restore` 這套「抽佔位→交給不可靠處理器→還原」在這個庫已經用了
  四處（SQL、OCR 圖片、簡→繁、英→繁）。要給收進時的 LLM 清理也套上時，我差點把翻譯那套
  **完整性檢查**整份搬過來：「任何佔位符不見 → 整段退回原文」。
- **實際發生**：清理的工作**本來就是刪雜訊**——它本來就會少東西。照搬翻譯的判準，
  等於任何一次成功的清理都會被判定為失敗、全部退回原文，**功能等於不存在**。
- **解決方式**：判準改成「**全部**佔位符都消失才退回」（＝模型根本沒照規則走），
  留下來的照常還原。機制相同、閾值相反。
- **教訓**：**一套機制可以複用，它的判準不行**——判準編碼的是那個用途的成功長什麼樣。
  搬機制時要問：**這個用途下，「正常」和「壞掉」的界線在哪？** 翻譯是「不該少東西」，
  清理是「本來就要少東西」，同一條規則在兩邊指向相反。
- **不適用的時候**：兩個用途的成敗定義真的相同時（例如同樣是翻譯、只換語言對）當然照搬。
- **相關**：與「切塊的用途決定了合法的切點」同源——那條是**切點**隨用途變，這條是**判準**隨用途變。
  再往上都是同一句：**複用的是機制，不是它成立的條件。**

### 一個閘門切錯軸，兩邊都會漏——切之前先問「風險住在哪一軸」

- **理論說**：要讓對話當文章的「情境」，就得擋住沒依據的東西跟著進來。我提的過濾是
  **只餵使用者自己的 turn、不餵 AI 的回覆**——理由是情境幾乎都在人的話裡，
  而把 AI 散文餵回 AI 生成正是 model collapse 那條線。聽起來兩全。
- **實際發生**：使用者一句話拆掉它——「如果只有我自己講的話，常常是沒有依據的」。
  我切的軸是「**誰講的**」，但風險住在「**有沒有依據**」那一軸，而**這兩軸正交**。
  於是兩種過濾各漏一邊：全對話漏未冊封的 AI 主張；只有人的 turn 漏未冊封的人的主張。
- **教訓**：**設計一個過濾器之前，先寫下「風險住在哪一軸」，再看你打算切的是不是同一軸。**
  不同軸就是白切——擋掉一半無辜的，放進一半有害的，而且兩邊都看不出來。
  ⓘ 這是「旋鈕裝在錯的軸上」的第三次（前兩次：膜 vs 場、存活期限 vs 可見性），
  但**時機不同**：前兩次是事後診斷沒人用的功能，這條是**設計當下**就該跑的檢查。
  ＋順帶一條：**未冊封 ≠ 中性**。對話走過 distill → 候選 → 人挑，未冊封裡有一部分是
  「提了、你看過、明確沒選」的——當情境餵回去等於把丟掉的東西從後門撿回來。
- **來源**：[draft/2026-08-21-從對話生文章.md](draft/2026-08-21-從對話生文章.md) 第三節；
  對照 `experience.md` 的「沒人用的功能，先問是不是搞錯了維度」。

### 保證分兩種：「不可能」與「可見」——把可見寫成結構性保證，是把人的注意力當成程式的保證

- **理論說**：讓對話收斂成一份 schema 放不下主張的簡報（只有「要回答的問題」「角度」
  「用哪幾條核心理解」），主張就進不來了——這是結構性保證。
- **實際發生**：schema 擋不住**偽裝成問句的主張**——「為什麼殘差**其實是**一種記憶機制？」
  就是一句夾帶。真正擋住它的不是 schema，是**人會看到這份簡報再按生成**。
- **教訓**：寫規格時要分清楚你手上是哪一種保證。**「不可能」＝程式路徑上做不到（可以測）；
  「可見」＝人有機會攔截（測不到，取決於人有沒有看）。** 把後者寫成前者，
  規格就開始說謊，而且是**最難發現的那種謊**——因為它在正常情況下看起來完全成立。
  正確寫法：關住可以關的（結構），**記下關不住的**（已知限制），不假裝全封。
  ＋設計「可見」型閘門時要壓低查驗成本：五個問句掃一眼就查得完，
  要人讀整段對話抓夾帶則不划算——**沒人負擔得起的可見性等於沒有可見性**。
- **來源**：[draft/2026-08-21-從對話生文章.md](draft/2026-08-21-從對話生文章.md) 第五節；
  同一個處理方式已用在 `specs/041-article-in-chat/spec.md` FR-003 的邊界說明。

### 一條「全有全無」的規則，顆粒度愈粗就愈不可能成立——先算 (1-p)^N 再定規則

- **理論說**：spec 039 FR-006 寫「含降級單位的翻譯結果不得被快取」——否則那次失敗會被
  固定下來，使用者永遠拿不到完整譯文。理由完全正確，我照著做成**逐文件**：全存或全不存。
- **實際發生**：真跑 45 個單位的來源，**失敗 1 個**（暫時性網路逾時）⇒ 整份不存 ⇒
  使用者要的「自動保存」**根本不會發生**。而且不是運氣：N 個單位、單位失敗率 p，
  整份可存的機率是 `(1-p)^N`，N=45、p=2% 只剩四成。
- **教訓**：**當一條規則是「全部滿足才算數」，它成立的機率隨顆粒度指數衰減。**
  定這種規則之前先估 N 和 p、算一下 `(1-p)^N`——若答案不接近 1，
  要動的不是規則本身，是**顆粒度**。把規則放到對的顆粒度上（逐單位），
  原規則的**理由**反而被更完整地滿足：失敗的永遠重試，成功的不必陪葬。
  ＋逐塊成敗要由產生它的那層**明講**（回傳 `ok` 陣列），
  **不能用「輸出 == 輸入」去猜**——純程式碼／URL 的單位翻完本來就可能一樣。
- **來源**：[history/102](history/102-譯文快取-從逐文件改為逐單位.md)；commit `6c9d367`；
  `specs/039-translation-cache/plan.md` 決策 D3。

### 日誌的 handler 掛在葉子上，就等於沒掛——沒人呼叫過設定函式的模組會整條鏈找不到 handler

- **理論說**：`logging_setup.get_logger(name)` 建好 handler 就能記錄，憲章 V 的可觀測性有著落。

### 一個機制的失敗如果是沉默的，就要另外給一條「我指定」的路——不是因為它不夠準

- **理論說**：來源已經會被撒網撈進對話（`_chat_corpus`），要「跟這份聊」再加一條路，
  聽起來只是準確度的邊際改善，YAGNI 該擋下來。
- **實際發生**：真正的差別不在準確度。**撒網沒撈到你這份時，畫面上沒有任何跡象**
  ——你會以為模型看過了，然後拿它的回答當「這篇沒提到」。人指定則沒有這種失敗模式。
- **教訓**：評估「要不要再加一條路」時，先問**既有那條的失敗是不是沉默的**。
  失敗會出聲 → 邊際改善，多半不值得；**失敗是沉默的 → 那不是準確度問題，是可信度問題**，值得。
  ＋這條同時決定驗收怎麼寫：**新路徑必須在舊路徑停用的條件下驗**，
  否則測到的是既有功能。（本刀的 SC-002 就是「撒網停用」。）
- **來源**：[history/103](history/103-來源直接對話-撒網的失敗是沉默的.md)；
  `specs/042-source-in-chat/spec.md` SC-002；commit `3aa6b46`。

### 一次「全面檢查」的完備性，上限是當時存在的路徑——新加一條就可能作廢舊結論，而它不會舉手

- **理論說**：`history/100` 對數學渲染做過一次全面檢查，四個缺陷都修了，判準也改成看 DOM 證據。收斂了。
- **實際發生**：spec 042 加了一個**受控 `<details>`**（為了打字重繪時不被掰回展開），

  而 typeset 的 effect 綁 `[text]` ⇒ **永遠不會再排**。實測 68 個公式 → 收合 → 0，等 4 秒仍是 0。

- **教訓**：死程式碼靜靜躺著，**壞掉的 skill 會被照著執行**；而 skill **沒有 oracle**
  ——不進 CI、沒有測試、沒人跑。⇒ **每次退役一個子系統，要順手掃一遍 skill 有沒有指向它。**
  可機械化的最小檢查（本次實際跑的）：把 skill 裡出現的 CLI 子指令與檔案路徑，
  對照專案實際註冊的子指令與檔案系統。掃完發現**只有那一個爛掉**，其餘引用的路徑都在。
  ＋退役 skill 要**連投影一起移除**——留在 `skillDirs` 裡就還是可被呼叫的。
- **不適用的時候**：judgment 型（meta）skill 講的是判準不是指令，不會因為程式碼變動而失效；
  這條專講**引用了具體指令／路徑**的 domain skill。
- **來源**：[history/107](history/107-退役會教錯路的來源skill-小腦沒有oracle.md)；
  被取代的 [history/011](history/011-固化-evaluate-and-add-source-skill.md)。

### 一個數字看起來像「沒人用」之前，還有四個更可能的解釋——「沒人用」是最後才輪到的

- **實際發生**：同一週撞到三次，形態各不相同：
  ① **訊號還沒開始記**——帶著文章／來源聊在儲存層零痕跡（spec 044 才補上）。
  ② **機制已經退役**——來源訂閱報 15/0，但根本沒有抓取路徑（[history/107](history/107-退役會教錯路的來源skill-小腦沒有oracle.md)）。
  ③ ⚠️ **量錯欄位**——對話清單讀 `conversations.why_node_id`，而事實來源是
     `why_nodes.conversation_id`；正式庫真的是由來的 12 段，畫面只認得 4 段。
     **程式自己的註解就寫著哪邊是事實來源**，而 UI 讀了另一邊。
  ④ ⚠️ **那個活動使用者還沒開始做**——`/api/source/distill`（來源頁「整理成核心理解」）
     上線至今 **0 條**。我正要把它當訊號解讀，使用者說：「**我只是還沒開始收集來源，
     到時候會用到**」。⇒ 那是**還沒到**，不是**不要**，而這兩者在數字上長得一模一樣。
     ＋前三種我自己查得出來，**第四種只有使用者知道**。
- **教訓**：**看到低得可疑的數字，依序排除：訊號多久前開始記？產生它的機制還在嗎？
  我讀的是不是事實來源？使用者進入那個階段了嗎？** 四個都排除掉，才輪到「沒人用」。
  跳過就會去解一個不存在的問題——而且很可能順手砍掉一個其實會動的功能。
  ＋**「還沒到」與「不要」的處置完全相反**：前者該**停止量它**（不然每次審計都跳出來
  浪費一輪對話），後者才該重新想設計。分不出來就**問人**——那一句話比再量三天都準。
  ＋前兩次錯在**報告**，第三次錯在**使用者的畫面**：同一個病灶，代價差一個量級。
  ＋當一份資料有兩個地方可以放（雙向連結、快取欄、反正規化），**寫下哪邊是事實來源，
  並讓讀取端只讀那一邊**——不然讀錯的那邊不會報錯，只會少顯示東西，而少顯示沒有人會抱怨。
- **來源**：[history/108](history/108-對話由來徽章讀錯欄位-儀器說謊的第三種形態.md)；
  spec 044／045、[history/106](history/106-三刀被做成量不到的-加欄地基補上.md)、[107](history/107-退役會教錯路的來源skill-小腦沒有oracle.md)。

### 量測工具報出來的 0，可能是工具在說謊——先確認那條路還在，再解讀那個數字

- **理論說**：`audit-field-usage` 報「來源訂閱：15 個訂閱、**0 個真的供過料（0%）**」，
  照判準讀就是「這功能沒人用」。
- **實際發生**：查下去發現**根本沒有抓取路徑**——沒有 `digest` 指令、`last_fetch_at` 零處寫入、
  那 15 筆是自動種的。⇒ 那個 🔴 不是「沒人用」，是**工具把殘骸列成現役功能**。
  照著它讀會去解一個不存在的問題。
- **教訓**：**看到 0 之前，先確認「產生這個數字的那條路現在還通不通」。**
  一個量測項的前提（機制還在）跟它的數值（有沒有人用）是兩件事，而報告只顯示後者。
  ⇒ 退役任何子系統時，**量測工具裡對應的那一列要一起處理**——改標成殘骸存量，
  不要留一個永遠紅的假訊號。假訊號會訓練人忽略紅色。
  ＋這是「量不到 ≠ 沒人用」的第二種形態：那次是**訊號還沒開始記**，這次是**機制已經沒了**。
- **來源**：[history/107](history/107-退役會教錯路的來源skill-小腦沒有oracle.md)；

### 用行號引用一份會一直長大的檔，等於寫下一個有到期日的指標

- **理論說**：引用一條教訓時附上 `experience.md:890`，讀的人一跳就到，比翻標題快。
- **實際發生**：`experience.md` 是 append-heavy（本週 47 → 62 條），**每加一條就把後面所有行號往下推**。
  `/knowie-judge` 機械掃過 16 處行號引用，**4 處已經指錯**——其中一處在**正式程式碼裡**
  （`src/knowfield/output/article.py`）。它們壞掉時沒有任何東西會報錯。
- ⚠️ **而我修的時候差點讓它更糟**：第一版用「行號現在屬於哪條教訓」機械替換，
  於是把「指向一堆看不懂的內文」（明顯壞掉）換成了「**指向一條真實但不相干的教訓**」（自信地錯）。

- **教訓**：**引用要錨在不會漂的東西上。** 判準：**這個錨點會不會因為別人在別處新增內容而失效？**

  而那種句子既穩定又可 grep。同理適用於：任何附行號的檔案引用、任何指向可變清單第 N 項的說法。

### 「還沒做的」通常不是尾巴，是洞——用水位線表示進度，等於把答案藏起來

- **理論說**：「上次收到哪裡」用一個水位線（`max(已處理)`）就夠了，前面已處理、後面沒處理。
  程式裡原本的 `distill_gap` 就是這個模型。
- **實際發生**：量了正式庫，覆蓋**不連續**——對話 44 收到第 46 則卻缺第 3–8 則、
  對話 31 缺 [1,2,9–12]。⚠️ 水位線會回報「收到第 46 則」，**而使用者要找的正是那個洞**。
- **教訓**：**進度不是一維的，除非你的流程強制它是。**
  凡是「可以跳著做」的工作（挑段落收、抽樣校對、逐條審核），
  進度就是**集合**不是**位置**——用位置表示會把已知的缺漏顯示成「已完成」。
  判準：**問「這件事能不能跳著做」。能 → 別用單一水位線。**
- ⚠️ **測起來有陷阱**：**沒有洞的 fixture，水位線實作也會綠。**
  一份「1–20 已收、21–46 沒收」兩種實作都通過。測試必須特地放一個**中間的洞**。
  ⇒ 這是「沒被錯誤實作撞過的測試」的變體：**撞得倒與否取決於 fixture 的形狀，不只取決於斷言的措辭。**

### 發現「同一件事有兩套介面」時，我的第一反應是補齊——使用者兩次都選拿掉

- **實際發生**：spec 046 之後我自己發現覆蓋顯示只加在聊天頁、檢視頁沒有，
  於是問使用者「要我補上嗎」。他的回答是「**我現在對話不想分檢視和接著聊了**」。
  ⚠️ **同一個模式的第二次**：spec 041 那次我加了「換你說」分隔線＋三顆起手式，
  他說「我純粹就只是想讓那文章當對話的第一則，**不用做什麼太特殊處理**」。
- **教訓**：**「兩套介面」的預設修法是砍到一套，不是補到兩套齊全。**

  判準：**兩套裡有一套是另一套的子集嗎？** 是 → 砍子集。

- ⚠️ **但砍之前必須逐項盤點能力**：刪頁面最容易的錯是順手弄丟一個**只有那頁有的動作**。
  用「可用動作集合的差 ＝ 0」當驗收，而不是憑印象說「反正那頁沒什麼」。
  ＋順帶會撈到既有的壞掉：這次發現側欄的「目前這段」高亮**只在要被刪的那頁亮得起來**
  ——砍之前不盤點，就會把一個一直壞的東西連同它的最後一個生效場景一起刪掉，
  然後永遠不知道它壞過。

## 關鍵延伸（主題觸發必讀）

### 偵測器缺了輸入不會回報「不知道」，它會回報「乾淨」——而乾淨看起來像好消息

- **理論說**：糾纏偵測寫好、測試綠了，就可以拿去搬任何一種知識。
- **實際發生**：`articles` 的來源當時是生成時寫進 markdown 的**字串**，不是連結。
  搬一篇文章時偵測器查不到任何相鄰知識，於是回報**「沒有糾纏」**——
  ⚠️ 那不是「沒關係」，是「沒問到」，而介面上這兩者長得一模一樣。
- **教訓**：**「查無結果」和「查不到」必須在儀器上分得開，否則缺陷會偽裝成通過。**
  凡是回傳空集合的偵測／檢查／掃描，動手前先問：
  **它的輸入來源全部接上了嗎？沒接上的那條，會讓它回報什麼？**
  若答案是「一樣回報空的」，那這個偵測器對那一類輸入是**半瞎的**，而它不會說。
  ⇒ 判準：**空結果要能區分成「找過了，沒有」與「沒得找」。** 做不到就先補輸入，別先出貨偵測。
- ⓘ 這是「儀器說謊」的第四種形態（前三種：量錯欄位、恆真條件、訊號起算時間），
  差別在**這次儀器的話是對的**——它說的是「我沒找到」，錯的是我把它讀成「不存在」。
- **來源**：[history/114](history/114-糾纏從裁決降級為問句-而護欄被實測的數字定住.md)；
  spec 049 把「補文章的來源連結」排成 P1、排在搬動之前；commit `7e97047`。

### 當我把一件事拆成「觸發器」和「結果」兩個名字，先問它們是不是同一個東西的兩個時刻

- **理論說**：搬動時偵測到的**衝突**叫「糾纏」，人選完之後留下的**邊**叫「捷徑」——兩個概念。
- **實際發生**：使用者一句「**或許糾纏 tangle 就是捷徑的別名**」把兩者合成一個。
  那條跨樹的邊在偵測之前就已經存在，偵測只是**讓它現形**，人只是決定要不要留著。
- **教訓**：**兩個名字若指向同一個東西在不同時刻的樣子，那是一個概念，不是兩個。**
  拆成兩個的代價不是多打幾個字，是**多出一個生命週期要維護**——
  合併之後，`resolve_tangle`、warning、「未解決的糾纏」清單**全部消失**，
  因為糾纏不再是要被消滅的錯誤狀態，它就是 DAG 的邊。
  ⇒ 判準：**問「這兩個名字有沒有可能同時為真」。** 會的話，它們是同一個東西。
- **來源**：[history/114](history/114-糾纏從裁決降級為問句-而護欄被實測的數字定住.md)；
  使用者裁決，2026-08-25。

### 用「最近一筆」指認你剛做的那件事，在有延遲時會指到上一筆——而它會回你「成功」

- **理論說**：`git push` 完馬上 `gh run list --limit 1`，抓到的就是這次的 CI run。
- **實際發生**：GitHub 註冊 run 有幾秒延遲。抓到的是**上一次**的 run，
  ⚠️ 而它回報「已經完成，success」——**假的綠燈長得跟真的綠燈一模一樣**，
  因為它沒有失敗，它只是在講另一件事。（用 `headSha` 比對才發現當下的 run 還 `in_progress`。）
- **教訓**：**指認要用內容比對，不要用時間或順序比對。**
  凡是「拿最新的一筆當作我剛產生的那一筆」（最後一個 run／最新的 pod／最近的檔案／最後一行 log），
  都在賭「寫入已經發生」，而延遲會讓這個賭安靜地輸。
  ⇒ 判準：**這個查詢有沒有把「我要的東西」寫進條件裡？** 沒有的話它找到的是「別的東西」，不是「沒東西」。
  ⓘ 同一族的第五種形態，也是最像好消息的一種——前四種回報怪數字，這種回報成功。
- **來源**：[skills/ship-knowfield/SKILL.md](skills/ship-knowfield/SKILL.md) 步驟 3（2026-08-25 現場撞到後補的）。

### 驗收的起始狀態要是使用者的起始狀態——而那幾乎永遠是「什麼都還沒做」

- **理論說**：搬動功能測試全綠、實跑也真的搬了，就是能用。
- **實際發生**：出貨隔天使用者問「要怎麼整理？」——答案是**幾乎不行**。
  正式庫 31/31 對話、75/75 理解**全部未歸屬**，而搬動入口只掛在**已歸屬**的項目上。
  ⚠️ 我實跑時**先用 SQL 把資料塞進領域再測搬動**，等於自己餵了一個現實中不存在的初始狀態。
- **教訓**：**功能在「使用者現在的狀態」上跑得起來嗎？**
  不是「在我準備好的狀態上」。做 setup 的那幾行 SQL／fixture，
  每一行都在把系統推離使用者所在的地方——**setup 越長，驗收離現實越遠**。
  ⇒ 判準：**問「第一次用的人，第一個動作是什麼？那個動作現在做得到嗎？」**
  起點動作做不到的話，後面全部的功能都站在空集合上。
- ⓘ 這跟「量錯欄位」不同：儀器沒壞、數字沒錯，**是我把系統擺到了一個沒人會在的位置**。
- **來源**：[history/115](history/115-在空集合上出貨-而測試是我自己餵的初始狀態.md)；
  spec 049 → 050 的落差；commit `7f35010`。

### 互動次數超過某個量，功能就等於不存在——那是可行性，不是體驗

- **理論說**：能搬就是能整理，一次搬一件慢一點而已，之後再優化。
- **實際發生**：108 件 × （開下拉 ＋ 選）＝ **216 次點擊**。沒有人會做完。
  ⓘ 這跟前一天寫下的「搬一段跳 15 條詢問 → 第二次就沒人用」**是同一條判準**，
  ⚠️ 而我當時只把它套在**詢問**上，沒想到它同樣管**操作**。
- **教訓**：**把互動次數乘上真實的資料量再看一次。**
  N 件 × K 次點擊，K 是常數不代表可行——決定可不可行的是 **N×K**，而 N 來自正式庫不是想像。
  ⇒ 判準：**這個操作在最大的那份資料上要點幾次？** 三位數就是「不存在」，不是「慢」。
- **來源**：[history/115](history/115-在空集合上出貨-而測試是我自己餵的初始狀態.md)；
  spec 050 的批次搬動。

### HTML5 拖放在觸控裝置完全不觸發——而它不報錯，只是不動

- **理論說**：`draggable` ＋ `onDrop` 就是拖放。
- **實際發生**：那版在合成事件下完全沒反應。查下去才想到 KnowField 是 **PWA**
  ——⚠️ HTML5 drag-and-drop **在觸控裝置上根本不產生事件**，手機使用者會遇到「拖不動也不報錯」。
  改用 Pointer Events（滑鼠與觸控同一條路）之後，實跑一次就過。
- ⓘ 附帶收穫：**能被自動化驅動的實作，通常也是跨裝置成立的那個**
  ——合成事件驅不動它，往往是因為它依賴一條只有某類輸入裝置才有的路徑。
- ⚠️ **同時撞到的第二個坑**：`Row`／`Node` 定義在元件內部 ⇒ 每次 render 都是**新的元件型別**，
  React 整棵子樹卸載重掛。拖曳一秒幾十次 render × 105 列 → **頁面卡死到截圖逾時**。
  判準：**定義在 render 裡的 JSX 元件是 bug，不是風格**。
- **來源**：[history/115](history/115-在空集合上出貨-而測試是我自己餵的初始狀態.md)；
  `frontend/src/pages/DomainsPage.tsx`（`beginDrag` / `renderRow` / `renderNode`）。

### 一個「例外桶」放在結構外面，就沒有人能在它裡面工作——把它放進結構的頂端

- **理論說**：沒有歸屬的東西不屬於樹，所以另外列一格「未歸屬」，清楚。
- **實際發生**：整理台出貨，使用者說「**還是很難整理**」——因為東西在樹**外面**，
  就做不了檔案系統最基本的動作：**在它現在的位置底下開一個子領域，再把它拖進去**。
  ⚠️ 資料模型一個字都不用改（仍是 `null`），錯的是它的**位置與名字**。
- **教訓**：**「還沒分類的」不是結構的例外，是結構的起點。**
  凡是你想開一個「其他／未分類／待處理」的桶子，先問：
  **使用者要在這個桶子裡做事嗎？** 要的話，它就得是結構裡的一個節點（通常是根），
  而不是結構旁邊的一格——旁邊那一格沒有子節點、不能被選、不能當容器。
  ⇒ 判準：**名字有沒有預設一個「之後會清空」的承諾？**「未歸屬」有，「根」沒有。
  而永遠不會清空的東西不該叫待辦。
- **來源**：[history/115](history/115-在空集合上出貨-而測試是我自己餵的初始狀態.md) 轉移五；
  使用者回饋，2026-08-25；`DomainsPage.tsx` 的 `ROOT_NAME`。

### 一條規則的**理由**被推翻時，先問規則本身還對不對——別連著一起丟

- **理論說**：「鄰居未歸屬時不算糾纏，因為**它還沒有位置**。」
- **實際發生**：把「未歸屬」改成「根領域」之後，它**有位置了**，理由當場失效。
  順手把規則一起改掉是很自然的下一步——⚠️ 而那會讓「搬出第一件東西」對所有鄰居報糾纏，
  66/75 條理解連著對話 ⇒ 第一次整理就跳十幾條詢問，正好撞回它本來要防的失效模式。
- **教訓**：**理由和規則是兩層，會分別壞掉。**
  理由塌了只證明「這條路走不通」，不證明「終點是錯的」——
  先用**後果**重新檢查規則（拿掉它會怎樣？），再決定要換理由還是換規則。
  ⇒ 判準：**改規則前先問「舊規則擋住的那個災難，現在還會發生嗎」。** 會 → 留規則、換理由。
- ⓘ 這次換的理由是：糾纏是「兩件**刻意放過**的東西被拆散」，根領域是還沒放過的地方
  ——比原本那個更準，因為它不依賴「有沒有位置」這個已經改掉的概念。
- **來源**：[history/115](history/115-在空集合上出貨-而測試是我自己餵的初始狀態.md) 轉移五；
  spec 050 FR-007（**行為零變更**，只換論證）。

### 下游的改善每次都有效一點點——那正是它掩蓋方向錯誤的方式

- **理論說**：使用者說「很難整理」，那就把整理介面做得更好用。
- **實際發生**：我連做兩刀（批次搬動、根領域＋搜尋＋全選），**每一刀都真的比前一刀好用**，
  而使用者每次都還是說「還是很難」。第三次我去查程式碼，才看到冊封／生文章／收來源
  **都不設歸屬** ⇒ ⚠️ **那份待整理清單是持續生產線，不是歷史包袱**。
  整理完，冊封三條又長回去。
- **教訓**：**改善不等於方向對。** 下游的每一次優化都會量到進步，
  所以「有進步」**不能**用來確認方向——能確認方向的只有「**它會不會再發生**」。
  ⇒ 判準：**問「我修完之後，同一個問題還會不會自己長回來」。**
  會 → 你在下游；那就去找**它是怎麼被生產出來的**。
- ⓘ 徵兆是可辨識的：使用者用同一句話抱怨第三次，而你每次都做了不同的（且有效的）改善。
  **同一句抱怨重複出現，比抱怨的內容更有資訊。**
- **來源**：[history/116](history/116-病因在上游-而繼承不是猜.md)；spec 045 → 050 → 051 的三刀。

### 把「猜」換成「繼承」——判準不是準不準，是錯的時候誰負責

- **理論說**：自動幫新知識歸類就是自動分類，而使用者已經否決過三次。
- **實際發生**：他要「新東西自動歸位」。同一個動作，兩種依據：
  自動分類是 **AI 看內容猜**；繼承是「**它長自一段你已經放好位置的東西**」。
- **教訓**：**一個自動行為可不可接受，看的是它的依據能不能被追問，不是它的準確率。**
  ⇒ 判準：**問「它錯的時候，是誰錯了」。**
  答案是「模型猜錯了」→ 那是推測，要人閘門；
  答案是「**你把出處放錯了**」→ 那是**導出**，可以自動做，因為錯誤有主人、而且改得動。
- ⓘ 同一把尺也解掉了「多個出處分屬不同領域怎麼辦」：取**最近共同祖先**
  （`AI/生成模型` ＋ `AI/數學` → `AI`）——那仍然是導出，不是猜。
- **來源**：[history/116](history/116-病因在上游-而繼承不是猜.md)；spec 051 FR-004／FR-007。

### 一個關係算不算「跨界」，取決於你站在哪裡看——那不是那條邊的屬性

- **理論說**：`A → B` 跨不跨領域，是這條邊自己的性質，算一次存起來就好。
- **實際發生**：使用者選了「當前領域**含子領域**」，同一條 `Flow Matching → 數學` 的邊
  就變成：站在 Flow Matching 是**跨出去**、站在 `AI` 是**內部連結**（兩端都在我的子樹裡）。
  實跑印證：同一條邊，一個立足點數到 1、另一個數到 0。
- **教訓**：**凡是含「外部／其他／跨」的概念，都要先問「相對於誰」。**
  這類詞看起來是在描述**對象**，其實藏著一個沒說出口的**觀察者**；
  把它當成對象的固有屬性存起來，換一個觀察者就全錯，而且不會報錯。
  ⇒ 判準：**這個屬性換一個立足點還成立嗎？** 不成立 → 它是關係，不是屬性，**不能快取成欄位**。
- ⓘ 連帶結論：同一個名字底下可以有兩個問句。搬動時問「**未來的歸屬**」、
  瀏覽時問「**現在的視角**」——邊是同一條，但顯示的字要不一樣
  （側欄寫「通往外面」不寫「糾纏」，後者看起來像有待辦要清）。
- **來源**：[history/116](history/116-病因在上游-而繼承不是猜.md)；spec 052 FR-003。

### 用「形式」命名一個位置，會無聲地排除掉所有其他形式

- **理論說**：那一格放的就是文章，所以叫「文章」最準確。
- **實際發生**：使用者要求改名「應用」，理由是「**這樣可以有更多類型的決策目標**」。
  他要的不是換個好聽的字——是**把那個位置從一種形式解放成一種用途**。
- **教訓**：**名字是這個位置未來能長出什麼的邊界。**
  用形式命名（文章／報告／清單），任何其他形式都會顯得「不屬於這裡」，
  ⚠️ 而排除是**無聲的**：沒有人會提案「在文章頁做一份決策清單」，所以你永遠不會收到抗議。
  ⇒ 判準：**問「這個名字是在講它長什麼樣，還是在講它拿來做什麼」。**
  講長什麼樣 → 換成用途，位置就空出來了。
- ⓘ 換名字**不必**同時把多種形式做出來（YAGNI）——先空出位置，形式後補。
- **來源**：[history/117](history/117-文章改名應用-而重載的詞會沉默地弄壞prompt.md)；
  使用者裁決，2026-08-26；spec 053。

### 改名之前先數一數這個詞有幾種意思——重載的詞會讓全域取代沉默地改壞語意

- **理論說**：把「文章」全部換成「應用」，改名完成。
- **實際發生**：`field_chat` 的三層份量 prompt 裡有**兩種**「文章」：
  「他收藏的**文章**/論文＝外部證言」是**別人寫的**、「他自己知識庫生成的」才是應用。
  ⚠️ 全換的話 prompt 會把外部來源歸進使用者的產出層，
  **而模型不會報錯——它只會開始拿別人的觀點當他的地基**，正好是反逢迎那道膜要擋的。
- **教訓**：**全域取代的風險跟出現次數無關，跟「這個詞有幾種意思」有關。**
  動手前先 grep 出全部出現處，逐一問「這裡指的是哪一個」——
  ⇒ 判準：**如果我改錯了，什麼東西會壞、誰會發現？**
  答案是「prompt 的語意會壞，而沒有人會發現」 → 那就要為它專門寫一支測試，
  因為既有測試全都不會紅。
- ⓘ 同一把尺也保住了「收進外部素材」那些入口的用詞（那裡的「文章」也是別人寫的）。
- **來源**：[history/117](history/117-文章改名應用-而重載的詞會沉默地弄壞prompt.md)；
  `tests/unit/test_vocabulary.py`；commit `f7a4efe`。

### 斷言「一個詞出現過」和斷言「一個規則還在」是兩件事

- **理論說**：測試裡寫 `assert "核心理解" in blob`，就表示那段 prompt 有在講理解優先。
- **實際發生**：⚠️ 那個條件**光靠 prompt 提到一次就滿足**。
  我把「與理解衝突時以理解為準」**整句刪掉**，測試照樣綠——
  它守的是一個詞的存在，不是那條規則的存在。
- **教訓**：**斷言要指向你真正怕失去的那句話，不是它附近的字。**
  ⇒ 判準：**把我怕的東西刪掉，這條測試會紅嗎？** 不會 → 它守的不是那個東西。
  文字型的斷言特別容易犯這個：詞會在很多地方出現，規則只在一個地方成立。
- **來源**：[history/117](history/117-文章改名應用-而重載的詞會沉默地弄壞prompt.md)；
  `tests/unit/test_field_chat_article.py::test_marked_as_ai_derivative`。
