# 功能規格：從對話生文章（階段 39，第一刀）

**Feature Branch**: `main`（小刀）· **Created**: 2026-08-22 · **Status**: Draft

**Input**: 使用者（2026-08-21）：「能不能直接從對話去生文章？前提是對話已經有相對應的核心理解了，只是用這樣的脈絡下去生的文章可能更有情境」

**知識庫來源**：vision 階段 39 · 設計源 [`draft/2026-08-21-從對話生文章.md`](../../knowledge/draft/2026-08-21-從對話生文章.md)（第一刀；第二刀「對話當情境」仍在 draft）

## ⚠️ 升之前量過的兩個數字，各自改掉了一版設計

**① 只用 referrers 生成會產出薄文章。** 實測本機場：13 段對話裡只有 **5 段**冊封出核心理解，
每段**中位數 2 條**，而 `top_k` 預設 8。

⇒ 形狀改為：**對話冊封出的節點釘住必進，其餘由場依相關度補滿**——對話決定角度，場提供厚度。

**② referrers 裡真的有 `猜想` 與 `類比`。** 實測：對話 #20 有 1 條 `猜想`、#23 有 1 條 `類比`。
現行生成把 `已證實/推論` 放正文、`類比/猜想` 隔到延伸閱讀（`output/article.py:15-16`）。

⇒ **釘住 MUST NOT 繞過這個分層**——否則「高證實文章」這個賣點就破了。釘的是「必被考慮」，不是「必進正文」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用這段對話生一篇 (Priority: P1)

使用者在一段已經冊封出核心理解的對話裡，一個動作就能生出一篇以那些理解為骨幹的文章。

**Why this priority**：使用者要的東西本身。

**Independent Test**：對一段有 N 條 referrers 的對話生成，檢查那 N 條**全部**出現在文章的
References 或延伸閱讀裡（依 kind 分流），不論向量檢索給不給分。

**Acceptance Scenarios**:

1. **Given** 一段冊封出 ≥1 條核心理解的對話，**When** 使用者按「用這段生一篇文章」，
   **Then** 生出的文章包含那些核心理解。
2. **Given** referrers 只有 2 條，**When** 生成，**Then** 正文仍達到 `top_k` 的厚度（其餘由場補）。
3. **Given** 一段**沒有**冊封出核心理解的對話，**When** 使用者看那個入口，
   **Then** 得到「這段還沒精選出核心理解，先精選」而不是一個失敗或空白。

---

### User Story 2 - 分層不因為釘住而被繞過 (Priority: P1)

**Why this priority**：與 P1 並列。文章的整個賣點是「高證實」（`app.py:585` 守衛：
「只採已證實/推論、結構化 References、不回灌場」）。釘住若能把 `猜想` 推進正文，賣點就破了。

**Independent Test**：對一段 referrers 含 `猜想` 的對話生成，檢查那條出現在**延伸閱讀**、不在正文。

---

### Edge Cases

- **referrers 全是 `類比`/`猜想`** → 正文由場補滿；那些條目進延伸閱讀。若場裡也沒有夠格的 → 沿用現行 `empty` 回應。
- **referrers 條數 > `top_k`** → 釘住的優先，超出部分照現行 `[:top_k]` 截斷（它們本來就同層，不是沉默失敗）。
- **對話已刪** → 明講找不到，不靜默生成一篇無關的。

## Requirements *(mandatory)*

- **FR-001**：使用者 MUST 能從一段對話**以一個動作**生成文章。
- **FR-002**：⚠️ 該對話冊封出的核心理解（`conversation_referrers`）MUST **全部被納入考慮**，
  且 MUST NOT 依賴向量檢索是否選中它們——向量沒選中是**沉默**的失敗（`experience.md:890`）。
- **FR-003**：⚠️ 釘住 MUST NOT 繞過認識論分層：`已證實/推論` 進正文、`類比/猜想` 進延伸閱讀，
  與現行規則**逐字相同**。釘的是「必被考慮」，不是「必進正文」。
- **FR-004**：正文不足 `top_k` 時 MUST 由場內**其餘已冊封節點**補滿；
  MUST NOT 讓任何未冊封的東西進場。
- **FR-005**：對話內容本身 MUST NOT 進入生成的 prompt（那是第二刀，仍在 draft）。
- **FR-006**：`conversation_referrers` 回空時，使用者 MUST 得到一個**可行動的下一步**
  （指向精選），MUST NOT 是空白或錯誤。
- **FR-007**：未走這條路徑時，`/api/article` 的行為 MUST 與現況**逐字相同**。
- **FR-008**：本刀 MUST NOT 修改任何已儲存內容（對話、核心理解、既有文章）。

## Success Criteria *(mandatory)*

- **SC-001**：一段有 N 條 referrers 的對話生成後，那 N 條的主張在
  **送給模型的 prompt ＋ 延伸閱讀區塊**中出現次數 **＝ N**。
  ⚠️ 原本寫成「在 References 中」——實作時才發現 `_references()`（`article.py:65`）
  渲染的是 URL 或「（你收藏的來源）」，**根本不含主張**，那樣寫永遠驗不到。
  正文節點的主張只存在於 prompt；延伸閱讀節點的主張才在 markdown 裡。
- **SC-002**：⚠️ **向量檢索停用**（embedder 為 None／排序失效）時，SC-001 仍成立
  ——這條是 FR-002 的真正驗收，不能靠「檢索通常也會選中」蒙混。
- **SC-003**：referrers 含 `猜想` 時，該條出現在正文的次數 **＝ 0**。
- **SC-004**：referrers 只有 2 條時，正文節點數 **＞ 2**（場有足夠節點的前提下）。
- **SC-005**：未帶對話時，`/api/article` 的請求／回應與現況 **逐字相同**。
- **SC-006**：既有測試零回歸。

## Assumptions

- 文章的 `topic`／標題沿用該對話的標題（`fc.title` 產的是「反映落點/全貌」的一句，不是問句）。
  標題另取列為 out of scope。
- 沿用現行 `top_k=8`、`length`／`level` 預設。

## Out of Scope

- **對話內容進 prompt**（第二刀，有真風險，仍在 draft）。
- **文章存 `conversation_id`** ——⚠️ `articles` 是既有表，而專案**沒有補欄機制**
  （`schema.py:148`：「不含舊 SQLite 檔的 `_migrate` 補欄」）⇒ `CREATE TABLE IF NOT EXISTS`
  對已存在的表是 no-op，正式環境不會長出新欄。加欄要另外處理，不塞進本刀。
- brief 中間物、標題另取、多段對話合生。
