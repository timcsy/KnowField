# Phase 0 研究：每日推播分診（推模式 MVP）

本檔解決 plan.md Technical Context 中的取捨。每項以「決策／理由／已考慮的替代」記錄。
研究輸入來源：`knowledge/draft/2026-07-23-來源策略與技術選型.md`（2026 上半年查證，含連結）。

## R1. 來源取得方式（FR-001）

**決策**：MVP 來源＝**論文骨幹＋1–2 精選新聞**：
- **arXiv**：官方 API（Atom），依 cs.LG/cs.CL 等分類查當日新論文。免費、穩定。
- **Hugging Face Daily Papers**：每日策展清單（HTTP/JSON），本身即高訊號來源。
- **Semantic Scholar**：Academic Graph API 補充 metadata／關聯；**須用指數退避、勿假設
  高吞吐**（官方已收緊速率）。
- **精選新聞（1–2 個）**：優先有 RSS 者；無 RSS 者以 **email-ingestion**（訂閱電子報 →
  轉 Atom feed，如 Kill the Newsletter 模式）取得，再以 `feedparser` 解析。

**理由**：全免費、可回溯、法遵風險低（公開頁／官方 API）；email-ingestion 是 2026 成熟
偏方，繞過無 RSS 問題。**X／Twitter 明確排除**（按用量計費、無實質免費層）。

**已考慮的替代**：付費新聞聚合 API（NewsAPI $449/月起、NewsCatcher $50/月起）——MVP
不需、成本高，延後；直接 scraping 有 ToS/合約風險（Meta v. Bright Data），僅在公開頁
且尊重 robots 時最後手段。

## R2. 去重／事件叢集（FR-002、SC-002 ≥95%）

**決策**：兩層去重。
1. **廉價精確層**：標準化識別碼與 URL——arXiv ID、DOI、canonical URL、正規化標題
   （去空白/大小寫/標點）→ 命中即同一則。
2. **語義層**：對通過第一層仍疑似重複者，用**本地 embedding** 算標題＋摘要的 cosine
   相似度，超過門檻者以**連通分量分群**歸為同一事件群組（entity-aware：標題中的實體
   命中加權）。

**理由**：多數跨源重複是同一論文/同一 ID 的轉貼，精確層即可低成本解決大宗；語義層只
處理殘餘的改寫／翻譯，控制成本。對齊研究「entity-aware embedding」為 SOTA 方向。

**已考慮的替代**：純 embedding 全量叢集——成本高且對「同 ID 轉貼」是殺雞用牛刀；
純 MinHash/SimHash——對語義改寫召回不足。故採混合。

## R3. 興趣過濾與排序（FR-003、SC-006 ≥70%）

**決策**：以**本地 embedding** 將使用者明講的興趣主題與條目（標題＋摘要）向量化，
以 cosine 相似度作相關性分數並排序；低於門檻者濾除。行為校準（US3/FR-012）以簡單
加權疊加於明講分數之上，且**明講永遠可覆寫**（憲章原則 VI）。

**理由**：明講主題多為語義概念（如「LLM 推理」），純關鍵字匹配召回不足；embedding
語義匹配較能達 SC-006 的相關性門檻。先明講當 prior、行為當 update，符合既有設計
（`knowledge/draft/2026-07-23-興趣畫像.md`）。

**已考慮的替代**：關鍵字/BM25——實作最簡但相關性品質恐不足；托管 embedding API
（Voyage/OpenAI）——增加成本與外部相依，違 YAGNI，且離線測試較難。故選本地模型。

## R4. Embedding 模型選型

**決策**：本地 `sentence-transformers` 小型多語模型（離線、可確定性測試）。具體型號在
實作時據當時可用者選定，介面以 `embed(texts) -> vectors` 抽象，方便替換。

**理由**：離線＝測試確定、零 API 成本、法遵單純；小模型對「標題/摘要相似度」已足夠。
多語以涵蓋非中文原文（FR-010）。

**已考慮的替代**：托管 embedding API（成本／相依）、大型本地模型（過重，違 YAGNI）。

## R5. 封頂摘要（FR-004、FR-005、SC-004）

**決策**：僅對**已進入匯整**的少數條目（≤15）呼叫 **Claude Haiku（`claude-haiku-4-5`）**，
以嚴格提示產生「一句定位＋一句為何值得看」，並在程式端加**長度守衛**（超過兩句即截斷／
重生），且提示明令**不得產生結論式判斷或深度分析**（原則 4）。

**理由**：只對少數條目呼叫＝成本受控；小模型足夠且快；程式端守衛確保 SC-004 不靠模型
自律。摘要是決策輔助非閱讀替代，與「工具不代替思考」一致。

**已考慮的替代**：抽取式摘要（取原文首句）——常無法給「為何值得看」的定位；大模型——
成本高且非必要。故選小 LLM＋硬守衛。

**LLM 相依備註**：模型 id 以環境提供的最新 Claude 型號為準；封裝於 `summarize/` 介面，
測試以錄製回應（stub）進行，不打真實 API。

## R6. 儲存（狀態）

**決策**：SQLite（stdlib）。資料表對應 data-model.md 的實體。已見條目、事件群組、
興趣畫像、每日匯整、行為訊號皆存於此。

**理由**：單檔、零外部相依、交易安全、易測試；MVP 規模綽綽有餘（YAGNI）。

**已考慮的替代**：Postgres（MVP 過度）、純 JSON 檔（查詢/去重不便）。

## R7. 交付與排程

**決策**：CLI 批次工具，一次執行產出當日匯整；輸出格式先支援終端／Markdown 檔，
交付管道（email 等）不綁定於 MVP。排程交給外部 cron。

**理由**：最簡、最快驗證核心分診價值（憲章 IV）；核心與交付解耦，日後可加通道。

**已考慮的替代**：內建排程器／常駐服務——MVP 不需，違 YAGNI。
