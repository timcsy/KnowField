# 功能規格：每日推播分診（推模式 MVP）

**Feature Branch**: `001-daily-triage-digest`

**Created**: 2026-07-23

**Status**: Draft

**Input**: 路線圖階段 1／2——LearnNews「推」模式：把 AI 相關新聞與論文的洪流，
去重、依興趣排序、濾成「今天值得點的幾則」，每則附極簡定位與直達原文連結。
知識來源：`knowledge/vision.md`、`knowledge/principles.md`、`.specify/memory/constitution.md`
與 `knowledge/draft/` 四份設計/研究草稿。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 收到每日分診匯整 (Priority: P1)

作為一位需要跟上 AI 趨勢的使用者，我每天收到**一份**匯整：系統已跨來源**去重**、
依我的興趣**排序**，只留下「今天值得我點的幾則」。每則只有**一句定位＋一句為何
值得看**，並附**直達原文**的連結，讓我三十秒掃完、決定深挖哪幾則。

**Why this priority**：這是整個產品的核心價值——用極低成本完成「分診」。單獨實作
這一條（搭配一份預設或手動的興趣清單）即為可用 MVP：使用者當天就能少花力氣跟上趨勢。

**Independent Test**：給定一組來源與一份興趣清單，執行一次每日匯整；驗證輸出為
去重後、依興趣排序的條目清單，每則含封頂摘要與可點擊直達原文的連結。

**Acceptance Scenarios**:

1. **Given** 已設定來源與興趣清單，**When** 產生當日匯整，**Then** 同一則消息（跨多個
   來源出現）在匯整中只出現一次。
2. **Given** 當日有數十至數百則候選，**When** 產生匯整，**Then** 條目依與興趣的相關性
   排序，且數量收斂到「可快速掃完」的規模。
3. **Given** 一則進入匯整的條目，**When** 使用者檢視它，**Then** 看到不超過兩句的
   「定位＋為何值得看」，以及一個可直達該則有價值原文的連結。
4. **Given** 一則條目，**When** 使用者檢視摘要，**Then** 摘要**不包含**系統對內容的
   結論式判斷或深度分析（工具只分診、不代替思考）。

---

### User Story 2 - 掌控自己的興趣清單 (Priority: P2)

作為使用者，我可以**明講**我在意的主題（例如 LLM 推理、agent、編譯器、具身智慧），
系統據此過濾與排序；我可以**隨時檢視、修改、覆寫**這份清單，且變更於次日匯整生效。

**Why this priority**：興趣過濾是「訊息適應人」的落地，也是使用者對「餵我什麼」保有
決策主權的體現。沒有它，匯整只能靠預設；有了它，分診才真正貼合個人。

**Independent Test**：新增／移除一個興趣主題，確認該變更被記錄、可再次讀回，且反映
在下一次匯整的過濾與排序上。

**Acceptance Scenarios**:

1. **Given** 空白或預設興趣清單，**When** 使用者新增主題，**Then** 系統記錄並於次日
   匯整套用。
2. **Given** 既有興趣清單，**When** 使用者檢視，**Then** 看得到目前生效的完整清單。
3. **Given** 系統對某主題的過濾結果，**When** 使用者移除或覆寫該主題，**Then** 使用者
   的決定優先於系統的任何自動推斷。

---

### User Story 3 - 從行為校準排序 (Priority: P3)

作為長期使用者，系統依我實際點開／略過哪些條目，**逐步校準**排序，讓匯整越來越貼合
我真正在意的東西——但明講清單永遠優先於學到的推斷。

**Why this priority**：先明講、再學習是設計定案，但學習屬加值；MVP 可先只靠明講清單
運作，行為校準可後續加入。

**Independent Test**：在固定興趣清單下，模擬使用者對某主題條目的持續點擊，驗證後續
匯整中該主題的相對排序上升，且使用者仍能以明講方式覆寫。

**Acceptance Scenarios**:

1. **Given** 使用者反覆點開某主題的條目，**When** 產生後續匯整，**Then** 該主題相關
   條目的排序相對提升。
2. **Given** 系統已學到某項偏好，**When** 使用者以明講清單覆寫，**Then** 明講設定優先。

---

### Edge Cases

- 當日**沒有**符合興趣門檻的新條目時，匯整如何呈現（空匯整 vs 放寬門檻的提示）？
- 某來源當日**無法取得**（逾時、失效、達用量上限）時，匯整是否照常產出並標示缺漏？
- 兩則來自不同來源但屬**同一事件的改寫／翻譯**，去重如何判定為「同一則」？
- 一則條目**無法取得可直達的原文**時，是否納入匯整（違反溯源硬需求則應排除或明確標示）？
- 使用者的興趣清單為**空**時，系統以何種預設行為過濾？
- 條目原文為**非中文**時，定位摘要以繁中呈現，但直達連結仍指向原文。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系統 MUST 從一組**已定義的來源**取得 AI 相關條目。MVP 的來源以**論文
  骨幹為主**，並納入**少量（1–2 個）精選新聞／部落格來源**以驗證「新聞×論文」的廣度
  差異化；新聞來源於後續階段再擴充。
- **FR-002**：系統 MUST 對跨來源的條目進行**去重**，使同一則消息／同一事件在單一
  匯整中只出現一次。
- **FR-003**：系統 MUST 依使用者的**興趣**對條目進行過濾與**相關性排序**（採「興趣
  過濾」，不採「讀者角色／深淺分層」）。
- **FR-004**：系統 MUST 為每則進入匯整的條目產生**封頂摘要**——不超過「一句定位＋
  一句為何值得看」。
- **FR-005**：系統 MUST NOT 在摘要中產生對內容的**結論式判斷或深度分析**；摘要僅為
  「是否值得深挖」的決策輔助。
- **FR-006**：系統 MUST 為每則條目提供**可直達有價值原文**的連結；無法提供者 MUST
  被排除或明確標示為缺漏，不得以生成內容取代原文。
- **FR-007**：系統 MUST 每日產出**一份**匯整，且其規模收斂到使用者可快速掃完。
- **FR-008**：使用者 MUST 能以**明講方式**建立興趣主題清單。
- **FR-009**：使用者 MUST 能**檢視、修改、覆寫**其興趣清單；使用者的明講設定 MUST
  優先於系統的任何自動推斷。
- **FR-010**：所有面向使用者的文字（摘要、介面、錯誤訊息）MUST 以**繁體中文**呈現；
  原文為其他語言時，直達連結仍指向原文。
- **FR-011**：當來源不可取得或當日無符合條目時，系統 MUST 仍產出匯整並**明確標示**
  缺漏或空狀態，不得靜默失敗。
- **FR-012**（對應 US3，可後續）：系統 SHOULD 依使用者的點擊／略過行為逐步校準排序，
  但 MUST 保持明講清單優先。

### Key Entities *(include if feature involves data)*

- **來源（Source）**：一個可取得條目的出處，具備類型（論文／新聞／部落格等）、取得
  方式與可用性狀態。
- **條目（Item）**：一則新聞或論文，具備標題、原文連結、發布時間、來源、所屬事件群組。
- **事件群組（Event Cluster）**：一組被判定為「同一則／同一事件」的條目集合，去重的單位。
- **摘要（Summary）**：附著於條目的封頂文字（定位＋為何值得看），繁中。
- **興趣畫像（Interest Profile）**：使用者的明講主題清單，加上（可選）從行為學到的
  偏好；明講部分優先。
- **每日匯整（Daily Digest）**：某日產出的、去重且排序後的條目清單，交付給使用者。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：使用者能在 **3 分鐘內**掃完一份每日匯整並決定要深挖哪幾則。
- **SC-002**：單一匯整內的**去重正確率 ≥ 95%**（同一事件不重複出現）。
- **SC-003**：進入匯整的條目中，**100%** 提供可直達原文的連結。
- **SC-004**：每則摘要長度**不超過兩句**。
- **SC-005**：使用者修改興趣清單後，變更於**次日匯整**內生效。
- **SC-006**：使用者對匯整條目標記為「相關」的比例 **≥ 70%**（相關性品質門檻）。
- **SC-007**：當日單份匯整的條目數收斂在可快速掃完的規模（預設上限，例如 **≤ 15 則**，
  可由使用者調整）。

## Assumptions

- **MVP 來源集（已定案 2026-07-23）**：以免費論文骨幹（arXiv、Hugging Face Daily
  Papers、Semantic Scholar）為主，**加上 1–2 個精選新聞／部落格來源**（可經「訂閱
  電子報再解析」取得無 RSS 來源）以驗證廣度差異化；**X／Twitter 明確排除**於 MVP
  （成本與取得限制，見 `knowledge/draft/2026-07-23-來源策略與技術選型.md`）。差異化
  定位＝廣度＋主權（非個人化本身），見 `knowledge/draft/2026-07-23-競品地貌與差異化.md`。
- **交付頻率**：每日一次批次匯整；具體交付管道（網頁／電子郵件等）屬實作決策，本規格
  不綁定。
- **冷啟動**：初次使用以明講興趣清單運作即可；行為校準（US3）為加值，非 MVP 必要。
- **範圍邊界**：本規格僅涵蓋「推」模式（每日分診匯整）。**拉模式（主題拉取深挖）屬
  路線圖階段 3、知識沉澱屬階段 4，均不在本規格範圍。**
- **不做深加工**：系統不產生第一性拆解、多鏡頭分析或趨勢外推——那是使用者自己做的
  （憲章原則 IV／VI、`knowledge/principles.md` 原則 4）。
- **法遵**：來源取得優先使用公開頁與官方 API，尊重各來源的 robots／服務條款
  （見 `knowledge/draft/2026-07-23-來源策略與技術選型.md` 的 scraping 邊界）。
