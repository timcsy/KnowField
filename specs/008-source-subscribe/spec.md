## User Scenarios & Testing *(mandatory)*

### User Story 1 - 自助追蹤一個站台／部落格（Priority: P1）

使用者發現某個部落格／站台很值得長期關注。他不想寫程式或找 AI——直接在 `/sources` 貼上那站的
網址（RSS feed 或首頁皆可），系統自動找出它的 feed、實測抓一次確認有內容，就把它加進來源清單。
**之後每次產出匯整，這個站的新文章就會自動一起被分診。**

**Why this priority**: 這是本階段的核心價值——把「追蹤一個水源」變成使用者自助、無需 AI/dev。
是第三種追蹤粒度（站台/作者＝持續水源），原則 5「人冊封」的又一投影。單獨實作即為可用 MVP。

**Independent Test**: 用可注入的假抓取器提供一個站台首頁 HTML（含 feed 連結）＋該 feed 的內容，
貼首頁 URL → 系統探測到 feed、驗證有料、加進來源；確認它出現在清單且被標為啟用。

**Acceptance Scenarios**:

1. **Given** 一個有 RSS 的站台首頁 URL，**When** 在 `/sources` 加入，**Then** 系統**自動探測到
   feed**、**實測抓到內容**、把它加進來源清單並**啟用**，回報成功（含來源名稱）。
2. **Given** 直接貼的就是 RSS feed URL，**When** 加入，**Then** 一樣驗證有料後加入（不必再探測）。
3. **Given** 已加入的來源，**When** 之後產出匯整，**Then** 該來源的新內容**自動被納入分診**
   （與內建來源一視同仁）。

---

### User Story 2 - 管理我追蹤的來源（Priority: P2）

使用者想整理來源：暫時**停用**某個太吵的、或**刪除**不再想追的、或**重新啟用**之前停用的。
`/sources` 列出所有來源（名稱／類型／啟用狀態），每個都能停用／啟用／刪除。

**Why this priority**: 追蹤要能反悔（主權含移除）；依附 P1 的來源清單，故 P2。

**Independent Test**: 種入幾個來源 → `/sources` 列出 → 停用一個（下次匯整不抓它）→ 刪除一個
（從清單消失）→ 重新啟用先前停用的。

**Acceptance Scenarios**:

1. **Given** 來源清單，**When** 停用一個來源，**Then** 它標為停用，且**後續匯整不再抓取它**。
2. **Given** 來源清單，**When** 刪除一個來源，**Then** 它從清單移除。
3. **Given** 已停用的來源，**When** 重新啟用，**Then** 它恢復被抓取。

---

### User Story 3 - 誠實邊界：不加壞來源（Priority: P3）

使用者可能貼錯網址、貼了沒有 RSS 的站、或站台當下抓不到。系統要**穩健**：明確的友善繁中提示、
**絕不把壞來源加進去**（避免日後匯整一直對死來源報錯或空抓）。

**Why this priority**: 「不加壞來源」是來源品質的底線（教訓 3、7）；依附 P1，故 P3。

**Independent Test**: 分別提供「無 feed 的站」「探測到 feed 但抓不到料」「網路失敗」三種假抓取器，
貼 URL → 皆得到友善繁中提示、**來源清單未新增任何項**。

**Acceptance Scenarios**:

1. **Given** 一個沒有可探測 feed 的網址，**When** 加入，**Then** 顯示友善繁中提示（如「找不到
   RSS，該站可能沒提供」）、**不加入任何來源**。
2. **Given** 探測到 feed 但實測抓不到內容（或網路失敗），**When** 加入，**Then** 友善繁中提示、
   **不加入**、不噴技術堆疊。

### Edge Cases

- **重複加同一 feed**：已在清單 → 提示「已在追蹤」，不重複加。
- **貼的 URL 同時可當首頁也可當 feed**：優先當 feed 驗證；失敗再當首頁探測。
- **刪除內建預設來源**：允許（使用者主權）；不因此在下次匯整自動補回（除非來源清單全空才重種預設）。
- **離線環境**：探測與驗證用可注入抓取器 → 完整可測（零外部呼叫）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系統 MUST 提供一個 web 頁，列出所有來源（**名稱、類型、啟用狀態**）。
- **FR-002**：使用者 MUST 能貼一個網址加來源；系統 MUST **自動探測 feed**——若網址本身是
  feed 直接用，若是站台首頁則從其內容找出 feed 連結。
- **FR-003**：加來源前，系統 MUST **實測抓取一次、確認有內容**才落庫並啟用（**不加壞來源**）。
- **FR-004**：探測不到 feed／實測抓不到內容／網路失敗時，系統 MUST 顯示**友善繁中提示**、
  **不新增任何來源**、不噴未處理技術堆疊。
- **FR-005**：加入的來源 MUST 於**後續匯整自動被抓取**（與內建來源一視同仁）。
- **FR-006**：使用者 MUST 能**停用／啟用／刪除**任一來源；停用後**後續匯整不抓取**它。
- **FR-007**：重複加同一 feed MUST NOT 產生重複來源（回報「已在追蹤」）。
- **FR-008**：**要追哪些來源由使用者決定**，系統 MUST NOT 自動加/推薦來源（原則 5、憲章 VI）。
- **FR-009**：所有面向使用者文字 MUST 為**繁體中文**（憲章原則 II）。
- **FR-010**：feed 探測與驗證 MUST **離線可測**（抓取可注入假來源，零外部呼叫綠燈，教訓 1）；
  MUST **復用既有來源存取**，不新增資料結構（教訓 8）。

### Key Entities *(include if feature involves data)*

- **來源（Source）**：一個被追蹤的內容管道——含名稱、類型（如 RSS）、feed 位址、啟用狀態；
  匯整會抓取所有**啟用**的來源。
- **Feed 位址**：實際的 RSS/Atom feed URL（可能等於使用者貼的網址，或從站台首頁探測而得）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：貼一個有效的 RSS／有 RSS 的站台 URL，系統 100% **探測到 feed＋實測有料後加入**，
  並出現在來源清單（啟用）。
- **SC-002**：加入的來源**下次匯整即被納入分診**（以種入的假來源驗證其內容出現在匯整）。
- **SC-003**：停用一個來源後，後續匯整**不再抓取它**；刪除後從清單消失；重新啟用可恢復。
- **SC-004**：對無 feed／抓不到料／網路失敗的網址，**100%** 友善繁中提示且**來源清單未新增**
  （0 個壞來源入庫）。
- **SC-005**：重複加同一 feed，來源**不重複**。
- **SC-006**：面向使用者文字全繁中；feed 探測/驗證在**離線**下完整通過測試；既有 177 測試不回歸。

## Assumptions

- **來源名稱**由 feed 標題或網域推得；**id** 由網域/feed 位址推得（穩定、可去重）。
- **加來源前必先驗證有料**（教訓 7：保證做進程式，不靠使用者保證 URL 對）。
- **範圍先做 RSS/Atom**；**無 RSS 站的 email-ingestion 兜底、作者跨平台的組合來源、每來源品質
  加權（把訂閱來源條目標成解說文）→ 後續**（範圍外）。
- **介面**：本階段為 **web `/sources`**（照 `/interests`/`/library` CRUD 模式）；CLI 為後續，
  `evaluate-and-add-source` skill 續作 AI 版後備（評估疑難來源）。
- **刪除內建來源**：允許且被尊重（僅在來源清單全空時才重種預設）。
- **開發**：TDD 強制（憲章原則 I）——先寫失敗測試再實作；契約測試用**可注入假抓取器**（離線）。
