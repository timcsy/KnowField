# Feature Specification: 個人內容進料——貼上＋PDF（多嘴一 pipeline 第一刀）

**Feature Branch**: `030-content-ingest`

**Created**: 2026-08-04

**Status**: Draft

**Input**: 路線圖階段 25／進料層任務 2 第一刀。把「收進」從「網址→淺抽摘要」擴成「個人內容進料」：常見知識來源多半塌回文字，第一刀做兩張「驗證過＋通用」的嘴——①貼上文字/markdown（通用、繞過登入/付費牆），②PDF→轉成 markdown。兩者都切塊、embed，落成可被 `/chat` 引用的「你收藏的」語料。依據：`draft/2026-08-04-進料轉檔選型.md`（含 Mistral Document AI 繁中實測）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 貼上一段內容收進知識庫 (Priority: P1)

使用者在別處讀到有價值的東西（別的 AI 聊天頁、付費文章、社群長討論），**全選複製** → 到 KnowField 貼進一個框、按「收進」→ 這段內容成為知識庫語料。之後在 `/chat` 問相關問題時，AI 能引用它、標「📎 你收藏的」。

**Why this priority**: 貼上是**通用且零外部相依**的一張嘴——它把「使用者自己的瀏覽器」當合法存取層，繞過登入/付費/JS/反爬，一張嘴涵蓋 AI Chat／社群／付費 Blog。是驗證整條進料→切塊→檢索 pipeline 最薄的一刀，也最先能穩。

**Independent Test**: 只實作貼上這條就是可用 MVP：貼一段文字 → 出現在「知識庫」清單 → `/chat` 問到它、答案帶 [n] 且標「你收藏的」。離線可測（注入替身 embedder/backend）。

**Acceptance Scenarios**:

1. **Given** 知識庫沒有相關內容，**When** 使用者貼上一段含「貓要吃貓砂」的文字並收進、接著在 `/chat` 問「貓怎麼養」，**Then** 回答引用該段、句尾標 [n]、來源列顯示「📎 你收藏的」。
2. **Given** 使用者貼上一段很長的文字（跨多個主題），**When** 收進，**Then** 它被切成多個可檢索單元（不是整段一塊），各自可被不同問題命中。
3. **Given** 使用者按收進但貼上框是空的，**When** 送出，**Then** 友善提示「沒有內容可收」、不新增任何語料。

---

### User Story 2 - 收進一份 PDF（論文／報告） (Priority: P1)

使用者上傳一份 PDF（或給 PDF 網址）→ 系統把它轉成 markdown、切塊、embed，成為知識庫語料 → `/chat` 能引用。即使 PDF 很長（超過轉檔服務單份上限）也不會崩。

**Why this priority**: PDF 是**已實測驗證**的一張嘴（Mistral Document AI 經現有 gateway，繁中吐繁體 markdown、數學保 LaTeX、表格成 md 表），且覆蓋最高價值來源（論文/報告）。

**Independent Test**: 上傳一份 PDF → 「知識庫」出現對應語料 → `/chat` 問其內容能引用。轉檔器注入替身可離線測；>30 頁 PDF 不噴 500。

**Acceptance Scenarios**:

1. **Given** 一份數位 PDF，**When** 收進，**Then** 轉成 markdown、切塊、embed，`/chat` 問其內容能引用、標「你收藏的」。
2. **Given** 一份超過轉檔服務單份頁數上限的 PDF，**When** 收進，**Then** 系統先分段處理、合併結果，**不崩**；若某段失敗，其餘照收、給友善提示（best-effort）。
3. **Given** 一份繁體中文 PDF，**When** 收進，**Then** 產出的 markdown **保持繁體**（不被轉成簡體）。
4. **Given** 轉檔服務暫時失敗（外部錯誤），**When** 收進，**Then** 不噴 500、給友善訊息、不影響既有語料與聊天。

---

### User Story 3 - 收進的內容是「證言」，永不變成「地基」 (Priority: P1)

不論貼上或 PDF，收進的內容都以**外部證言**身分存在：`/chat` 可引用它，但它**絕不進入使用者的「核心理解」地基**、**不自動變成精選的核心理解**。

**Why this priority**: 原則 6（複利而不污染）的安全底線，延續 spec 029 的膜分層守衛。缺了它，進料越多越可能把他人觀點污染成使用者的地基——這正是本產品最不能破的線。

**Independent Test**: 收進一段含 `SECRET_外部觀點` 的內容後，`build_field_system_prompt(list_why_nodes("anointed"))` **不含** `SECRET_外部觀點`；且核心理解數量**不因收進而增加**。

**Acceptance Scenarios**:

1. **Given** 收進一段含 `SECRET_外部觀點` 的內容，**When** 檢查場的地基（膜的 system prompt），**Then** 不含該內容。
2. **Given** 連續收進多筆內容，**When** 檢查核心理解清單，**Then** 數量不因收進而自動增加（收進 ≠ 精選）。

---

### Edge Cases

- **切塊邊界**：一段 markdown 內含公式塊或表格時，切塊**不從公式/表格中間切開**（否則餵檢索會壞）。
- **極短內容**：貼上/轉檔結果很短（不足一塊）→ 就當一塊收，不報錯。
- **重複收進**：同一份內容重複收進 → 不應無限增生重複語料（沿用既有去重精神；至少不崩）。
- **PDF 切檔膨脹**：長 PDF 分段時，不可用「每頁複製共用資源」的笨切法（實測會把 6MB/49 頁膨脹成 45MB）——分段須用不膨脹的方式。
- **轉檔部分失敗**：多段 PDF 其中一段失敗 → 其餘段照收、標示哪段沒進，不整份丟失。
- **非文字 PDF**（純掃描圖）：走轉檔服務的 OCR，仍應得到文字；完全無法辨識時給友善提示、不崩。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供「貼上文字/markdown」收進入口；貼上內容經切塊、embed 後成為可被 `/chat` 檢索引用的語料。
- **FR-002**: 系統 MUST 提供「PDF 收進」入口（檔案上傳與/或 PDF 網址）；PDF 經轉檔成 markdown、切塊、embed 後成為可檢索語料。
- **FR-003**: 系統 MUST 把長內容（貼上或 PDF）**切成多個可檢索單元**，而非整份一塊；切塊為可離線測試的純邏輯。
- **FR-004**: 切塊 MUST 遵守：中文按字元數切（預設約 400 字、重疊約 40 字，不依賴空白分詞）；**不從公式塊或 markdown 表格中間切開**；以 markdown 章節（含編號）為優先切點；粒度與檢索取回數（top_k）相容。
- **FR-005**: PDF 轉檔 MUST 能處理**超過轉檔服務單份頁數上限**的檔案——先分段、逐段轉、合併 markdown；分段方式**不得造成檔案膨脹**。
- **FR-006**: 轉檔、分段、切塊、embed 任一步失敗 MUST 以 best-effort 處理：給友善訊息、保住已成功的部分、不噴 500、不影響既有語料與聊天。
- **FR-007**: 收進的內容 MUST 以「外部證言」身分存在——可被 `/chat` 引用並標示為「你收藏的」，但**不得進入場的地基**（不進 `build_field_system_prompt`）、**不得自動變成精選的核心理解**。
- **FR-008**: 繁體中文 PDF 收進後產出的 markdown MUST 保持繁體（OCR 讀既有字形；本階段不含會產生簡體的語音轉錄，故不需簡繁轉換）。
- **FR-009**: 空內容（空貼上、空轉檔結果）MUST 友善提示、不新增語料。
- **FR-010**: 轉檔能力 MUST 可注入替身，使貼上/切塊/收進流程能在**零外部呼叫**下自動測試。

### 非功能需求／約束（憲章與教訓）

- **NFR-001（憲章 IV 零相依）**：轉檔與切塊 MUST 藏在可插拔介面後；重活走使用者既有的 API gateway 或選用相依，核心保持 stdlib；預設提供離線替身。
- **NFR-002（教訓 8 少動結構）**：MUST 復用既有語料與 embedding 儲存，**不新增資料表**；一個來源切出的多塊落在既有語料結構。
- **NFR-003（憲章 I / TDD）**：先紅後綠；切塊純函式、轉檔注入替身、貼上→檢索 web 流程皆須自動化測試涵蓋，且既有測試（現 277）不回歸。
- **NFR-004（憲章 II）**：全繁體中文（介面、提示、來源標記）。

### Key Entities *(include if feature involves data)*

- **收進來源（Source）**：一次進料的原始輸入——貼上的文字，或一份 PDF（上傳/URL）。承載其標題與原始出處（若有）。
- **語料塊（Chunk）**：來源切出的一個可檢索單元，帶內容、embedding、以及回指來源的資訊。以既有語料結構承載（一來源→多塊），檢索時等同既有「收進條目」，可被 `/chat` 標「你收藏的」引用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者貼上一段內容並收進後，能在 `/chat` 問到它、答案引用該段並標「你收藏的」（附 [n]）。
- **SC-002**: 使用者收進一份 PDF（含超過轉檔服務單份頁數上限者）後，能在 `/chat` 引用其內容；**超長 PDF 收進不失敗**。
- **SC-003**: 收進的繁體中文 PDF，產出內容維持繁體（抽樣檢查無簡體化）。
- **SC-004**: 長內容收進後被切成多塊、可被不同問題各自命中；公式/表格不被切半。
- **SC-005**: 收進任一段含標記字串的內容後，該字串不出現在場的地基（膜 system prompt），且核心理解數量不因收進增加。
- **SC-006**: 轉檔/切塊/embed 任一失敗時，收進動作給友善提示、不噴 500、不影響既有聊天與語料。
- **SC-007**: 全流程可在零外部呼叫下自動測試；既有測試不回歸。

## Assumptions

- **切塊落點**：一個來源切出的每一塊，以既有語料結構的一筆條目承載（一來源→多筆），沿用既有 embedding 與檢索（spec 029），不新增資料表。
- **PDF 輸入**：以檔案上傳為主要入口，PDF 網址為輔；兩者殊途同歸走同一轉檔→切塊流程。
- **轉檔服務**：走使用者現有 OpenAI 相容 gateway 上的文件轉檔能力（已實測可用、輸出繁體 markdown）；實際模型/端點屬實作細節，於 plan 決定。
- **切塊參數固定**：預設約 400 字＋40 重疊，本階段**不提供讓使用者調參的 UI**。
- **去重**：沿用既有語料的去重精神；本階段至少保證重複收進不崩、不失控增生（完整去重策略若需要，於 plan 評估）。
- **範圍邊界（本階段明確排除，皆為後續各自增量）**：URL 抓正文（trafilatura 類）、YouTube 逐字稿、瀏覽器擴充、手機分享（PWA Share Target）、Word/Excel/PPT/音訊/影片的原生處理、hybrid/sparse/RRF/reranker/視覺檢索（ColPali）、多模態 embedding、檢索調參 UI、跨文件多跳推理、收進自動變核心理解、CLI。
