# spec 063：B-底層——資料層變成多租戶，但不開放註冊（vision 階段 58）

## 為什麼現在做，而不是等第二個人

**不可逆的先做對，可逆的等。** `owner_id` 是 schema 決定，越晚加越貴
（成本跟**查詢面**成正比，而查詢面隨每個新功能長大）；開放註冊是外向、可逆、隨時能做。

⚠️ 反面也記著：正式庫使用量還很低，這一刀買的是**未來的成本**，不是現在的功能。
所以它**不含** B-開放（見 out of scope）。

## FR

- **FR-001** `domains`／`why_nodes`／`articles`／`conversations`／`digest_entries` 各加 `owner_id`。
  ⚠️ 補欄用 `DEFAULT 1` ⇒ **加欄本身就是 backfill**，不需要另一支腳本。
- **FR-002** 過濾在 `Repository(owner=…)` **這一層**，不在呼叫端。
- **FR-003** ⚠️ **這件事不能靠記性。** 判準：**能靠記性守住的東西，就是保證會漏的東西。**
  ⇒ 兩層測試互相補洞：
  - **行為層**：兩個 owner，交叉可見度是 0（讀、寫、語料、清冊、猜 id 都要擋）
  - **掃描層**：原始碼裡每一個碰到 owned 表的查詢都帶條件；刻意的例外要寫
    `# owner-exempt: 理由`——把「我忘了」變成「我宣告了」
- **FR-004** join 表（`entry_embeddings`／`article_roots`）**不加** owner：
  它們只經父 id 存取，而父 id 一定來自已過濾的查詢。

## 不做，以及為什麼

- **每人一棵實體根領域**——draft 原本要求這條，理由是「`domain_id IS NULL` 多人之後變歧義」。
  ⇒ **`owner_id` 已經把它吃掉了**：`(owner=1, NULL)` 與 `(owner=2, NULL)` 本來就是兩個根，
  因為每一個查詢都帶 owner。已用 `TestRootIsNotAmbiguous` 驗證。多做就是多一個要維護的東西（憲章 IV）。
- **B-開放**（開放註冊／邀請碼）——等真的有第二個人要用。
- 密碼管理（OAuth 已處理）· RBAC（AC 是 room 樹上的距離，不是角色表）· 計費。

## 驗收

1. 兩個 owner 的交叉可見度 = 0（含**語料**——語料外洩＝別人的理解在回答你的問題）
2. 掃描器涵蓋 `repository.py` ＋ `app.py`，具名表與**動態表名**都掃
3. ⚠️ 掃描器自己要斷言**分母不是零**（spec 061 的教訓）
4. 對抗驗證：把 `self.owner` 釘死成 1 → 行為層應大量變紅
5. 既有 736 支測試全綠（它們都是單人的 ⇒ 這一刀不該改變單人行為）
6. 實跑：既有資料仍然看得到、件數不變
