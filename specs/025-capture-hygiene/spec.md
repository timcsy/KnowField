# Feature Specification: 對話收料的漏——去重＋收尾缺口提醒

**Feature Branch**: `025-capture-hygiene`

**Created**: 2026-07-29

**Status**: Draft

**Input**: User description: "同一段對話冊封多條根因時去重（連同一份存檔、不再複製）＋長對話收尾缺口提醒（尾段未收就提醒、人按才收）——真實使用審計照出 spec 023 的漏"

## 由來（真實使用審計照出）

使用者請我讀他自己存下的場（19 段對話／24 條根因），照出 spec 023 兩個漏——**「引擎好 ≠ 收料好」**：深長推導煉出 15 條根因（引擎好），但**收料跟不上**。現場數據可回溯（`learnnews.db`）：

- **漏 A（囤積）**：15 條根因源自**同一段 32 句對話**，但每次「冊封時連同存」都新增一份完整複本 → **同一段對話存了 15 遍**。打臉 spec 023／vision 階段 18 的成功標準「**人閘門、選擇性、預設流走（不囤積）**」。
- **漏 B（收尾缺口）**：根因停在第 31-32 句，對話卻聊到第 70 句。第 33-70 句**最原創的落點**（四元樹多尺度、QuadTree Attention、影片串流當訓練資料）**一條根因都沒有** → 最原創的沒被蒸餾，躺在沒連根因的存檔裡。

本規格修這兩個漏（**#3 標題/章節切分待議、不在本輪**）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 同一段對話冊封多條根因，只留一份存檔（Priority: P1）

使用者在一段長對話裡，一次蒸餾出多條重點、逐條冊封成根因，並選擇「連同這段對話存成由來」。系統應把這些根因**都連到同一份存檔**，而不是每冊封一條就複製一整份對話。事後在 `/roots` 看，這幾條根因的「← 由來」**都指向同一段對話**；`/conversations` 清單裡**這段對話只出現一次**。

**Why this priority**: 直接堵住囤積漏（現況一段對話被存 15 份）；兌現 spec 023 本意「不囤積」。是使用者指定「先做」的修，且最便宜。

**Independent Test**: 從同一段 live 對話連續冊封 N 條根因（皆選連同存）→ 驗證 `/conversations` 只多一份、N 條根因皆連到它；`/roots` 各「← 由來」指向同一 id。

**Acceptance Scenarios**:

1. **Given** 一段 live 對話，**When** 使用者連續冊封 3 條根因、每條都選「連同這段對話存成由來」，**Then** 只新增**一份**存檔、3 條根因皆連到它（不再 3 份複本）。
2. **Given** 已就上一段對話存過一份由來，**When** 使用者再冊封第 4 條根因並選連同存，**Then** 不新增第二份，第 4 條連到**既有那份**。
3. **Given** 一條根因**單獨**冊封（不選連同存），**When** 冊封完成，**Then** 不新增任何存檔（維持既有行為）。
4. **Given** 兩段**不同**的對話各自冊封根因，**When** 各選連同存，**Then** 產生**兩份**不同存檔（去重只在「同一段對話」內生效，不誤併不同對話）。

---

### User Story 2 - 長對話尾段沒收，提醒使用者現在收（Priority: P2）

使用者習慣在一段對話裡深挖很長。當對話已經很長、而他**上次冊封／存檔之後又長出一大段還沒蒸餾**時，介面出現一個**溫和提醒**：「自上次整理後又聊了一大段（第 N–M 句）還沒收，要不要現在冊封？」使用者可以點提醒去整理，也可以忽略。系統**只提醒、不自動冊封**。

**Why this priority**: 直接打到「最原創的沒收」漏——幫使用者把長線尾段的金子收乾淨。次於 #1（囤積是既成 bug），但對長期複利價值最大。

**Independent Test**: 餵不同長度／不同「上次收位置」的對話狀態給判準純函式 → 驗證只有「夠長且尾段未收達閾值」時回真，短對話或剛收滿時回假；UI 據此顯示/隱藏提醒。

**Acceptance Scenarios**:

1. **Given** 一段很長的對話、且自上次冊封後又長出一大段未收，**When** 使用者在對話頁，**Then** 出現「尾段未收」提醒（標出大約區間），可點去整理或忽略。
2. **Given** 一段短對話（未達長度閾值），**When** 使用者在對話頁，**Then** **不出現**提醒（不吵）。
3. **Given** 一段長對話但剛剛才冊封／存過（尾段沒有累積未收），**When** 使用者在對話頁，**Then** **不出現**提醒。
4. **Given** 提醒出現，**When** 使用者忽略、繼續聊，**Then** 系統**不自動冊封任何東西**（人閘門，原則 5）。

---

### Edge Cases

- **空對話／缺欄位**：判準對空 messages、缺 content 不崩，回「不提醒」。
- **去重的「同一段」判定**：需有穩定依據判「這就是剛才那段對話」（如首次連同存後記住其 id、後續帶回）；不得把**不同**對話誤判為同一段而併檔。
- **既有 15 份歷史複本**：本輪**不做**回頭清理／遷移（避免破壞性操作）；只保證「以後不再複製」。既有複本維持可讀。
- **提醒閾值邊界**：剛好在閾值上下要有明確、可測的行為（判準純函式定義清楚）。
- **並存兩存檔點**：`/chat/save`（獨立存）與 `/chat/anoint`（連同存）都不得產生對同一段的重複份。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 讓「同一段 live 對話」冊封的多條根因**共用同一份存檔**——第一次連同存建立存檔，後續冊封連到**既有那份**，不新增複本。
- **FR-002**: `/roots` 中源自同一段對話的多條根因，其「← 由來」MUST 皆指向**同一份**存檔；`/conversations` 清單中該段對話 MUST 只出現一次。
- **FR-003**: 系統 MUST 只在「同一段對話」內去重；**不同**對話各自的連同存 MUST 產生各自的存檔（不誤併）。
- **FR-004**: 單獨冊封（不選連同存）MUST 不新增任何存檔（維持既有行為）。
- **FR-005**: 系統 MUST 提供一個**純函式判準**，依（對話長度、上次收的位置、閾值）判定是否該提醒「尾段未收」及其大約區間；離線可測、對缺項不崩。
- **FR-006**: 當判準為真時，對話介面 MUST 顯示**溫和的收尾提醒**（標出未收區間、可點去整理、可忽略）；為假時 MUST 不顯示（不吵）。
- **FR-007**: 收尾提醒 MUST 只提醒、**不自動冊封、不自動存**（人閘門，原則 5）。
- **FR-008**: 去重 MUST 是「新存時連既有」的加法行為，**不得刪除或改寫既有存檔**、不改場（原則 6，唯讀取向）。
- **FR-009**: 若去重需要演進「一段對話 ↔ 多條根因」的關聯，其資料結構變更 MUST **冪等遷移、不破壞既有 spec 023 的存檔**；此為新資料關係、MUST 記一筆（教訓 8）。
- **FR-010**: 所有新增介面文字 MUST 為繁體中文；核心判準邏輯 MUST 零第三方相依。

### Key Entities *(include if feature involves data)*

- **對話存檔（Conversation）**：既有實體（spec 023）。本輪關聯演進為「一份存檔可為**多條**根因的由來」。
- **根因（Why node）**：既有實體。其「由來」關聯改為可與其他根因**共用**同一份存檔。
- **由來對應（provenance）**：`{根因 → 存檔}` 的對應；本輪允許多個根因對應到同一存檔。
- **收尾缺口判準（純值）**：由（對話長度、上次收位置、閾值）算出「是否提醒＋未收區間」，**不落庫**。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一段對話冊封 N 條根因（皆連同存）→ 存檔數只增 **1**、N 條根因「← 由來」皆指向它（不再 N 份）。
- **SC-002**: 不同對話各自連同存 → 各自產生存檔（去重不誤併）；單獨冊封 → 存檔數不增。
- **SC-003**: 長對話且尾段未收達閾值 → 出現收尾提醒並標出區間；短對話或剛收滿 → 不出現。
- **SC-004**: 收尾判準為純函式、離線可測、對空／缺欄位不崩；提醒**不自動冊封／不自動存**。
- **SC-005**: 去重不刪改既有存檔、不改場；關聯變更冪等遷移、既有 spec 023 存檔仍可讀。
- **SC-006**: 全繁中；核心零相依；**現有 393 測試不回歸**＋新增涵蓋去重與收尾判準的測試。

## Assumptions

- 「同一段對話」的判定以**內容指紋**為準（訊息序列的穩定雜湊）：因 anoint 後頁面清空、client 難持有存檔 id，指紋是最務實的識別，且能正確把「同一狀態下批次冊封的多條根因」併到一份。代價：若兩次冊封之間對話又長了一句，會被視為不同段（各存一份）——實務上批次冊封發生在同一狀態，可接受，仍遠勝現況 N 份。（原傾向「stable-id」因 UX 清空而不可行，依憲章 III 於規劃階段更正。）
- 收尾判準以**可測的量**為訊號（對話長度、上次收的位置/長度、閾值），非語意判斷；具體閾值於實作階段定，且以純函式封裝便於調整與測試。
- 沿用既有 `/chat`、`/chat/anoint`、`/chat/save`、`/roots`、`conversations` 表與 `why_node_provenance`。

## Out of Scope（明確排除，防蔓延）

- **#3**：標題凍在第一句、章節切分、用「落點」重命名（待議，本輪不做）。
- 回頭清理／遷移既有 15 份歷史複本（避免破壞性操作；只保證以後不再複製）。
- 自動冊封／自動存全部。
- 對話全文搜尋、跨對話關聯／多跳。
