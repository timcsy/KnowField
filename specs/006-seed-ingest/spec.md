## User Scenarios & Testing *(mandatory)*

### User Story 1 - 把一篇經典收進知識庫，之後問得到（Priority: P1）

使用者讀到一篇該領域的地基材料（一篇 arXiv 論文、或一篇部落格文章），想讓它**永久成為
自己知識庫的一部分**——不必等它剛好出現在某天的匯整。下一個指令 `ingest <arXiv-id|url>`，
工具抓取該篇、消化成可讀散文、收進 KB。之後對相關主題問 `ask`，這篇就會被檢索到、
且答案能一鍵回到原文。

**Why this priority**: 這是本增量的核心價值，也是原則 5「權重由人冊封」的**第一個具體動作**
——使用者親手把一個「深度吸引子」放進場。單獨實作即補上 KB 的「地基」缺口（增量 1 只有每日流）。

**Independent Test**: `ingest` 一個已知內容的來源（用可注入的假抓取器），再問一個命中它的問題，
驗證答案出自該種子、來源列出其原文連結。

**Acceptance Scenarios**:

1. **Given** 一個 arXiv ID 或文章 URL，**When** 執行 `ingest`，**Then** 該篇被抓取、消化、
   收進知識庫，並回報成功（含標題）。
2. **Given** 已 ingest 的種子，**When** 對相關主題問 `ask`（CLI 或 web），**Then** 該種子可被
   檢索到、列為來源、附**原文連結**（沿用增量 1 的檢索與門檻）。
3. **Given** 同一材料，**When** 重複 `ingest` 兩次，**Then** 知識庫只保留**一份**種子（不重複）。

---

### User Story 2 - 解說文勝過平庸快訊（品質不對等）（Priority: P2）

使用者知道某些來源（把 why 講透的解說文）價值遠高於一則快訊。ingest 時可把該篇**標為
解說文**；日後檢索同一主題時，解說文的**權重高於一般快訊**，更容易被選為答案依據——
落實「一篇高品質文章可打敗五十篇平庸」。

**Why this priority**: 品質不對等是「深度吸引子」的關鍵性質；但依附於 P1 的 ingest 管線，故 P2。

**Independent Test**: ingest 一篇標為解說文、一篇標為一般的材料，兩者對某問題都相關；
驗證解說文排序在前 / 更易入選來源。

**Acceptance Scenarios**:

1. **Given** 一篇解說文種子與一篇一般快訊，兩者都與問題相關，**When** 問 `ask`，**Then** 解說文
   的相關度排序**高於**快訊（品質權重生效）。
2. **Given** ingest 時未標類型，**When** 收進，**Then** 以合理預設類型處理（不因未標而失敗）。

---

### User Story 3 - 誠實邊界：抓不到就好好講，不炸（Priority: P3）

使用者可能貼錯連結、來源 404、網路不通、或頁面無法解析。工具要**穩健**：明確的友善繁中
訊息、指令正常結束，而非噴出技術堆疊或寫入半殘的種子。

**Why this priority**: 工具可信度底線（教訓 3），但依附 P1 管線，故 P3。

**Independent Test**: 令抓取器丟出各種失敗（404／逾時／無法解析），驗證得到友善繁中訊息、
非零但正常的結束、且**知識庫未被寫入半殘種子**。

**Acceptance Scenarios**:

1. **Given** 一個抓不到或無法解析的來源，**When** `ingest`，**Then** 顯示友善繁中訊息、正常
   結束、不噴 traceback，且**不寫入任何殘缺種子**。
2. **Given** 消化/嵌入後端（真實 API）暫時失效，**When** `ingest`，**Then** 同樣攔成友善訊息。

### Edge Cases

- **重複 ingest**：同 arXiv ID／同 URL 再收 → 不新增第二份（可回報「已在庫」）。
- **arXiv ID 多種寫法**：`2407.12345`、`arXiv:2407.12345`、`https://arxiv.org/abs/2407.12345`
  應視為同一篇。
- **一般 URL 無摘要**：抓 title＋主文文字即可（abstract 級消化）；無法取得正文 → 視為抓取失敗。
- **離線環境**：可注入假抓取器完整測試（零外部呼叫）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：系統 MUST 提供一個指令，接受**單篇材料識別**（arXiv ID 或文章 URL），抓取該篇、
  消化成可讀散文、收進知識庫成為「種子」——**獨立於每日匯整**（不需該篇出現在某日 digest）。
- **FR-002**：種子收進後 MUST 能被既有問答（CLI 與 web `ask`）檢索到、列為來源、附**原文連結**，
  沿用增量 1 的檢索與相關度門檻（不另立門檻，experience 教訓 4）。
- **FR-003**：每個種子 MUST 存有**可直達的原文連結**（原則 3）；無來源連結者不入庫。
- **FR-004**：系統 MUST 同時支援 **arXiv ID** 與**一般文章 URL** 兩種輸入，並把同一篇的多種
  寫法視為同一材料（去重依據）。
- **FR-005**：使用者 MUST 能把種子標記為**解說文**（高品質類）；檢索時解說文的權重 MUST
  **高於一般快訊類**（落實品質不對等）。未標記時採合理預設類型，不因此失敗。
- **FR-006**：抓取／解析／後端失敗時，系統 MUST 攔成**友善繁中訊息**、正常結束、不噴未處理
  技術堆疊，且 **MUST NOT 寫入半殘種子**（教訓 3）。
- **FR-007**：重複 ingest 同一材料 MUST NOT 產生重複種子（idempotent；可回報「已在庫」）。
- **FR-008**：ingest MUST **由使用者主動指定**要收哪一篇；系統 **MUST NOT 自動決定/推薦** canon
  （原則 5「權重由人冊封」、憲章原則 VI 決策主權）。
- **FR-009**：系統 MUST **複用既有核心**（消化、嵌入、檢索、存取、指令框架），不重寫；且 MUST
  有**離線可測路徑**——抓取可注入假來源，契約測試零外部呼叫綠燈（教訓 1）。
- **FR-010**：嵌入 MUST **批次**處理（不逐一呼叫外部 API）；面向使用者文字 MUST 全繁中（憲章 II）。

### Key Entities *(include if feature involves data)*

- **種子（Seed）**：使用者手動收進 KB 的一篇材料——含原文標題、原文連結、消化散文、**來源
  類型（解說文／一般）**；與每日匯整條目**同屬檢索語料**（都能被 `ask` 找到），但來源不同。
- **材料識別（Source Ref）**：arXiv ID 或文章 URL；用於抓取與**去重**（多種寫法歸一）。
- **來源類型／品質層級**：至少分「解說文（高品質）」與「一般」；決定檢索時的**權重**。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：`ingest` 一篇後，一個命中它的 `ask` 問題能**檢索到該種子並列為來源**（含原文連結）；
  可溯源率 100%。
- **SC-002**：同一材料 ingest 兩次，知識庫只有**一份**種子（重複率 0）。
- **SC-003**：一篇解說文與一篇一般快訊對同一問題都相關時，**解說文排序在前**（品質權重生效，
  以種入的對照材料驗證）。
- **SC-004**：抓取／解析失敗時 **100%** 呈現友善繁中訊息、無技術堆疊、且**無半殘種子入庫**。
- **SC-005**：功能可在**離線**下完整通過測試（零外部呼叫）；既有 147 測試不回歸。
- **SC-006**：面向使用者文字全繁中。

## Assumptions

- **解說文由使用者 ingest 時宣告**（例如一個「標為解說文」的旗標），工具**不自動判定**——
  符合原則 5「人冊封」。品質層級初期二分（解說文／一般）即可，細分為後續。
- **種子與每日匯整共用檢索語料**（都成 corpus entry）；種子「存在哪」的實作由 `/speckit-plan`
  拍板（新表或合成容器）。
- **一般 URL 抓取**取 title＋主文文字（abstract 級消化即可）；**深度全文 readability 為後續升級**，
  本增量取不到正文即視為抓取失敗。
- **沿用增量 1** 的嵌入後端、相關度門檻、`RagService`；不改增量 1 行為。
- **介面**：本增量為 **CLI `ingest`**；web ingest 介面為後續 fast-follow（範圍外）。
- **範圍外**：根因萃取／試金石／信心層級／人冊封候選（增量 2b）；吸引子拓撲／成核／衰減
  （增量 3）；自動發現要收哪些種子。
- **開發**：TDD 強制（憲章原則 I）——先寫失敗測試再實作；契約測試用離線後端＋可注入假抓取器。
