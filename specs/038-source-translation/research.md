# Phase 0 研究：英→繁一鍵全文翻譯

所有數字皆為**實測**，對真實語料（Lil'Log〈What are Diffusion Models?〉，`chunk_markdown` 切出的 11 塊）。

## 決策 1：並行度 8，不做快取

| 設定 | 11 塊耗時 | 每塊 | 推估 125 塊 |
|---|---:|---:|---:|
| 序列（探針基準） | 58.5s | 5.32s | **11.1 分** |
| workers=4 | 27.1s | 2.46s | 5.1 分 |
| **workers=8** | **9.8s** | **0.89s** | **1.8 分** ✅ |
| workers=16 | 9.4s | 0.86s | 1.8 分 |

- **決策**：`max_workers=8`。
- **理由**：達成 SC-002（≤2 分鐘，實測 1.8 分、**6 倍**加速）；16 沒有進一步收益（外部 API 是瓶頸）。
  8 也正好是既有 `summarize/article.py:20` `build_articles` 的預設值——**沿用而非另立**。
- ⚠️ **這組數字的誠實邊界**：只有 11 塊，`workers=16` 本來就展不開超過 11 路並行，
  所以「16 沒有更快」對**大批次不算數**。可下結論的只有「8 已達標且明顯優於 4」。
- **不做快取的理由**：1.8 分鐘的 on-demand 可接受 ⇒ 落庫快取是**還不需要的複雜度**
  （憲章 IV／YAGNI），且會帶來衰減、失效、DB 膨脹三個新問題。若日後量到不夠快再加。

## 決策 2：沿用既有並行形狀，不另造

`summarize/article.py:18-32` 的 `build_articles` 已經解過同一個問題：

```
with ThreadPoolExecutor(max_workers=min(max_workers, len(pairs))) as ex:
    return list(ex.map(...))
```

三個性質正好是本功能要的：**順序與輸入一致**（`ex.map`）、**單則失敗內部降級不中斷其他則**、
**單一元素時不開池**。⇒ 直接照這個形狀寫，不引入新的並行機制。
（experience：「對外部 API 別在迴圈裡逐一呼叫——批次＋並行」；[history/015](../../knowledge/history/015-web效能與即時進度.md) 靠這招 115s→~20s。）

## 決策 3：保護片段不完整 → 該塊退回原文

- **決策**：翻譯後檢查每個佔位符是否都還在；缺任何一個，該塊**整塊丟棄、用原文**。
- **理由**：翻譯是**生成式**的，模型不保證照規則。探針 11 塊 34 個片段全保住，但那是樣本不是保證。
  少一個佔位符 ⇒ `restore` 會把那段承重內容**永久丟失**（不是改壞，是不見）。
  ⇒ **寧可不翻，不可殘缺**——與 spec 037 FR-006 同方向：少做比做壞安全。
- **否決**：嘗試修補（把缺的片段接回結尾）——位置錯的公式比沒有翻譯更糟。

## 決策 4：進度用既有 SSE 協定

`web/app.py:329` 的 `_stream_gen` 已有 `stage/token/done/error` 協定供 `/chat` 用。
翻譯進度沿用同一個形狀（`stage` 帶已完成/總數），不另造推播機制。
（experience：「慢操作要給即時進度，而非假 spinner」。）

## 決策 5：英文偵測用 CJK 佔比

- **決策**：CJK 字元佔比 < 3% 視為英文來源（FR-009 據此決定要不要提供翻譯動作）。
- **理由**：探針掃語料時就是用這個判準分出三篇英文來源，實測可用；純函式、可測、零相依。
- **否決**：語言偵測套件——為一個閾值判斷引入相依，違反憲章 IV。
