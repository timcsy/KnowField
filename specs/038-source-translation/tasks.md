## 追加：兩個真跑才照出的接縫問題（2026-08-18）

第一次真跑（93 秒、SC-002 達標）之後，**在畫面上**看到「條件式 **Generat**」和落單的
「**離子**」。追下去是兩層，而且第二層比第一層深：

### 層一：獨立翻譯廢掉了 `stitch_chunks` 的不變式

`stitch_chunks` 靠**精確字串比對**去除塊間 40 字元重疊——那對**原文**成立。但每塊獨立翻譯後，
重疊段在前後塊會翻成不同中文，比對失敗 → 兩份都留下 → 殘影。

⚠️ 這裡**沒有任何元件是錯的**：`chunk_markdown` 的重疊對（給檢索）、`stitch_chunks` 的去重疊對
（給原文）、逐塊翻譯也對。壞的是「獨立翻譯」這個新前提**悄悄廢掉了 `stitch_chunks` 依賴的
不變式**。修法：`dedupe_for_translate`（翻譯前裁掉重疊、記下分隔、翻完接回）。

### 層二：檢索的切點不是翻譯的合法切點

修完層一，殘影變了形狀但沒消失。實測：`chunk_markdown` 在 Lil'Log 那篇造出的 124 個接縫，
**55 個切在單字中間**。對 embedding 無害；對翻譯致命——`Conditioned Generat` ＋ `ion`
各自被當成完整文字翻譯，後者成了「離子」。

修法：**不再重用檢索塊**。先拼回全文，再用 `split_units` 切成翻譯單位（段落邊界；過長段落
退而切在空白處；絕不從單字中間切；重組逐字還原）。

驗證：`條件式 Generat` 0 次、`離子` 0 次，讀作「條件式生成」「分類器引導擴散」，行內數學 240 條全保留。

### 層三：修好接縫卻打破了效能

段落切法讓每個清單項（「- 簡化」）自成一單位：125 塊 → **211 單位**，耗時 93s → **137s**，
**SC-002 破了**。原因是我的 `split_units` 只切開過大的、從不合併過小的——`target` 只作用了一半。

修法：合併相鄰小單位到 target 以內。211 → **79 單位**，耗時 137s → **63 秒**
——比接縫修正前的 93s **還快**（單位少了、API 呼叫也少了）。

⇒ 判準：**一個「大小參數」若只管上界不管下界，它就沒有在管大小。**

### 這一輪的測試我寫錯了四次

| 錯法 | 為什麼 |
|---|---|
| 驗即時進度只驗「有沒有事件」 | 存在性 ≠ 時機 |
| 驗即時進度只驗「順序」 | 順序對、時機仍可錯 |
| 語言偵測用不真實的術語密度當樣本 | 樣本不真實 → 失敗的是測試 |
| 接縫斷言「不准有任何共同前後綴」／忽略分隔 | 比較兩個東西前要先確定中間沒有第三個東西 |

⇒ 每一次都是**先拿錯誤實作去撞**才發現的。已蒸餾為 experience 判準。
