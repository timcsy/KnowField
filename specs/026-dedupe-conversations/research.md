# Research: 既有重複對話清理

## D1：計畫純函式、與執行分離
- **決定**：`plan_dedupe(convos, provenance) -> DedupePlan`（分組/選留存/算重指，純值）；repo 執行層才真刪＋重指。
- **理由**：刪除不可逆——把「決定要做什麼」抽成純函式＝離線可窮舉測（分組正確、選對留存、重指正確、空/無重複/異指紋不動），
  再讓薄執行層照計畫做。符合教訓 1、憲章 IV。預覽＝算計畫不執行；確認＝重算再執行（不信 client 帶回計畫，單人本機重算便宜且安全）。

## D2：留存規則＝id 最大（最新）
- **決定**：每組同指紋留 id 最大者；其餘為待刪。
- **理由**：最新份標題/時間最貼近現況（自動標題可能隨對話演進而較好）。規則單純、可測、決定性。

## D3：只併同指紋（非破壞第一原則）
- **決定**：分組鍵＝`conversation_fingerprint(messages)`（spec 025，忽略標題/sources 等易變欄）。只併同鍵。
- **理由**：同指紋＝role＋content 序列**完全相同**＝內容無損可併。異指紋（如 #18/#19，65 vs 70 句）鍵不同→天然分到不同組→**絕不動**。
  這是「非破壞」的機械保證，不靠人判斷。

## D4：重指走既有 why_node 側連結
- **決定**：對「`conversation_id` 指向該組待刪份」的 why_nodes，`UPDATE ... SET conversation_id=留存 id`；再刪多餘 conversations 列。
- **理由**：spec 025 已把由來連結存 why_node 側（多對一）——重指只是改指標，天然支援「多條根因指同一留存份」。
  **根因主張/階梯完全不碰**（FR-006）。清理後 `why_node_provenance` JOIN conversations，每條仍連得到留存份（不斷、不孤兒）。

## D5：兩段式人閘門（原則 5）
- **決定**：GET `/conversations/dedupe`＝預覽（算計畫、不動）；POST `/conversations/dedupe`＝人確認後執行。無自動/背景/定期清理。
- **理由**：刪除不可逆，必須人看過「將發生什麼」再按。GET 純唯讀（守衛測：GET 不改資料）。
