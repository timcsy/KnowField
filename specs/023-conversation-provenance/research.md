# Research：對話的「由來」存檔

無 NEEDS CLARIFICATION——使用者已定案（兩存檔點、存整段＋自動標題）。記關鍵抉擇。

## D1：新表 conversations（vs 塞既有表）
- **決策**：新建 `conversations` 表（title/messages JSON/why_node_id/created_at）。
- **理由**：對話目前是**暫時、client 帶回、不落庫**；本層第一次要**持久化整段對話**——語意上是新實體
  （episodes）。硬塞 digest_entries/why_nodes 會扭曲語意。教訓 8「盡量不動既有結構」下，新表比亂塞乾淨。
- **否決**：把對話塞進 why_nodes 的欄位——根因是「結論」、對話是「現場」，混一起破壞分層。棄。

## D2：守純度＝結構性保證，不靠自律（原則 6）
- **決策**：`conversations` 表**不被任何對話路徑讀進場脈絡**；`build_field_system_prompt` 只吃已冊封根因
  （既有、不改）。寫**守衛測**：存對話後 `/chat` 的 system prompt 不含該對話內容。
- **理由**：這是本 spec 最重要的原則（存下的對話不污染地基）。跟溯源一樣（教訓 7）——**把保證做進結構**
  （對話表根本不接場脈絡的路徑），而非靠提示叮嚀。
- **否決**：把存下的對話也注入回對話「當背景」——正是使用者最怕的污染，明確違硬原則。棄。

## D3：刪根因不崩＝對話變獨立（不孤兒）
- **決策**：`why_node_id` 不設 FK 約束；根因被刪 → 對話仍在 `list_conversations`（自然變獨立存檔），
  只是 `/roots` 不再連得到。
- **理由**：對話是「由來」，就算它的結論根因被刪，那段現場本身仍有回顧價值——不該連帶消失或崩。
- **否決**：ON DELETE CASCADE（連對話一起刪）——丟掉還有價值的現場，棄。

## D4：自動「由來」標題＝LLM 一句摘要，失敗退回
- **決策**：`FieldChat.title(messages)` 生一句（≤20 字）摘要；失敗→退回首個 user 訊息截斷/時間（教訓 3）。
- **理由**：清單一眼認得出是哪段；離線 stub 確定性可測；LLM 失敗不該讓「存對話」崩。

## D5：存的是整段（含來源），不編輯
- **決策**：存 client 帶回的整段 history（role/content/sources）；MVP 不編輯、不版本。
- **理由**：使用者要「查閱當初現場」——忠實整段最有價值；編輯/版本後續。
