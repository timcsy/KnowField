# Feature Specification: 前端 re-platform 階段一——/chat React 打樣 ＋ /api 基座

**Feature Branch**: `033-react-chat-api`

**Created**: 2026-08-06

**Status**: Draft

**Input**: 見 vision 階段 27 phase 1、決策 history/075、設計 draft/2026-07-23-部署與介面路線。用核心頁 `/chat` 證明「React SPA ＋ FastAPI JSON API ＋ SSE 串流」整條跑得動，且**不碰後端邏輯（產品靈魂在 field_chat）**。

## 動機 *(why)*

產品要換上業界 AI 產品的介面（React＋shadcn/ui）、並為上線鋪路。這是一次 **strangler re-platform**：不一次全換，先用**最核心、最能照出問題的頁面 `/chat`** 把整條新管線（新前端 → JSON API → 既有服務 → SSE 串流）打通，證明可行後才逐頁遷。**紅線**：產品的靈魂——反逢迎的膜、溯源引用、「精選＝人親手決定」——**全在後端，本階段一律不動**；新介面只是換一張臉去呼叫同一套邏輯，**不能在翻譯中把這些行為弄掉或圖方便繞過**。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 用新介面跟知識聊、拿到有膜且可溯源的回答（Priority: P1）

使用者在新版 `/chat` 輸入一個想法/問題，即時看到**逐字串流**的回答；回答**帶膜**（不順著他說好聽話、從他的核心理解出發）；引用以 `[n]` 呈現、**點得到對應來源**，收進的來源標「你收藏的」。整體體驗與舊版一致，只是介面換新。

**Why this priority**: 這是整個 re-platform 的「打樣」——聊天是核心體驗，把它在新管線上重現，就證明 SPA＋API＋串流＋溯源整條通。沒有它，階段二～五無從談起。

**Independent Test**: 開新版 `/chat` → 送一句 → 看到串流回答＋`[n]` 引用可跳來源＋「你收藏的」標記；與舊 `/chat` 對同輸入行為一致。後端 API 可離線注入替身測（串流事件、結構化來源）。

**Acceptance Scenarios**:

1. **Given** 使用者在新版 `/chat`，**When** 送出一句話，**Then** 回答**逐步串流**出現（先進度、後逐字），完成後定版。
2. **Given** 回答引用了來源，**When** 顯示，**Then** 內文 `[n]` 可點、跳到對應來源項；收進來源標「你收藏的」。
3. **Given** 同一句輸入，**When** 分別在新版與舊 Jinja `/chat` 送出，**Then** 兩者的回答依據（膜、grounding、引用結構）**行為一致**。

---

### User Story 2 - 整理成重點、逐條親手精選（人閘門）（Priority: P2）

聊完一段，使用者按「整理成重點」，系統提出**候選**核心理解；使用者**逐條檢視、親手精選**進核心理解。新介面裡「精選」一樣是**人的逐條決定**，不是無摩擦一鍵、也不會自動把對話內容變成核心理解。

**Why this priority**: 這是產品的人閘門與反逢迎紀律（原則 5/6）。re-platform 最大的風險就是把這道閘門在翻譯中弄成橡皮圖章——必須在新介面守住。

**Independent Test**: 新版聊一段 → 整理 → 得候選 → 精選一條 → 到核心理解確認在；且**未精選的候選不進核心理解、不進聊天地基**（守衛測，延續既有純度守衛）。

**Acceptance Scenarios**:

1. **Given** 一段對話，**When** 按整理成重點，**Then** 得到**候選**清單（每條可改、標為 AI 推斷）。
2. **Given** 候選，**When** 使用者親手精選其中一條，**Then** 它進核心理解；**未精選的一律不進**。
3. **Given** 跑完整理，**When** 檢查聊天地基，**Then** 對話內容**未自動變成核心理解、未進地基**（純度守衛）。

---

### User Story 3 - 遷移不掉行為、舊版照跑（安全網）（Priority: P3）

在 `/chat` 遷到新介面的過程中，**舊版 `/chat` 仍照常可用**（strangler）；新舊行為一致，膜與純度守衛不變。使用者不會因為換介面而失去任何既有能力或安全性。

**Why this priority**: strangler 是避免「重寫災難」的關鍵紀律。它讓每一步可回退、隨時有可用版本。

**Independent Test**: 部署新版後，舊 `/chat` 路由仍回應且功能完整；既有後端邏輯測（膜、純度守衛、串流）全綠、零回歸。

**Acceptance Scenarios**:

1. **Given** 新版 `/chat` 上線，**When** 訪問舊 `/chat`，**Then** 舊版仍完整運作。
2. **Given** 本階段完成，**When** 跑既有測試，**Then** 全數不回歸；膜/純度守衛行為不變。

---

### Edge Cases

- **串流中斷**：連線中途斷 → 顯示友善「連線中斷，請重試」，不留半殘狀態。
- **後端服務失敗**（金鑰/外部）：回答或整理失敗 → 友善訊息，不崩、不擋介面（教訓 3）。
- **沒有任何核心理解**（空知識庫）：新版仍可聊，並提示可先去精選幾條。
- **SPA 深層路由重整**：直接開/重整 `/chat` 之類的前端路由 → 仍載入應用（伺服器對非 API 路徑回前端入口）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 提供一組 `/api/*` JSON/串流端點，**包既有聊天服務、不重寫其邏輯**（HTML 舊路由與 /api 共用同一套服務函式）：對話狀態、串流回覆、整理候選、精選、自動暫存、核心理解讀取。
- **FR-002**: 串流回覆 MUST 沿用既有的事件協定（進度／逐字／完成／錯誤），使新介面能逐步顯示。
- **FR-003**: 回答的來源 MUST 以**結構化資料**回傳（含編號、標題、連結、是否「你收藏的」）；新介面把 `[n]` 接回對應來源錨點——**溯源靠程式結構保證，不靠模型自律**（原則 3）。
- **FR-004**: 「精選」成核心理解 MUST 由使用者親手逐條觸發（人閘門）；系統 MUST NOT 自動把對話內容或候選變成核心理解、MUST NOT 讓它們自動進聊天推理地基（純度守衛，延續既有）。
- **FR-005**: 回答的「膜」（反逢迎、從使用者核心理解出發）MUST 與現行後端一致——本階段 MUST NOT 修改該後端邏輯。
- **FR-006**: 新舊 `/chat` 對相同輸入 MUST 行為一致（膜、grounding、引用結構）。
- **FR-007**: 舊版 `/chat`（及其他既有頁）MUST 在本階段照常運作（strangler，不破）。
- **FR-008**: 系統 MUST 能服務新前端應用，且對非 API 的前端路徑回傳前端入口（前端路由可直接開啟/重整）。
- **FR-009**: 串流／整理／精選／自動暫存任一失敗 MUST 在邊界攔截、給友善繁中訊息、不崩（教訓 3）。
- **FR-010**: 全繁體中文；既有測試零回歸；核心（非前端）邏輯 MUST NOT 因本階段改動。

### Key Entities *(include if feature involves data)*

- **對話狀態**：核心理解數、上次未存的暫存對話、目前訊息串／草稿——新介面初始化所需。
- **串流事件**：進度、逐字 token、完成（含來源）、錯誤。
- **候選核心理解**：AI 從對話推斷、待使用者精選的暫態項（既有結構）。
- **來源引用**：編號＋標題＋連結＋類別（web／你收藏的），供 `[n]` 溯源。
- 以上皆**復用既有後端資料結構**，本階段不新增資料模型。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新版 `/chat` 能完成一輪：送訊 → 逐步串流回答 → `[n]` 可跳來源 → 「你收藏的」標記正確——與舊版對同輸入行為一致。
- **SC-002**: 使用者能在新版把一段對話整理成候選、**逐條親手精選**進核心理解；**未精選者 100% 不進核心理解、不進地基**（守衛測通過、零污染）。
- **SC-003**: 產品的膜（反逢迎、從核心理解出發）與純度守衛**行為不變**——既有後端相關測試全數不回歸。
- **SC-004**: 舊版 `/chat`（及其他既有頁）在本階段全程可用（strangler 成立）。
- **SC-005**: 使用者可直接開啟或重整新前端路由而正常載入（伺服器對非 API 路徑回前端入口）。
- **SC-006**: 新 `/api` 端點皆有自動化測（串流事件、結構化來源、人閘門守衛）；既有 345 測不回歸；全繁中；核心零相依不變。

## Assumptions

- **架構已定案（vision 階段 27／history 075）**：前端＝React＋Vite＋TypeScript＋Tailwind＋shadcn/ui（骨架 phase 0 已就緒）；後端＝FastAPI 轉 JSON API 並服務前端 build；開發時前端 dev server 把 `/api` 轉給後端。本 spec 的技術脈絡是這個 re-platform 的內在前提，非可選。
- **靈魂在後端、不動**：膜、grounding、串流、整理、精選邏輯皆在既有服務層；本階段只在其上「加一層 JSON/串流門面」與「換一張前端臉」，復用既有離線注入點做測試。
- **前端測試**：本階段以**後端 API 測 ＋ 人工視覺驗收 `/chat`** 為主；重前端測試框架（元件/e2e）**留後續**——UI 的「順不順/好不好看」非 TDD-shaped，誠實記，不在本階段強推。
- **範圍外**：其餘頁面重建（階段二）、PWA/手機分享 share_target（階段四）、auth/多租戶（見 `draft/共享的膜` A/B）、web 測全面遷移（階段三）、舊 Jinja／DaisyUI 退場（階段五）、Next.js（否決）、iOS 分享（平台限制、使用者為 Android）。
