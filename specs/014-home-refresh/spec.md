# 規格：首頁重新整理（從 web 重跑分診）

**功能**：KnowField 路線圖階段 12（web 完整性）
**分支／目錄**：`specs/014-home-refresh/`
**建立日期**：2026-07-25
**狀態**：草擬中（待 plan）

## 摘要

首頁目前只顯示「**上一次 CLI 跑的匯整**」；要拿到最新，使用者得回終端機跑 `knowfield digest`。
本功能在首頁加一個「**🔄 重新整理**」鈕：按一下就從**啟用中的來源**重跑分診、抓最新新聞／
論文、重建匯整、首頁顯示最新（連**熱詞 chips 也一併更新**）——**不必碰 CLI**。直接降低「拿到
最新」的操作成本（根公理）。

因為會抓來源＋逐則消化，**較慢且會花 API 額度**，所以它是**使用者明確觸發的動作**（按鈕），
不自動定時，且鈕旁明確提示成本。

## 使用者情境與測試

### 主要使用者故事

**US1（P1）——一鍵拿到最新**
作為一個在首頁看匯整的使用者，我想直接按個鈕就重新抓最新、重建今天的匯整，不必切到終端機
打指令。

- **驗收情境**：
  1. **Given** 我在首頁，**When** 我按「重新整理」，**Then** 系統從啟用中的來源重跑分診、
     產生一份**新的最新匯整**，完成後**首頁顯示這份最新匯整**（含依它重算的熱詞 chips）。
  2. **Given** 重新整理前已有舊匯整，**When** 重整完成，**Then** 舊匯整**仍保留**（流的紀錄不刪），
     首頁預設顯示**最新**那份。

**US2（P1）——知道這會花成本**
作為使用者，我希望在按之前就知道「這會抓最新、重新消化，需要一點時間、會花額度」，不要
莫名其妙卡住。

- **驗收情境**：
  1. **Given** 首頁的「重新整理」鈕，**When** 我看它，**Then** 旁邊有**明確的繁中提示**說明它會
     抓最新並重新消化、需要一點時間。
  2. **Given** 系統，**When** 我沒有按這個鈕，**Then** **不會自動**重跑分診（無背景定時刷新）。

**US3（P2）——外部不穩不崩**
作為使用者，就算某些來源當日取不到、或後端暫時失敗，我仍希望有清楚交代，而不是看到錯誤堆疊。

- **驗收情境**：
  1. **Given** 部分來源當日取不到，**When** 重整完成，**Then** 匯整**照常產出**並**明確標示缺漏
     來源**（沿用既有缺漏標示）。
  2. **Given** 重跑分診整體失敗（後端／網路），**When** 我按重新整理，**Then** 頁面顯示**友善繁中**
     說明、**不噴錯誤堆疊、不回伺服器錯誤**；既有匯整不受影響。

### 邊界情況

- **首次（無任何來源）**：沿用預設來源清單重跑。
- **重整期間**：同步等待完成（MVP）；完成後導回首頁看結果。
- **連續多次重整**：每次產生一份新匯整（append），首頁顯示最新；不覆蓋、不去重同日。
- **離線後端**：走離線 stub 產生（可測、零外部呼叫）。

## 需求（功能）

- **FR-001**：首頁**必須**提供一個「重新整理」動作，觸發後**從啟用中的來源重跑分診**、產生一份
  **新的匯整**並保存，完成後**首頁顯示最新那份**（含依它重算的熱詞）。
- **FR-002**：重新整理**必須是使用者明確觸發的動作**；系統**不得自動／定時**重跑分診。
- **FR-003**：「重新整理」動作旁**必須有明確繁中提示**，說明它會抓最新並重新消化、需要一點時間
  （成本可見）。
- **FR-004**：重整**必須不刪除既有匯整**（流的紀錄保留）；每次重整**新增**一份匯整。
- **FR-005**：部分來源當日取不到時，匯整**必須照常產出並標示缺漏來源**（沿用既有缺漏機制，憲章 V）。
- **FR-006**：重跑分診**整體失敗／逾時**時，**必須**以**友善繁中**處理，**不得**顯示例外堆疊或回傳
  伺服器錯誤；既有匯整不受影響。
- **FR-007**：重整的分診產生**必須可被測試以離線方式注入**（零外部網路呼叫可通過契約測試）。
- **FR-008**：本功能**必須不新增資料表、不改動既有資料表**（用既有匯整保存機制）。
- **FR-009**：所有面向使用者文字**必須為繁體中文**。

### 明確排除（範圍外，防蔓延）

- **串流即時進度**（逐則推送，像主題深挖）——後續（需把分診管線改為可逐步回報）。
- **自動／定時刷新、背景排程**——不做。
- **在 UI 選日期／主題／數量**——沿用既有興趣清單、來源與預設數量。
- **覆寫／去重同日匯整**——每次新增一份即可。
- **CLI**（已有 `knowfield digest`）。

## 關鍵實體

- **匯整（Digest）**：一次分診的結果（既有實體）；重整＝新增一份最新的，不動舊的。
- **啟用中的來源**：重整只抓使用者啟用的來源（沿用來源訂閱管理）。

## 假設

- 沿用既有分診管線（抓取→去重→排序→消化）與匯整保存；不改資料結構（教訓 8）。
- 沿用熱詞 chips（階段 11）：首頁顯示新匯整時一併重算。
- 同步執行（MVP）：使用者按下後等待完成再看結果；串流進度列後續。
- 重整用當前日期；沿用 `config` 的匯整數量與使用者興趣／來源設定。

## 成功標準（可驗，技術中立）

- **SC-001**：使用者在首頁按「重新整理」後，**看到一份剛產生的最新匯整**（含更新後的熱詞），
  全程**不需離開網頁介面**。
- **SC-002**：**沒有使用者動作時系統不自動重跑**；動作旁有清楚的成本提示。
- **SC-003**：重整**不刪既有匯整**；缺漏來源被明確標示。
- **SC-004**：外部失敗時使用者看到**友善說明**、頁面不崩、不顯示技術錯誤。
- **SC-005**：重整可**離線測試**（零外部呼叫）；**不新增／不改資料表**；既有 243 測試不回歸。
- **SC-006**：**串流進度／自動定時／UI 選項未出現**在本次交付（範圍守住）。
