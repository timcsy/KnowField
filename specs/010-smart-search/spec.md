# 規格：智慧搜尋（搜尋結果的消化＋溯源整理）

**功能**：LearnNews 路線圖階段 9 增量 b
**分支／目錄**：`specs/010-smart-search/`
**建立日期**：2026-07-25
**狀態**：草擬中（待 plan）

## 摘要

現在的 `/search`（階段 9）只把搜尋後端回的**原始結果**倒出來，使用者得自己一則則點進去讀。
本增量把工具**自己的核心本領（消化、溯源、排序）**套到 live 搜尋結果上——**「RAG over 搜尋
結果」**：使用者打一個 query，工具**讀完前幾則結果、合成一段可回溯的繁中「整理」重點**、把
結果依相關度排好，使用者看完重點再挑有價值的「收進」成種子。

一句話：**搜尋 → 讀完告訴你重點＋來源 → 你挑要留的收進。**

## 使用者情境與測試

### 主要使用者故事

**US1（P1）——讀完給我重點（整理）**
作為一個沒時間逐則點開搜尋結果的使用者，我打一個 query 後，希望工具**先讀過前幾則結果、
給我一段整理好的繁中重點**，每個重點**標明出自哪一則結果**（可點回核對），這樣我不必自己
讀完每則就能掌握這次搜尋的全貌。

- **驗收情境**：
  1. **Given** 我在 `/search` 打「Multi Agent RL」且搜尋後端有回結果，**When** 頁面載入，
     **Then** 頁面**頂端**出現一段「整理」重點，且重點中的每個 `[n]` 標記可**點擊捲動到下方
     對應的第 n 則結果卡**。
  2. **Given** 整理內容，**When** 我核對某個 `[n]`，**Then** 它指向的是**真實抓到的那則結果**
     （標題／網址對得上），不是工具憑空生成的來源。
  3. **Given** 搜尋結果與 query **完全無關**（沒有可用材料），**When** 產生整理，**Then** 工具
     **明說「沒有相關材料」不杜撰**，不硬編一段像樣但無根據的整理。

**US2（P1）——排序把最相關的擺前面**
作為使用者，我希望結果**依與 query 的相關度排序**，最相關的擺最前面，省得我從一堆結果裡
自己挑。

- **驗收情境**：
  1. **Given** 搜尋後端回多則結果，**When** 頁面呈現，**Then** 結果清單**依相關度排序**（最相關
     在前），且整理的 `[n]` 編號與**排序後**的清單一致。

**US3（P1）——挑到的才留（人冊封不變）**
作為使用者，我看完整理與結果後，想**自己決定**把哪幾則收進知識庫；沒挑的、以及整理本身，
都不該留下。

- **驗收情境**：
  1. **Given** 排序後的結果清單，**When** 我對某則按「收進」，**Then** 它**照既有流程冊封成種子**
     （行為與階段 9 完全一致），之後 `ask` 可檢索到。
  2. **Given** 一次搜尋，**When** 我沒有按任何「收進」，**Then** **搜尋結果與整理都不落庫**
     （下次不會看到殘留），知識庫沒有新增任何東西。

**US4（P2）——外部不穩時仍可用（友善降級）**
作為使用者，就算某些結果的內文抓不到、或整理服務暫時失敗，我仍希望頁面**照常給我能用的
東西**、用友善繁中說明，而不是看到一頁錯誤堆疊。

- **驗收情境**：
  1. **Given** 某則結果的內文**抓不到**，**When** 產生整理，**Then** 工具**退回用該則的既有摘要
     （snippet）**或友善標示該則，**不讓整個整理壞掉**。
  2. **Given** 整理服務（或內文抓取）**整體失敗／未設金鑰**，**When** 頁面載入，**Then** 顯示
     **友善繁中說明**、**仍照常列出原始結果（可收進）**，不噴 traceback、不回 500。

### 邊界情況

- **query 為空**：不觸發搜尋與整理（維持階段 9 行為）。
- **搜尋回 0 則**：顯示「查無」，不產生整理（沒有材料可整理）。
- **只有 1 則結果**：仍照常抓內文、產生整理（`[1]`）。
- **所有結果內文都抓不到**：整理退回全用 snippet；若 snippet 也不足以支撐 → 明說材料有限／
  沒有相關材料，不杜撰。
- **離線（無真實後端金鑰）**：走離線 stub（假搜尋＋stub 整理），流程能零外部呼叫跑完並可測。

## 需求（功能）

- **FR-001**：`/search` 收到非空 query 時，除了列出搜尋結果，**必須**對**前 N 則**（預設 3–4，
  由 plan 定）結果讀取其內文，合成一段**繁中「整理」重點**顯示於頁面頂端。
- **FR-002**：整理中的每個要點**必須以 `[n]` 標記**掛到對應的結果，且 `[n]` 在頁面上是**可點擊
  的連結、點擊捲動到下方第 n 則結果卡**（沿用問答頁的維基式引用呈現）。
- **FR-003**：整理**必須只根據實際抓到的結果內文／摘要**產生（grounded）；當可用材料與 query
  **完全無關**時，**必須明確告知「沒有相關材料」而非杜撰**。此保證**須落在程式結構**（沿用
  既有 grounded 合成與「無材料」判定），不得僅靠提示詞自律。
- **FR-004**：結果清單**必須依與 query 的相關度排序**（最相關在前）；整理的 `[n]` 編號**必須與
  排序後**的清單順序一致。
- **FR-005**：每則結果**必須保留「收進」動作**，行為與階段 9 完全一致（冊封成種子、之後可
  `ask`）。
- **FR-006**：搜尋結果與整理**一律不落庫**；**只有**使用者「收進」的那則才成為種子。
- **FR-007**：**單則結果內文抓取失敗**時，該則**必須退回使用其既有摘要（snippet）或被友善
  標示**，**不得**使整段整理或整頁失敗。
- **FR-008**：內文抓取或整理服務**整體失敗／未設金鑰／逾時**時，頁面**必須**以**友善繁中**說明，
  且**仍照常列出原始結果（可收進）**；不得回傳伺服器錯誤或顯示例外堆疊。
- **FR-009**：在**離線後端**（無金鑰）下，`/search` 的整理流程**必須能零外部網路呼叫**完成並
  通過契約測試。
- **FR-010**：所有面向使用者的文字**必須為繁體中文**。
- **FR-011**：本功能**不得**新增資料表或改動既有已出貨資料結構（收進沿用既有種子容器）。

### 明確排除（範圍外，防蔓延）

- **探索**（multi-angle 查詢擴展／agentic 讀完看缺口再搜）——**本規格絕不做**，列為 optional、
  另立里程碑（成本翻倍）。
- 把 web search 併進 `pull`（收斂管線）、每來源品質加權、CLI（先 web）、趨勢讀數（B）。
- 整理結果落庫或快取（絕不；只有收進成種子）。
- 更換／新增搜尋後端（沿用階段 9 的 WebSearch）。

## 關鍵實體

- **整理（Digest/Overview）**：對一次搜尋前 N 則結果合成的一段繁中重點文字，含 `[n]` 引用；
  **短暫、不落庫**；「無材料」時為一則明說沒有相關材料的訊息。
- **搜尋結果（SearchResult）**：沿用階段 9（標題／網址／摘要）；本增量**多一個排序位置**與
  「是否被整理引用」的對應（`[n]` ↔ 第 n 則）。
- **內文（抓取所得）**：對結果網址抓到的正文，作為整理的材料；抓不到時以 snippet 代替。

## 假設

- 沿用階段 9 的可插拔 `WebSearch`（離線 stub／真實 API）與 `/search` 頁；本增量疊在其上。
- 沿用階段 4/5 的 RAG 合成（grounded answerer＋「無材料」判定）與問答頁的 `[n]` 溯源渲染。
- 沿用階段 3（種子）的 `fetch_url` 抓內文與「收進」→ 種子流程。
- 相關度排序沿用既有嵌入器（Embedder）＋餘弦相似度；離線 stub 下為確定性行為。
- 前 N 預設 3–4（plan 定）：越多整理越全但越慢／越貴；使用者觸發、單次可接受。

## 成功標準（可驗，技術中立）

- **SC-001**：使用者在 `/search` 打一個 query，**看到一段整理重點＋依相關度排序的結果清單**；
  整理的每個引用可點回對應結果。
- **SC-002**：整理內容**可逐點回溯到真實結果**；當結果與 query 無關時，工具**明說沒有相關材料**
  （不杜撰）——以一組正例／反例查詢驗證。
- **SC-003**：使用者**只有按下「收進」的結果會進知識庫**；未收進的結果與整理都不殘留。
- **SC-004**：當部分結果內文抓不到或整理服務失敗時，使用者**仍看到可用的結果清單與友善說明**，
  頁面不崩、不顯示技術錯誤。
- **SC-005**：離線（無金鑰）下整理流程可跑完並通過測試；**既有 197 項測試不回歸**。
- **SC-006**：**探索功能未出現**在本次交付中（範圍守住）。
