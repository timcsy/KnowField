# spec 076：對專案也能聊——**語料是那個專案的 `knowledge/`**（階段 70 第一刀）

## 為什麼

> 「我想要對專案也可以聊⋯但是是**以專案開發為目的**的」

而開發模式現在是**唯讀的閱讀器**。你讀得到 VizGPT 的 141 份 history，
但**問不了它任何問題**。

## ⚠️ 這一刀不打薄那道膜——它承認有兩個場

spec 074 我把問題寫成「**外部知識該不該進檢索語料**」。**那是問錯了。**
正確的是「**哪一個場**」：

| 你站在哪 | 語料 |
|---|---|
| 💬 互動 | 你自己的理解（`why_nodes`） |
| 🧰 開發（站在某個 base 裡） | **那個 base 的 `knowledge/`** |

⇒ VizGPT 的判準**只在你明確站在 VizGPT 裡**時是語料，切回來就不是。
**spec 074 既有的兩層測試（行為＋掃描）照樣要綠**——那條線沒有變鬆，是多了第二個場。

## FR

- **FR-001** `retrieve_corpus(...)` 多一個 `entries=` 參數（預設 `None` ＝ 照舊）。
  ⚠️ 只有兩個呼叫點，**不要改它們的行為**。
- **FR-002** ⚠️ **切塊**：`ext_items` 共 **184 萬字**、最大一份 **226,460 字**——整份塞不進 context。
  第一刀只切 `experience`／`concepts`／`principles`／`vision` 四層。
- **FR-003** ⚠️ **要說明白哪幾層進了語料**——否則「答不出來」會被誤讀成「它不知道」。
- **FR-004** 站在某個 base 裡聊；回答的引用**看得出是哪一份檔案**。
- **FR-005** 對話標記屬於哪個專案（`conversations` 加一欄，走 `_ADD_COLUMNS`）。
- **FR-006** ⚠️ **兩個場不互相污染**：互動模式的語料**完全不含** `ext_*`。
- **FR-007** 每個查詢過 `_own()`；新表帶 `owner_id` ＋ `persona_id`。

## 驗收

1. 站在 VizGPT 裡問一個**只有它的 knowledge 答得出來**的問題 → 答得出來
2. 回答的引用看得出**是哪一份檔案**
3. ⚠️ 切回互動模式問**同一句** → **答不出來**（行為層）
4. ⚠️ 掃描層：`list_corpus_entries` 的組成不含任何 `ext_` 表（spec 074 那條不准鬆）
5. 畫面上**說得出**哪幾層進了語料
6. 換 owner／persona 看不到

## Out of scope

**產出 draft 與送回去**（第二刀）· `history`／`episodes`／`draft`／`skills` 進語料 ·
來源收 repo 以外的東西 · 「專案底下再分領域」 ·
⚠️ **寫回去碰 `draft/` 以外的任何東西——這條是永久的**
（`experience.md` 不是 append-only，它會被反流、合併、拆分）
