# spec 074：互動／開發雙模式（階段 69 第一刀）

## 為什麼

> 使用者給了三個對照（Gemini 即時通訊/Spark · Claude Code 💬/`</>` · 對話/工作）。
> 那個軸分的是：**線性的、當下的來回** vs **有狀態、有產物、會回頭看的工作**。

⚠️ **而這不是換版面。** 階段 68 抓進來的六層——`vision`／`principles`／`experience`／`draft`
——**正好就是開發模式那四個入口**。而正式庫的 **514 個檔案現在沒有任何消費者**
（只有教訓抽取與死指標用得到）。⇒ 這一刀讓它們第一次被讀得到。

## ⚠️ 這一刀逼出一個上一刀刻意延後的決定

spec 073 的 out of scope 寫著：「讓 `ext_items` 進搜尋／檢索語料——那是**另一個決定**」。
而 §七 的判準是「**⌘K 必須跨模式**」⇒ 現在必須答。

**答案：進搜尋，不進檢索語料。**

| | 是什麼 | 外部知識 |
|---|---|---|
| **搜尋**（⌘K） | 「找得到」 | ✅ 進——但**結果標來源**，你看得出那是別人的 |
| **檢索語料** | 聊天時當你的**地基** | ❌ 不進——那是原則 6 那道膜守的東西 |

兩件事本來就不同。混為一談的話，別人的判準會**沒有經過冊封**就開始影響你的回答。

## FR

- **FR-001** 模式切換擺 logo 旁；⚠️ **分層不並列**——persona 切換器留在下面那層
  （兩個切換器搶同一格會爆）。
- **FR-002** 模式走 **URL**（`/dev/...`），不是元件狀態：可分享、上一頁有用、重整不掉。
- **FR-003** 開發模式：選一個 base（`ext_bases`）→ 📐路線圖 📖原則 🧪經驗 ✍draft
  四個閱讀頁，內容讀 `ext_items`，以 markdown 呈現。
- **FR-004** ⚠️ **⌘K 跨模式**：搜得到外部知識，且每筆**標出它來自哪個 base**。
- **FR-005** ⚠️ **外部知識不進 `list_corpus_entries`**——有測試釘住（沿用 spec 062 FR-005 的做法）。
- **FR-006** **persona 不進開發模式**——專案 base 天然隔離，再疊一層可見性只是負擔。
- **FR-007** ⚠️ **不做「移動」功能**：**寫在哪就算哪邊**。
  跨界只有一條路——在多個 base 獨立撞到 → 提議升格（階段 68 已建）。
  ⇒ 也就沒有「我到底搬過去了沒」那種狀態，而那是雙模式介面第三個坑。
- **FR-008** 沒有任何 base 時，開發模式要**說怎麼開始**（指向 🌍 那一頁），不是空白。

## 驗收

1. 切到開發模式 → 選 KnowField → 四個頁面都讀得到內容（路線圖／原則／經驗／draft）
2. ⌘K 搜一個**只存在於外部 base** 的字 → 找得到，且看得出來自哪個 base
3. ⚠️ 同一個字在**聊天的檢索語料**裡搜不到（掃程式碼＋行為各一條）
4. 開發模式**沒有** persona 切換器（掃原始碼）
5. ⚠️ 介面上**沒有任何「移動到另一邊」的動作**（掃原始碼）
6. 重整 `/dev/experience?base=…` 回到同一個地方
7. 換 owner／persona 看不到別人的 base
8. 沒有 base 時，開發模式顯示怎麼開始
